# 相关数据库表结构

## 说明

牛券原始业务是优惠券系统。为了方便你迁移到“景区订票/订单”口径，本文档只保留和下面两个亮点直接相关的表：

1. MQ 消息幂等消费
2. 预约提醒、超时关单、锁定、核销、退款回退等状态流转

需要先说明一个事实：

- 当前源码里没有单独的“MQ 去重表”实体、Mapper 或建表 SQL。
- 第 22 小节文档写的是“去重表 + Redis”的思路。
- 当前仓库实际落地代码是“注解 + AOP + Redis 幂等 Key + Lua”。

所以如果你面试时说“基于注解 + 去重表实现 MQ 幂等”，要么你明确说这是课程方案，要么你按源码实说“基于注解 + Redis 幂等 Key 实现 MQ 幂等消费”。

## 1. 优惠券模板表 `t_coupon_template_*`

源码位置：

- `code/onecoupon/resources/database/onecoupon.sql`
- `code/onecoupon/engine/src/main/java/com/nageoffer/onecoupon/engine/dao/entity/CouponTemplateDO.java`

SQL 关键字段：

```sql
CREATE TABLE `t_coupon_template_0` (
    `id` bigint(20) NOT NULL AUTO_INCREMENT COMMENT 'ID',
    `name` varchar(256) DEFAULT NULL COMMENT '优惠券名称',
    `shop_number` bigint(20) DEFAULT NULL COMMENT '店铺编号',
    `source` tinyint(1) DEFAULT NULL COMMENT '优惠券来源',
    `target` tinyint(1) DEFAULT NULL COMMENT '适用对象',
    `goods` varchar(64) DEFAULT NULL COMMENT '优惠商品编码',
    `type` tinyint(1) DEFAULT NULL COMMENT '优惠类型',
    `valid_start_time` datetime DEFAULT NULL COMMENT '有效期开始时间',
    `valid_end_time` datetime DEFAULT NULL COMMENT '有效期结束时间',
    `stock` int(11) DEFAULT NULL COMMENT '库存',
    `receive_rule` json DEFAULT NULL COMMENT '领取规则',
    `consume_rule` json DEFAULT NULL COMMENT '消费规则',
    `status` tinyint(1) DEFAULT NULL COMMENT '状态',
    `create_time` datetime DEFAULT NULL COMMENT '创建时间',
    `update_time` datetime DEFAULT NULL COMMENT '更新时间',
    `del_flag` tinyint(1) DEFAULT NULL COMMENT '删除标记',
    PRIMARY KEY (`id`),
    KEY `idx_shop_number` (`shop_number`) USING BTREE
);
```

字段说明与参考值：

| 字段 | 作用 | 参考值 | 说明 |
| --- | --- | --- | --- |
| `id` | 模板主键 | `1001` | 一张模板的唯一标识。用户领券、预约提醒、结算时都会通过它关联模板。 |
| `name` | 优惠券名称 | `景区早鸟票100减20券` | 券的展示名称，面向商家和用户。 |
| `shop_number` | 店铺编号 | `1810714735922956666` | 代表是哪家商户/景区创建的模板，也是分片键。 |
| `source` | 模板来源 | `0` 或 `1` | `CouponTemplateDO` 注释里定义：`0` 店铺券，`1` 平台券。代码里 `couponTemplate.getSource() == 0` 时会校验订单店铺必须一致。 |
| `target` | 适用对象 | `0` 或 `1` | `CouponTemplateDO` 注释里定义：`0` 商品专属，`1` 全店通用。代码里 `couponTemplate.getTarget().equals(0)` 表示要按具体商品校验。 |
| `goods` | 适用商品编码 | `SPU_10001` 或 `null` | 当 `target = 0` 时有值，表示这张券只针对某个商品；当 `target = 1` 时通常为空。 |
| `type` | 券类型 | `0` / `1` / `2` | `CouponTemplateDO` 注释与 `UserCouponServiceImpl` 中的 `switch` 定义：`0` 立减券，`1` 满减券，`2` 折扣券。 |
| `valid_start_time` | 生效开始时间/开抢时间 | `2026-04-20 10:00:00` | 预约提醒就是基于这个时间计算 `delayTime`；模板查询时也会判断是否处于可用期。 |
| `valid_end_time` | 生效结束时间 | `2026-04-30 23:59:59` | 模板缓存 TTL 和用户券有效期计算都与它相关。 |
| `stock` | 模板总库存 | `1000` | 秒杀/兑换时先在 Redis 预热，再异步落库扣减。 |
| `receive_rule` | 领取规则 JSON | `{"limitPerPerson":"1"}` | `UserCouponServiceImpl` 里会解析 `limitPerPerson`，用于限制每人最多可领取次数。 |
| `consume_rule` | 使用规则 JSON | `{"termsOfUse":100,"maximumDiscountAmount":20}` | 代码里会读取 `termsOfUse`、`maximumDiscountAmount`、`discountRate` 等字段，校验订单金额并计算折扣。 |
| `status` | 模板状态 | `0` 或 `1` | `CouponTemplateStatusEnum` 定义：`0` 生效中，`1` 已结束。查询模板时要求状态必须为 `ACTIVE(0)`。 |
| `create_time` | 创建时间 | `2026-04-10 09:00:00` | 商家创建模板的时间。 |
| `update_time` | 更新时间 | `2026-04-10 09:30:00` | 模板最后一次修改时间。 |
| `del_flag` | 逻辑删除标记 | `0` 或 `1` | `0` 未删除，`1` 已删除。正常可用模板通常都是 `0`。 |

`consume_rule` 常见参考值可以按代码理解成这三种：

```json
// 立减券
{"maximumDiscountAmount":20}

// 满减券
{"termsOfUse":100,"maximumDiscountAmount":20}

// 折扣券
{"termsOfUse":100,"discountRate":0.90,"maximumDiscountAmount":30}
```

`receive_rule` 在当前代码里至少会读取这个字段：

```json
{"limitPerPerson":"1"}
```

也就是“每人最多可领 1 张”。

它在这两个亮点里承担的作用：

- 秒杀/兑换时，`stock` 是库存源头。
- 预约提醒时，`valid_start_time` 是提醒触发的基准时间。
- 订单锁定时，`consume_rule` 会参与金额校验和使用规则校验。

如果迁移成景区订票口径，可以把它理解成：

- `票种模板`
- `场次票模板`
- `景区门票售卖模板`

## 2. 用户优惠券表 `t_user_coupon_*`

源码位置：

- `code/onecoupon/resources/database/onecoupon.sql`
- `code/onecoupon/engine/src/main/java/com/nageoffer/onecoupon/engine/dao/entity/UserCouponDO.java`

SQL 关键字段：

```sql
CREATE TABLE `t_user_coupon_0` (
    `id` bigint(20) NOT NULL AUTO_INCREMENT COMMENT 'ID',
    `user_id` bigint(20) DEFAULT NULL COMMENT '用户ID',
    `coupon_template_id` bigint(20) DEFAULT NULL COMMENT '优惠券模板ID',
    `receive_time` datetime DEFAULT NULL COMMENT '领取时间',
    `receive_count` int(3) DEFAULT NULL COMMENT '领取次数',
    `valid_start_time` datetime DEFAULT NULL COMMENT '有效期开始时间',
    `valid_end_time` datetime DEFAULT NULL COMMENT '有效期结束时间',
    `use_time` datetime DEFAULT NULL COMMENT '使用时间',
    `source` tinyint(1) DEFAULT NULL COMMENT '券来源',
    `status` tinyint(1) DEFAULT NULL COMMENT '状态 0未使用 1锁定 2已使用 3已过期 4已撤回',
    `create_time` datetime DEFAULT NULL COMMENT '创建时间',
    `update_time` datetime DEFAULT NULL COMMENT '更新时间',
    `del_flag` tinyint(1) DEFAULT NULL COMMENT '删除标记',
    PRIMARY KEY (`id`),
    UNIQUE KEY `idx_user_id_coupon_template_receive_count` (`user_id`,`coupon_template_id`,`receive_count`) USING BTREE,
    KEY `idx_user_id` (`user_id`) USING BTREE
);
```

字段说明与参考值：

| 字段 | 作用 | 参考值 | 说明 |
| --- | --- | --- | --- |
| `id` | 用户券实例主键 | `50001` | 代表用户真正拿到手的一张券实例，不是模板。后续锁定、核销、退款都是围绕这个实例操作。 |
| `user_id` | 用户 ID | `20001` | 表示这张券属于哪个用户。 |
| `coupon_template_id` | 关联模板 ID | `1001` | 指向 `t_coupon_template.id`，表示这张用户券来自哪一种模板券。 |
| `receive_time` | 领取时间 | `2026-04-11 10:00:00` | 用户领券成功或 MQ 消费成功落库的时间。 |
| `receive_count` | 第几次领取 | `1`、`2` | 代码里这个值来自 Lua 返回结果，第一次领到通常是 `1`，第二次是 `2`。并且与唯一索引一起约束重复实例写入。 |
| `valid_start_time` | 实例生效开始时间 | `2026-04-11 10:00:00` | 在 `UserCouponRedeemConsumer` 里通常会直接设为领取时刻。 |
| `valid_end_time` | 实例生效结束时间 | `2026-04-18 10:00:00` | 在 `UserCouponRedeemConsumer` 中根据模板 `consumeRule` 里的 `validityPeriod` 计算得出。 |
| `use_time` | 使用时间 | `2026-04-12 14:30:00` 或 `null` | 未使用时通常为空；核销/支付成功后会有业务意义。 |
| `source` | 券实例来源 | `0` / `1` / `2` | 表注释定义：`0` 领券中心，`1` 平台发放，`2` 店铺领取。代码中会把请求参数里的 `source` 直接写入实例。 |
| `status` | 用户券状态 | `0` / `1` / `2` / `3` / `4` | `UserCouponStatusEnum` 定义：`0` 未使用，`1` 锁定中，`2` 已使用，`3` 已过期，`4` 已撤回。 |
| `create_time` | 创建时间 | `2026-04-11 10:00:00` | 记录插入时间。 |
| `update_time` | 更新时间 | `2026-04-11 10:05:00` | 状态变化时会更新。 |
| `del_flag` | 逻辑删除标记 | `0` 或 `1` | `0` 未删除，`1` 已删除。正常业务数据一般为 `0`。 |

`status` 在当前代码里的典型流转是：

```text
0 未使用 -> 1 锁定中 -> 2 已使用 -> 退款后回退为 0 未使用
```

另外还有一条过期链路：

```text
0 未使用 -> 3 已过期
```

这是由延时消息消费者 `UserCouponDelayCloseConsumer` 触发的。

它在这两个亮点里承担的作用：

- MQ 成功消费后，会落一条用户实例记录。
- 状态流转时，`status` 会从未使用改为锁定、已使用，再在退款时回退。
- 唯一索引 `user_id + coupon_template_id + receive_count` 能辅助拦住部分重复写入。

如果迁移成景区订票口径，可以把它理解成：

- `用户持有的票实例`
- `用户订单关联的权益实例`

## 3. 结算单表 `t_coupon_settlement_*`

源码位置：

- `code/onecoupon/resources/database/onecoupon.sql`
- `code/onecoupon/engine/src/main/java/com/nageoffer/onecoupon/engine/dao/entity/CouponSettlementDO.java`

SQL 关键字段：

```sql
CREATE TABLE `t_coupon_settlement_0` (
    `id` bigint(20) NOT NULL AUTO_INCREMENT COMMENT 'ID',
    `order_id` bigint(20) DEFAULT NULL COMMENT '订单ID',
    `user_id` bigint(20) DEFAULT NULL COMMENT '用户ID',
    `coupon_id` bigint(20) DEFAULT NULL COMMENT '优惠券ID',
    `status` int(11) DEFAULT NULL COMMENT '结算单状态 0锁定 1已取消 2已支付 3已退款',
    `create_time` datetime DEFAULT NULL COMMENT '创建时间',
    `update_time` datetime DEFAULT NULL COMMENT '更新时间',
    PRIMARY KEY (`id`),
    KEY `idx_user_id` (`user_id`) USING BTREE
);
```

字段说明与参考值：

| 字段 | 作用 | 参考值 | 说明 |
| --- | --- | --- | --- |
| `id` | 结算单主键 | `80001` | 一条订单使用优惠券的结算记录主键。 |
| `order_id` | 订单 ID | `90001` | 代表是哪一笔订单锁定或使用了这张券。迁移成景区订票口径时，就是票务订单 ID。 |
| `user_id` | 用户 ID | `20001` | 代表这条结算记录属于哪个用户。 |
| `coupon_id` | 用户券实例 ID | `50001` | 指向 `t_user_coupon.id`，表示订单操作的是哪一张具体的用户券，而不是模板券。 |
| `status` | 结算单状态 | `0` / `1` / `2` / `3` | `CouponSettlementDO` 注释定义：`0` 锁定，`1` 已取消，`2` 已支付，`3` 已退款。 |
| `create_time` | 创建时间 | `2026-04-11 11:00:00` | 一般是创建锁定记录的时间。 |
| `update_time` | 更新时间 | `2026-04-11 11:05:00` | 支付、取消、退款时会更新。 |

`status` 在当前代码里的典型流转是：

```text
0 锁定 -> 2 已支付 -> 3 已退款
```

如果要补“超时关单/超时取消”链路，则可以扩展成：

```text
0 锁定 -> 1 已取消
```

当前代码里三种典型业务动作分别对应：

- `createPaymentRecord`：创建结算单并写入 `status = 0`
- `processPayment`：把 `status = 0` 更新成 `status = 2`
- `processRefund`：把 `status = 2` 更新成 `status = 3`

它在这两个亮点里承担的作用：

- 记录“某张券被哪张订单锁定、支付、退款”的过程。
- 状态流转的主表是它，不是 `t_user_coupon`。
- `t_user_coupon` 保存的是实例状态，`t_coupon_settlement` 保存的是订单结算状态。

如果迁移成景区订票口径，可以把它直接理解成：

- `票务订单锁定记录`
- `订单优惠/权益结算单`

## 4. 预约提醒表 `t_coupon_template_remind`

源码位置：

- `code/onecoupon/resources/database/onecoupon.sql`
- `code/onecoupon/engine/src/main/java/com/nageoffer/onecoupon/engine/dao/entity/CouponTemplateRemindDO.java`

SQL 关键字段：

```sql
CREATE TABLE `t_coupon_template_remind` (
    `user_id` bigint(20) NOT NULL COMMENT '用户ID',
    `coupon_template_id` bigint(20) NOT NULL COMMENT '券ID',
    `information` bigint(20) DEFAULT NULL COMMENT '预约提醒位图信息',
    `shop_number` bigint(20) DEFAULT NULL COMMENT '店铺编号',
    `start_time` datetime DEFAULT NULL COMMENT '开抢时间',
    PRIMARY KEY (`user_id`, `coupon_template_id`)
);
```

字段说明与参考值：

| 字段 | 作用 | 参考值 | 说明 |
| --- | --- | --- | --- |
| `user_id` | 用户 ID | `20001` | 表示是哪位用户创建了提醒。 |
| `coupon_template_id` | 模板 ID | `1001` | 指向 `t_coupon_template.id`，表示提醒针对哪张模板券。 |
| `information` | 提醒位图信息 | `1`、`2`、`4096`、`4100` | 不是普通状态字段，而是位图。用于把“提醒时间 + 提醒方式”压缩存到一个 `Long` 中。 |
| `shop_number` | 店铺编号 | `1810714735922956666` | 代表这张券属于哪家店铺/景区。 |
| `start_time` | 开抢时间/提醒基准时间 | `2026-04-20 10:00:00` | 所有提醒时间都是围绕这个时间向前偏移计算出来的。 |

`user_id + coupon_template_id` 作为联合主键，表示：

- 一个用户对同一张模板券，只有一条提醒主记录
- 如果设置了多个提醒时间或提醒方式，不会插多行，而是合并进 `information`

`information` 在当前代码里的编码方式来自 `CouponTemplateRemindUtil`：

- 每 `5` 分钟一个档位
- 每种提醒方式占 `12` 个 bit
- 当前提醒方式枚举：
  - `0`：App 通知
  - `1`：Email 提醒

常见参考值可以这样理解：

```text
1     = App 提前 5 分钟提醒
2     = App 提前 10 分钟提醒
4     = App 提前 15 分钟提醒
4096  = Email 提前 5 分钟提醒
8192  = Email 提前 10 分钟提醒
4100  = App 提前 15 分钟提醒 + Email 提前 5 分钟提醒
```

也就是说：

- `information = 1` 不是“状态 1”，而是一个位图值
- `information = 4100` 表示一条记录里同时配置了两种提醒

如果迁移成景区订票口径，可以把它理解成：

- `用户门票开售提醒表`
- `预约提醒配置表`

## 5. 分片情况

从 `shardingsphere-config.yaml` 看，和你这两个亮点相关的表有分片：

- `t_coupon_template`：按店铺维度分表
- `t_user_coupon`：按用户维度分表
- `t_coupon_settlement`：按用户维度分表

只有 `t_coupon_template_remind` 是单表。

这意味着：

- 高并发领券、状态流转的数据热点主要落在分片表中。
- 提醒配置表更偏配置型数据，写频率低于订单/实例表，不需要像交易表那样做大规模分片。

## 6. 迁移成“景区订票项目”时怎么说

你可以这样理解这些表：

| 牛券原表 | 订票口径可理解成 |
| --- | --- |
| `t_coupon_template_*` | 门票模板/场次模板 |
| `t_user_coupon_*` | 用户持有的票实例/权益实例 |
| `t_coupon_settlement_*` | 订单锁定/支付/退款状态表 |
| `t_coupon_template_remind` | 开售提醒表/预约提醒配置表 |

如果面试官问“为什么订单状态流转需要两张表”，你可以回答：

1. `实例表` 负责表示用户当前持有的权益是否可用。
2. `结算表` 负责表示这次订单对该权益做了什么操作。
3. 两张表一起，才能完整表达“锁定中、已支付、已退款”这类订单过程状态。

## 7. 如果改成 RabbitMQ，需要修改的部分

这篇文档涉及的是业务表结构，所以如果消息中间件从 RocketMQ 改成 RabbitMQ，核心业务表基本不用改。

不变的部分：

- `t_coupon_template_*`、`t_user_coupon_*`、`t_coupon_settlement_*`、`t_coupon_template_remind` 这 4 类表仍然成立。
- 订单锁定、支付、退款、预约提醒这些业务状态，仍然建议落在这几张表里。

可能需要调整的部分：

- 如果你继续采用当前源码里的“Redis 幂等 Key”方案，不需要新增 MQ 去重表。
- 如果你想把“注解 + 去重表”真正落地到 RabbitMQ，可以新增一张 `mq_consume_record` 或 `message_consume_record` 表专门保存消费记录。
- 如果你用 RabbitMQ 做超时关单或预约提醒，延时能力通常通过 `TTL + 死信交换机（DLX）` 或 `x-delayed-message` 插件实现，这部分主要改 MQ 拓扑，不改业务表。
- 如果你希望对延时任务做更强审计，也可以额外增加一张 `task_retry_record` 或 `delay_task_record`，但这不是当前业务主表必须项。
