# 基于注解实现 MQ 消息幂等消费

## 1. 先说结论

如果严格按当前仓库源码来讲，这个项目的 MQ 幂等消费实现是：

- `注解 + AOP`
- `Redis 幂等 Key`
- `Lua 保证 Redis 原子写入`
- `消费中/已消费` 两阶段状态

而不是严格意义上的“注解 + 去重表”。

课程文档第 22 小节提到的是“消息去重表 + Redis”的思路，但当前仓库里没有独立的消息去重表建表 SQL、实体类、Mapper 和 Service 落地代码。

所以你可以分两种口径：

1. 按源码实说：`基于注解 + Redis 幂等 Key 实现 MQ 消息幂等消费`
2. 按课程方案扩展：`基于注解 + 去重表/Redis 实现 MQ 消息幂等消费`

如果你想尽量避免面试时被追问穿，建议简历改成第一种。

## 3. 注解是怎么定义的

注解 `NoMQDuplicateConsume` 提供了 3 个核心属性：

```java
String keyPrefix() default "";
String key();
long keyTimeout() default 3600L;
```

含义分别是：

- `keyPrefix`：幂等 Key 前缀
- `key`：通过 SpEL 表达式从消息体里提取唯一业务标识
- `keyTimeout`：幂等 Key 的过期时间

例如在 `UserCouponRedeemConsumer` 中：

```java
@NoMQDuplicateConsume(
    keyPrefix = "user-coupon-redeem:",
    key = "#messageWrapper.keys",
    keyTimeout = 600
)
```

意思是：

- 这个消费者的每条消息，都会按 `messageWrapper.keys` 生成幂等 Key。
- 10 分钟内，如果同一条消息重复投递，就不会重复执行核心业务。

## 4. AOP 是怎么做幂等控制的

核心逻辑在 `NoMQDuplicateConsumeAspect`。

### 第一步：拼幂等 Key

切面会先把注解中的 SpEL 表达式解析成一个唯一业务 Key：

```java
String uniqueKey = noMQDuplicateConsume.keyPrefix()
    + SpELUtil.parseKey(...);
```

例如最终可能生成这样的 Key：

```text
user-coupon-redeem:123456789
```

### 第二步：用 Lua 原子占坑

切面里执行了下面这段 Lua：

```lua
local key = KEYS[1]
local value = ARGV[1]
local expire_time_ms = ARGV[2]
return redis.call('SET', key, value, 'NX', 'GET', 'PX', expire_time_ms)
```

Java 调用时传入的是：

- value = `0`，表示 `CONSUMING`
- TTL = 注解里配置的 `keyTimeout`

这个 Lua 的作用是：

1. 如果 Key 不存在，则原子地写入 `0`，表示“这条消息正在消费中”。
2. 如果 Key 已存在，则返回旧值。

这里用了 Redis `SET NX GET PX`，把“判断是否存在”和“设置消费状态”合成一次原子操作，避免并发下两个消费者同时通过判断。

### 第三步：根据旧值判断如何处理

系统定义了两个状态：

- `0`：消费中 `CONSUMING`
- `1`：已消费 `CONSUMED`

切面处理逻辑如下：

#### 场景 A：返回 `null`

说明 Key 原来不存在，这次是第一次消费。

此时允许业务方法继续执行。

#### 场景 B：返回 `0`

说明已经有另一个消费者在处理这条消息。

切面会抛异常，让 MQ 走稍后重试，而不是并发执行两次。

这样做的原因是：

- 不能直接跳过，因为当前那次消费可能还没成功提交事务。
- 如果直接当成“已处理”跳过，可能会丢业务结果。

#### 场景 C：返回 `1`

说明这条消息已经成功消费过。

切面直接返回，不再进入业务方法，从而保证不会重复下单、重复扣库存、重复修改状态。

## 5. 业务成功和失败时怎么处理

### 消费成功

业务方法正常执行完成后，切面会把 Redis Key 更新为 `1`：

```java
stringRedisTemplate.opsForValue().set(
    uniqueKey,
    IdempotentMQConsumeStatusEnum.CONSUMED.getCode(),
    noMQDuplicateConsume.keyTimeout(),
    TimeUnit.SECONDS
);
```

这样同一条消息再次到来，就会被直接判定为“已消费”。

### 消费失败

如果业务方法抛异常，切面会删除这个 Redis Key：

```java
stringRedisTemplate.delete(uniqueKey);
throw ex;
```

这样做的目的很关键：

- 删除 Key 之后，MQ 重试时还能重新进入业务逻辑。
- 如果失败后还保留 `CONSUMING` 状态，就会把消息永远卡死。

## 6. 业务消费者里是如何配合幂等的

以 `UserCouponRedeemConsumer` 为例：

1. 消费器上加了 `@NoMQDuplicateConsume`
2. 业务方法本身又加了 `@Transactional`
3. 先扣减数据库库存
4. 再插入 `t_user_coupon`
5. 再维护用户券缓存
6. 最后发送延时关闭消息

这意味着：

- 幂等切面负责“同一条消息最多只成功落地一次”
- 事务负责“本次消费涉及的多步数据库操作要么都成功，要么都回滚”

两者职责不同，缺一不可。

## 7. 为什么它能避免重复下单、重复扣库存和状态错乱

你可以把这套机制总结成一句话：

> 先用 Redis 幂等 Key 把同一条 MQ 消息串行化，再用事务保证单次消费的多步业务原子提交。

对应到结果上：

### 避免重复下单

同一个订单创建消息重复投递时，只会有第一次真正执行业务。

### 避免重复扣库存

如果消费者负责落库扣库存，幂等控制会让这条消息只扣一次。

### 避免订单状态错乱

例如“已锁定 -> 已支付”这类状态推进消息，如果重复消费，就可能把同一笔业务推进多次。幂等控制可以拦住这类重复推进。

## 8. 当前源码和“去重表方案”的区别

### 当前源码

优点：

- 实现简单，接入成本低
- 不需要额外建表
- 性能好，路径主要在 Redis

缺点：

- 依赖 Redis 持久化和 TTL 管理
- 只能保留一段时间内的幂等记录
- 审计能力不如数据库表

### 去重表方案

更完整的做法通常是新增一张表，例如：

```sql
CREATE TABLE mq_consume_record (
    id bigint PRIMARY KEY AUTO_INCREMENT,
    message_key varchar(128) NOT NULL,
    consumer_group varchar(64) NOT NULL,
    topic varchar(128) NOT NULL,
    status tinyint NOT NULL,
    consume_time datetime DEFAULT NULL,
    create_time datetime DEFAULT CURRENT_TIMESTAMP,
    update_time datetime DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_message (message_key, consumer_group)
);
```

典型流程：

1. 消费前先插入一条 `消费中` 记录
2. 若插入失败，说明这条消息已经处理过或正在处理
3. 业务执行成功后把状态改成 `已消费`
4. 业务失败则删除记录或改回失败态等待重试

这种方案更适合：

- 金融类
- 审计要求高
- 需要长期保留消息消费轨迹

## 9. 幂等性的其它实现方案

除了当前项目这种做法，常见方案还有下面几种。

### 方案 1：业务唯一索引

例如订单表上加唯一索引：

```sql
UNIQUE KEY uk_order_no (order_no)
```

优点：

- 实现最直接
- 数据库天然兜底

缺点：

- 只能兜底“重复插入”
- 对“重复更新状态”帮助有限

### 方案 2：状态机 + 条件更新

例如只允许：

```sql
update order set status = 'PAID'
where order_id = ? and status = 'LOCKED'
```

优点：

- 很适合状态流转
- 能防止状态被重复推进

缺点：

- 只能保证状态更新本身
- 无法替代消息级幂等

### 方案 3：Redis `SETNX`

和当前项目类似，只是不用注解/AOP封装。

优点：

- 快
- 实现简单

缺点：

- 业务里到处写样板代码，可维护性差

### 方案 4：去重表 / Inbox 表

每个消费者都维护自己的消费记录表。

优点：

- 可审计
- 易排障

缺点：

- 写库成本更高
- 需要处理大量历史记录

### 方案 5：Outbox + Inbox

生产方落 Outbox，消费方落 Inbox。

优点：

- 更适合跨服务最终一致性

缺点：

- 设计复杂度明显更高

## 10. 如果迁移到 RabbitMQ 应该怎么说

当前仓库用的是 RocketMQ，但这套思路对 RabbitMQ 同样成立，因为核心不在中间件品牌，而在于：

1. MQ 默认不能保证“业务只执行一次”
2. 重复投递、重复消费是常态，不是异常
3. 必须在消费端做应用级幂等

所以你面试时可以这样说：

> 在消费端通过注解 + AOP 统一封装幂等逻辑，基于 Redis 原子占坑控制同一消息的并发消费，并用消费中/已消费两阶段状态避免重复下单、重复扣库存及订单状态错乱。

如果面试官继续追问“为什么不是去重表”，你就补一句：

> 课程方案里可以扩展为去重表 + Redis 双层幂等，但当前项目源码落地的是 Redis 幂等 Key 方案。
