创建优惠券模板责任链

1. 为什么要用责任链模式？

在没有引入责任链之前，创建优惠券模板的参数校验通常会写成下面几种形式：

  • 在 createCouponTemplate 方法里堆一长串 if / else 判断；

  • 或者抽一个 validateXXX(requestParam) 大方法，里面塞满各种校验逻辑。

这种写法有几个明显问题：

  1. 1.

    职责不清晰、方法越来越臃肿：所有校验揉在一起，一个方法里既判断必填项、又判断格式、还要查库校验业务约束，导致方法越来越长，很难快速看懂「这一段是在干嘛」。

  2. 2.

    扩展性差，改动成本高：新增一个校验规则要么去改那段 if / else，要么继续往 validateXXX 里塞逻辑，很难做到「增加功能不修改原有代码」，违反开闭原则。

  3. 3.

    复用困难：某些校验逻辑（比如时间范围合法性、店铺是否存在等）本来可以复用到其他业务（比如修改模板、复制模板），但因为写死在方法里，想抽出来又很痛苦。

  4. 4.

    测试不友好：大方法里什么逻辑都有，单元测试要覆盖每个分支非常麻烦，也不方便针对某个校验规则单独写测试。

引入责任链后，把复杂的校验拆成多个「处理器」，每个处理器只关注一件事（比如非空校验、基础格式校验、业务校验等），既符合单一职责原则，又方便新增/下线某个规则，整体结构会清晰很多。

2. 执行创建优惠券会走哪些责任链处理器？

例如：

  1. 1.

    必填项非空校验处理器

    • 校验优惠券名称、优惠类型、有效时间、库存等是否为空；

    • 类：CouponTemplateCreateParamNotNullChainFilter。

  2. 2.

    基础格式与范围校验处理器

    • 校验时间区间 valid_start_time < valid_end_time；

    • 校验库存必须是正数；

    • 校验 JSON 字段结构是否符合预期、数值是否在合理范围内；

    • 类：CouponTemplateCreateParamBaseVerifyChainFilter。

  3. 3.

    业务一致性校验处理器

    • 校验店铺编号是否存在、是否属于当前登录用户；

    • 校验商品编码是否存在、商品是否属于该店铺；

    • 校验平台券/店铺券与来源、成本承担逻辑是否匹配；

    • 类：CouponTemplateCreateParamBizVerifyChainFilter。

  4. 4.

    扩展规则校验处理器（可选）

    • 比如校验「同一时间同一店铺类似优惠活动是否超出上限」；

    • 校验运营侧通用规则（如某些品类禁止打折等）。

每个处理器都实现统一接口 MerchantAdminAbstractChainHandler<T>，对外暴露一个 handler(T requestParam) 方法，责任明确、粒度清晰，后续想加某个新校验，只需要新增一个实现类接入责任链即可。

3. 责任链模式如何实现？

启动时扫描所有实现了 MerchantAdminAbstractChainHandler 的 Bean，按 mark() 分组，并根据 Ordered 接口的顺序进行排序，简要流程：

  1. 1.

    启动时扫描 Bean：

    textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                    
    Map<String, MerchantAdminAbstractChainHandler> chainFilterMap =
        applicationContext.getBeansOfType(MerchantAdminAbstractChainHandler.class);

    把 Spring 容器中所有责任链处理器 Bean 拿出来。

  2. 2.

    按 mark 分组

    • 遍历这些 Bean，调用每个 Bean 的 mark() 方法；

    • 以 mark 为 key，把属于同一场景（例如「创建优惠券模板」）的处理器放入同一个 List<MerchantAdminAbstractChainHandler> 里。

  3. 3.

    按优先级排序

    • 各处理器都实现了 Ordered 接口；

    • 通过 unsortedChainHandlers.sort(Comparator.comparing(Ordered::getOrder));

    • 实现「order 值越小，处理越靠前」，比如：

      • 0：非空校验

      • 10：基础格式校验

      • 20：业务校验

  4. 4.

    执行业务链 当业务中调用：

    textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                    
    merchantAdminChainContext.handler(mark, requestParam);

    时，就会拿到这个 mark 对应的处理器列表，然后顺序执行：

    textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                    
    abstractChainHandlers.forEach(each -> each.handler(requestParam));

这样一来，责任链的组装、排序、执行都被封装到了 MerchantAdminChainContext 里，开发者只需要关心「我传哪个 mark、requestParam 是什么」就够了。

4. 责任链执行遇到异常如何中断？

在当前 MerchantAdminChainContext 实现里，是通过顺序 forEach 调用每个处理器的：

abstractChainHandlers.forEach(each -> each.handler(requestParam));

要实现「失败即中断」的效果，最常见也是最简单的做法是：在处理器内部抛出异常，例如统一的业务异常 BizException / ClientException 等：

public void handler(CouponTemplateSaveReqDTO requestParam) {
    if (requestParam.getStock() == null || requestParam.getStock() <= 0) {
        throw new ClientException("库存必须为正整数");
    }
}

一旦抛出异常：

  • 当前处理器的后续逻辑不会执行；

  • forEach 会立即终止；

  • 上层 createCouponTemplate 可以捕获异常并返回统一的错误响应。

  • 最终会通过 Web 全局异常拦截器捕获并返回前端。

扩展思路：

如果以后想支持「不中断，只记录告警」的场景，也可以在责任链模型上做扩展，例如：

  • 在 handler 方法里返回一个状态对象；

  • 状态对象中包含 pass / fail / warn 等标记；

  • 上层根据状态决定是否继续执行、是否告警等。

但在牛券实现「参数校验」场景下，校验失败直接抛异常中断，是最简单也最常见的实践。

5. 如何复用责任链模式？

当前框架的设计是「业务无关」+「通过 mark 区分业务」，因此可以很方便复用到其他场景，例如：

  • 修改优惠券模板；

  • 创建优惠券发放批次；

  • 审批操作校验；

  • 商家后台其他表单类操作的参数校验。

复用方法：

  1. 1.

    定义新的业务标识：在 ChainBizMarkEnum 中新增一个标识，例如：

    MERCHANT_ADMIN_UPDATE_COUPON_TEMPLATE_KEY,
MERCHANT_ADMIN_CREATE_COUPON_BATCH_KEY
  2. 2.

    为新场景编写处理器

    • 处理器依然实现 MerchantAdminAbstractChainHandler<对应DTO>；

    • 在 mark() 中返回新的标识；

    • 在 getOrder() 中指定执行顺序。

  3. 3.

    业务中直接调用

    updateReqDTO

这样，责任链基础代码 (MerchantAdminAbstractChainHandler、MerchantAdminChainContext) 都是通用的，真正和业务耦合的只有：

  • 具体处理器里的校验逻辑；

  • 每条链对应的 mark 枚举。

创建优惠券模板分库分表

1. 为什么优惠券模板这张表需要考虑分库分表？单表顶不住吗？

从业务侧看，优惠券的主体是商家。按“3000 万商家，每个商家平均创建 100 张优惠券模板”来估算，单表数据量大概会到 30 亿行。而且这个数字还是“当下的保守估计”，随着商家增长和运营玩法迭代，未来只会越来越大。

单表撑不住主要体现在几方面：

  • 存储压力：几十亿行堆在一张表里，备份、迁移、DDL 调整都非常痛苦。

  • 查询性能：即便走索引，页分裂、索引层级增加后，磁盘 IO 次数会明显上升，延迟抖动会变大。

  • 写入性能：高并发写入场景下，行锁/页锁竞争会越来越明显。

所以与其等到单表撑爆再救火，不如在设计之初就按「海量数据 + 未来增长」的维度规划好分库分表方案，把优惠券模板做成天然可扩展的存储结构。

2. 为什么单表上限控制在大约 2000 万？

单表到底能撑多少数据，没有绝对标准，取决于：

  • SQL 是否复杂，是否大量走全表/联合查询；

  • 是否能稳定命中索引；

  • 底层存储和硬件条件（磁盘、IOPS 等）。

在优惠券模板这个场景里：

  • 查询模式相对简单，大部分都是带分片键、走单表索引的分页查询；

  • 不需要跨表 join，也没有太重的分析类 SQL。

在这种前提下，把单表控制在 2000 万左右 是一个比较安全、留有余量的经验值：

  • 数据量不到特别夸张时，通常 3 次左右磁盘 IO 就能命中到目标记录，性能比较稳定；

  • 后续考虑备份、迁移、分区、DDL 等操作，也不会因为单表太大而“动一次就抖一次”。

所以用 30 亿 ÷ 2000 万 ≈ 150 张表 作为规划基准，再配合分库，把压力摊薄，是一个比较务实的折中方案。

3. 优惠券模板为什么“只分表就行”还要讨论分库？

对于优惠券模板这个实体，可以从两个维度看是否需要分库：

  1. 1.

    写入并发是否逼近 MySQL 实例上限？

    • 单台 MySQL 的写入瓶颈大约在 4000–5000 TPS 左右；

    • 如果创建优惠券模板的 QPS 不高（商家配置优惠券的操作本身就不算高频），其实可以只分表、不分库。

  2. 2.

    是否有后续复用的需求？

    • 后面真正高并发的是「优惠券发放 & 领取」业务，那一块大概率要分库；

    • 为了避免后面再重复做一次拆表、迁库动作，示例中就直接用「分库 + 分表」的形态演示一套完整方案。

按现状只分表就够用，但从整体架构演进和教学示例的角度，直接展示分库分表的完整形态更有价值。

4. 为什么选择店铺编号作为分片键？

分片键的选型主要考虑三点：数据均匀、业务友好、不可变。放到优惠券模板业务里，就是：

  1. 1.

    业务查询路径决定了分片键

    • 商家后台的典型需求是“查询当前店铺创建的优惠券模板列表”，也就是：

      textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                      
      WHERE shop_number = ? ORDER BY create_time LIMIT ?, ?

    • 用 shop_number 做分片键，可以保证一间店铺的数据都落在同一个分片库/表里，分页查询只打一个分片，不需要跨库跨表扫。

  2. 2.

    数据分布相对均匀

    • 店铺数量巨大，店铺 ID 本身就是一个天然分散的维度；

    • 对 shop_number 做 Hash 取模，能比较自然地把不同店铺均匀打散到各个分片。

  3. 3.

    字段稳定，不会变更

    • 店铺编号一旦生成，就不应该被修改；

    • 用这种“业务主键级别”的字段做分片键，可以避免后续「改值 + 搬迁数据」的尴尬。

而如果选主键 ID 或创建时间：

  • 用 ID：你分页时一般是按 shop_number + create_time 排序，很容易出现跨分片范围查询的问题；

  • 用时间：优惠券创建行为早期店铺少，后期店铺多，会出现「时间切片明显不均匀」的问题，而且按店铺维度查询会变得非常难看。

所以对这个场景来说，shop_number 是一个同时满足“读路径友好 + 分布均匀 + 稳定不变”的理想分片键。

5. 为什么选 ShardingSphere，而不是 MyCat 或直接用 TiDB 这类分布式数据库？

回答如下：

  1. 1.

    ShardingSphere vs MyCat（都是“分库分表框架”）

    • 生态和社区

      • MyCat：社区相对小，版本更新和新特性节奏偏慢；

      • ShardingSphere：Apache 顶级项目，文档齐全，社区活跃度高，踩坑能搜到答案。

    • 功能和策略丰富度

      • MyCat：实现了基础的水平分表、垂直拆库，策略相对有限；

      • ShardingSphere：支持标准分片、范围分片、复合分片、自定义算法、读写分离、分布式事务等，扩展能力强。

    • 代码侵入

      • ShardingSphere-JDBC 模式可以直接嵌入到 SpringBoot 项目里，基本不改业务 SQL，改的主要是 DataSource 配置和分片规则文件，开发体验更好。

  2. 2.

    ShardingSphere vs 分布式数据库（PolarDB/TDSQL/TiDB）

    • 兼容性和迁移成本

      • 分布式数据库常常标榜兼容 MySQL，但在某些 SQL 语法、系统变量、运维方式上依然有差异，“几乎兼容”不等于“平滑迁移”。

    • 技术储备要求更高

      • 真出了集群层面的故障，需要团队里有人对这类分布式引擎有比较深的理解，否则线上事故处理风险很大。

    • 成本 & 成熟度

      • 公有云版 PolarDB、TDSQL 都是付费产品，总体成本明显高于自建 MySQL 集群；

      • TiDB 虽然有开源版，但社区 Issue 较多，踩坑成本不低，商业版又是另一套成本模型。

在“现有业务是 MySQL + SpringBoot，团队以 Java + 中间件为主”的前提下，用 ShardingSphere 做分库分表是一条更加务实、可控的路径。

6. 如果查询语句没带分片键，比如只按优惠券名称 name 搜，会发生什么问题？

这是典型的「读扩散（查询放大）」问题。

当 SQL 是：

  • 只好把这条 SQL 广播到所有库、所有分片表，再用 UNION ALL 合并结果，类似：

  • 某个商家的只查一页数据，结果后台要扫 16 张物理表，QPS 一上去，瞬间把数据库 I/O 打穿；

  • 极端情况下，稍有慢表就会拖垮整个查询，导致调用超时。

所以在这种按店铺维度设计分片键的场景，请求里一定要尽量带上分片键，例如：

只有写的时候带分片键、查的时候也带分片键，才能真正发挥分库分表的性能优势。

创建优惠券模板操作日志

1. 为什么要专门给优惠券模板做操作日志？

简单的业务，打两行 info 日志确实也能看个大概。但优惠券这种东西，有几个特点：

  • 商家自己会不断改规则：改库存、改门槛、改有效期，甚至关掉某个券；

  • 一旦出问题，影响的是钱：多给钱、少给钱、没给到钱，都会有人来追责；

  • 操作链路又长：运营、商家、平台后台都有可能改到同一张券。

这时候，你只靠程序日志（按时间滚动那种），排查成本会非常高，很难一句话看到“谁在什么时间对哪张券做了什么改动”。

专门搞一张 t_coupon_template_log：

  • 直接挂在店铺 + 优惠券模板 ID 上；

  • 把“原始数据 / 修改后数据 / 文案日志”都记下来；

后面商家问“为什么这张券昨天还能领，今天就不能用了”，你就有一条完整的审计线，既方便自己排查，也方便甩证据。

2. 为什么需要使用 biz-log 框架打印？

直接在 createCouponTemplate 里面手写插日志 String.format 也行。一开始确实没啥问题，代码大概长这样：

textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy

但你会慢慢发现几个坑：

  1. 1.

    业务方法越来越“花”：创建优惠券本身要做一堆校验、落库、缓存等逻辑，再加上操作日志那坨拼字符串，方法一下子变得很长，读起来很费劲。

  2. 2.

    所有地方都要手抄一份：不止创建要记日志，修改、上下线、停用、批量操作……都要记。每个方法都 copy 一段拼接逻辑，后面想改文案，得到处搜。

  3. 3.

    字段一变，全线跟着改：你在请求 DTO 里加了一个字段，比如“券标签”，原来的日志里没这个信息。你就得回头把所有日志拼接的地方都重新撸一遍。

所以才有了咱们的方案：用 Spring AOP 把“记录日志”这件事从业务方法里剥出去，对业务来说就一句注解，日志内容交给框架和 SpEL 表达式去处理。

3. 为什么不是自己写而是用开源框架？

自己写肯定能写，但你会踩不少“重复的坑”，比如：

  • 注解怎么设计？只支持简单字符串，还是支持变量、函数、条件？

  • 日志模版里需要取方法参数、返回值、当前用户信息，表达式怎么写才不丑？

  • 要不要支持“自定义函数”，比如把枚举值转成中文、做个格式化之类的？

  • 日志持久化怎么扩展？后面想发 MQ、落 ES，还得再加一层抽象。

mzt-biz-log 把这些活基本都帮你干了：

  • 注解语法设计好了一套，支持变量、SpEL 表达式、自定义函数；

  • 跟 SpringBoot 贴合得比较紧，直接加依赖、加 @EnableLogRecord 就能用；

  • 预留了 ILogRecordService 扩展点（还有很多自定义函数解析、缓存性能），你只管实现具体的“怎么保存”。

所以这个地方用现成的轮子，主要图省时间以及开源质量比自己写好很多。真要自己写，通常是在这套能力还“兜不住需求”的时候，再考虑造轮子。

4. 操作日志记录失败，是否要把整个业务操作失误回滚？

这个就看对日志这件事的态度了，课程里的选择是比较务实的一种：

  • 记录日志失败，不回滚业务

    • 优惠券创建是主业务，日志只是旁路记录；

    • 真让日志异常把主流程打挂了，商家那边直接感知到的是“券创建失败”，体验很差；

    • 正常做法是：捕获异常，打错误日志 + 告警，有问题再人工补。

  • 要不要异步？

    • 并发小、业务不敏感：直接同步落库就行，简单粗暴；

    • 并发大、链路比较长：可以在 record 里发一条 MQ，把 LogRecord 交给消费端慢慢落库，这样不拖慢主链路。

创建优惠券模板防重复提交

1. 为什么做“防重复提交”？

前端禁用按钮、加 loading 是第一道防线，但真要保险一点，后端还是得兜底。几个现实情况：

  • 用户网络抖一下，浏览器“卡在加载中”，人一急就疯狂点按钮；

  • 页面被刷新、回退再提交，请求其实已经发出去了，用户自己也分不清；

  • 系统本身有延迟，用户以为没点上，再点一次。

如果操作只是“多查了一次列表”，问题不大；但创建的是优惠券、订单、退款单这种带业务意义的东西，一旦重复，就是真金白银出去了，所以：

前端能拦一部分，真正兜底的逻辑还是要放在后端。

2. JVM 本地锁能不能直接用来防重复提交？

不够用，原因主要有两个：

  1. 1.

    只管当前进程，管不了集群

    • 单机 demo 里，synchronized 和 ReentrantLock 都是好用的；

    • 一上生产，服务一般都是多实例部署，你锁的是“这台机器上的这个方法”， 别的机器完全不知道这回事。

  2. 2.

    粒度太粗，不好区分“不同用户 / 不同参数”

    • 你要是真在方法上来个 synchronized，那等于所有人按顺序排队——吞吐量直接打死；

    • 想支持“同一个用户相同参数不能重复，不同用户互不影响”，本地锁要搞复杂的 Map 来管理，没啥必要。

所以，实际项目中直接把本地锁排除掉，一步到位使用分布式锁。

3. 分布式锁 Key 如何定义？

你可以把分布式锁理解成：“这一次操作的指纹”。

这一节里拼出来的 Key 结构是：

textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                
no-duplicate-submit:path:{请求路径}:currentUserId:{用户ID}:md5:{参数MD5}

拆开来看：

  • path：区分不同接口，比如“创建优惠券”和“修改优惠券”；

  • currentUserId：同一个用户重复点按钮要防掉，不同用户互不影响；

  • md5(参数)：同一个用户、同一套参数才算重复提交，换了参数就当新请求。

这样有几个好处：

  • 粒度比较合理，“谁 + 调的哪个接口 + 提交了什么” 都在里头；

  • 保证“同一个人提交同一份表单”会被拦住；

  • 不会影响其它用户正常提交，也不会误伤参数不同的请求。

4. 用 Redisson 分布式锁是不是就完美了？

锁只是控制并发窗口，并不能解决所有场景的问题。


时序图里演的是这么个情况：

  1. 1.

    请求 1 进来，加锁成功，0.2s 内执行业务并释放锁；

  2. 2.

    请求 2 稍微晚一点到，等它到的时候锁已经释放了，又加锁成功，又执行了一遍。

也就是说：只要两个请求没真正重叠在“锁持有期间”，它们就会被视为两次合法操作。

在不少业务里，这是可以接受的（比如抢接口、配置变更类操作）； 但像“支付回调、防止重复扣款”这类场景，你可能会想要更硬一点的约束，这时候就会考虑：

  • 除了锁，还在 Redis 里建一条标记，例如：

    SET key 1 NX EX 5

    • 第一次能成功 set，后面的在过期时间内都失败；

    • 就算上一个请求瞬间结束，这个标记也能挡住一段时间的重复。

所以最后想表达的是：

分布式锁是一种手段，不是银弹。不同业务对“重复”的定义不一样，要结合具体场景看是用锁、用 Redis Key 标记、还是干脆业务上做“幂等校验”。

优惠券模板操作库存

1. 并发增加发行量，会不会把库存加乱？

接口逻辑是这样的：

textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                
UPDATE t_coupon_template
SET stock = stock + #{number}
WHERE shop_number = #{shopNumber}
  AND id = #{couponTemplateId}

很多人第一反应是：

万一张三、李四同时操作同一个模板，都会在原来 10 的基础上加 10，会不会最后只变成 20，而不是 30？

这个担心其实是把“读出来再 +10 回写”和“在 SQL 里直接 +10”混一起了。

这里我们用的是原地自增：stock = stock + ?，加上 MySQL 的行级排他锁，行为其实是这样的：

  • 第一个线程拿到这行的锁，执行 stock = 10 + 10 -> 20，提交；

  • 第二个线程会在 UPDATE 时 阻塞，等前一个提交后，再以最新的 stock 做加法：20 + 10 -> 30；

  • 所以最终落库的值是 30，而不是 20。

只要你让更新逻辑尽可能在一条 SQL 里完成，再配合 MySQL 默认的行锁机制，并发更新不会像“先查再改”那样容易踩坑。

优惠券模板 RocketMQ 定时到期

1. 定时任务不也能做吗？为啥还要上 RocketMQ？

两个方案都能做成，但侧重点不一样：

  • 定时任务/XXL-Job 更像是扫库型：隔一段时间去查“哪些券已经过期但还没关”，然后批量处理。数据量大了以后，扫库这件事本身就会给 DB 造成压力，还得考虑分片、并发、补偿之类的问题。

  • RocketMQ 定时消息更像是提前约好闹钟：创建模板的时候，就把「这张券在 X 时间点要关闭」这件事交给 MQ，到了时间 MQ 把消息推给你，你只要按消息把状态改掉就行了。

对于“优惠券模板有一个明确的失效时间”这种业务场景，MQ 定时消息刚好对上：

  • 精度够，按毫秒时间戳直接丢；

  • 不用自己维护一堆扫描任务；

  • 跟已有的异步链路也比较契合。

后面你再讲 XXL-Job，可以当做是另一种思路：一个偏“批处理”，一个偏“事件驱动”，都对，只是适用场景不一样。

2. RocketMQ 5.x 的任意延时消息，跟以前的固定延时等级比，体验差别在哪里？

早期版本是“档位制延迟”，比如只支持：

1s、5s、10s、30s、1min、2min、5min、10min…

你的业务如果刚好要在 2025-12-01 20:00:07 执行，就会比较别扭：不是提前很多，就是晚一点，只能折中。

5.x 之后支持“任意时间戳”，你在代码里直接用优惠券的失效时间：

Long deliverTimeStamp = couponTemplateDO.getValidEndTime().getTime();
rocketMQTemplate.syncSendDeliverTimeMills(topic, message, deliverTimeStamp);

简单理解：

  • 以前是「你去迁就 RocketMQ 的固定档位」；

  • 现在是「RocketMQ 配合你的业务时间点」，哪个毫秒触发都可以。

对于优惠券到期关闭、订单超时关闭这类精确到具体时间点的需求，5.x 的任意延时体验会好很多。

3. 延时关闭优惠券，消费者需要幂等处理吗？

这里的操作是把状态改成“已结束”，多次执行结果是一样的。即使同一条消息被重复投递几次，最终状态都还是 ENDED，不会出现“扣多次库存”这种问题，所以不做复杂幂等也没关系。

EasyExcel 解析百万 Excel 批量分发

1. 为什么优惠券分发是通过 Excel 进行的？

这背后其实有一些背景需要先了解，首先是 Excel 中的用户数据是怎么来的。

我们日常在淘宝、京东等大型电商平台上浏览或购买商品时，都会被埋点采集数据。这些埋点可以精确到你点击了哪个商品、浏览了多长时间、访问了几次店铺等。这些行为数据会被汇总到用户画像系统中（不同公司可能叫法不同），用于识别潜在意向客户。基于这些画像，平台运营人员可以有针对性地进行优惠券投放或发送营销短信。

针对如何将优惠券分发给这些潜在客户，通常有两种模式：

  1. 1.

    Excel 导出模式：运营人员根据需求向画像平台提报，画像平台返回一个符合条件的用户列表（Excel 文件）。然后，平台通过内部运营系统，选择优惠券并将其分发给 Excel 中的用户。

  2. 2.

    标签查询模式：运营人员向画像平台提需求，画像平台将用户打上统一标识。平台根据这个标识，在分发时结合优惠券执行用户发放。

在实际企业中，这两种方案都存在，且各有适用场景。

我们当前的方案采用的是第一种 Excel 导入模式，原因也很简单：我们并没有真正接入用户画像平台，因此通过模拟生成 Excel 数据的方式，更容易实现并演示整个分发流程。

如果在面试中有面试官对此提出质疑，也可以补充说明第二种标签模式的实现逻辑，大部分人其实都能理解和认可。

例如，如果我们要上线一家高端服装店，为了提升其生意，我们可以从意向客户中提取长期浏览高端服装或已经购买过类似品牌或价位的用户信息，然后将优惠券和通知发送到这些用户的账户。这样可以精准地锁定潜在客户，提高营销效果。

3. 分发接口中统计 Excel 行数有什么意义？

两个点都挺实用：

  1. 1.

    任务规模预览

    • 管理后台展示“本次任务计划发放 X 人”，运营同学心里就有个数；

    • 配合状态和时间，也能大概判断这个任务会跑多久、是否需要拆批。

  2. 2.

    数据完整性校验（可扩展）

    • 理论上，Excel 行数 = 成功发放数 + 失败数；

    • 如果你后续在任务执行完之后补一段校验逻辑，就能自动发现“漏处理”的情况：

      • 比如中途挂了一个节点；

      • 或某个分片没跑完；

    • 先把“行数”写进库里，后续要做这种校验就有基础数据了。

简单说： 行数本身不是目标，但“有这个全量基数”之后，很多后续能力才有落脚点。

线程池和延时队列优化接口响应

1. 为什么要把 Excel 行数统计异步化？

百万行 Excel，用 EasyExcel 数一遍行，差不多要 4～5 秒。

在后管系统里，这就会有几个问题：

  1. 1.

    接口响应太慢

    • 创建优惠券任务的接口，本质只是“登记一个任务 + 做些基础校验”；

    • 用户点一下按钮，要傻等 5 秒才看到“创建成功”，体验会很割裂。

  2. 2.

    链路上耦合太重

    • 行数统计只是个“增强信息”，是为了后续做进度、校验用；

    • 不值得把整个创建任务流程都绑在这个耗时步骤上。

所以做法就变成：

  • 接口里只做：参数校验 + 任务入库，马上返回成功；

  • 行数统计这类耗时活，丢给线程池后台慢慢跑；

  • 真正的瓶颈从“用户等待时间”挪到了“后台异步任务”，对体验影响就小很多了。

一句话：行数一定要算，但没必要绑死在接口响应时间上。

2. 如何设置线程池参数？为啥不用 Executors.newFixedThreadPool 这种快捷方式？

这块主要是两层考虑：

  1. 1.

    场景本身决定了配置范围

    • 属于后台管理任务，调用频率不会像前台接口那样高；

    • Excel 解析是 IO + 一点点计算的混合型任务，所以：

      • corePoolSize = CPU 核数：正常情况下就够用了；

      • maximumPoolSize = 核数 * 2：偶尔高峰来了，可以多开一点线程兜一兜；

      • workQueue = SynchronousQueue：不排队，来了就立刻交给线程执行，要么新建线程，要么走拒绝策略。

  2. 2.

    为什么不用 Executors 快捷方法

    • newFixedThreadPool / newSingleThreadExecutor：底层是无界队列，任务堆多了直接把内存撑爆；

    • newCachedThreadPool：线程数量理论上无限创建，高并发下可能把系统拖跨；

    • 简单就是：方便是方便，但默认参数太“乐观”，一旦遇到大任务就容易翻车。

线程数有限，队列不堆积，超出直接丢弃（但有 Redis 延时队列兜底）。

3. 为什么这里还要用 Redis 延时队列？能不能用 RocketMQ？

这块主要是“环境现实”问题，而不是技术优劣：

  • 理论上，用消息队列做异步 + 延时，是更标准的做法：

    • 持久化能力更强；

    • 消费模型更丰富；

    • 重试、堆积、监控都更专业。

  • 但在实际项目里常见情况是：

    • 有的项目本身就没接入 MQ，引入一套 RocketMQ/Kafka 成本不低；

    • 或者 MQ 主要留给“强一致、强可靠”的业务，这种“统计 Excel 行数”的辅助任务就不一定值得占坑。

所以这里的定位是：

线程池 = 主力，Redis 延时队列 = 兜底辅助。

  • Redis 本身定位还是缓存，持久化和主从同步都有丢数据的可能；

  • 但“统计行数”这件事，属于可补偿、可人工处理的类型，用 Redis 做兜底完全够用；

  • 真正强一致的发券流水，还会在后面的核心链路里通过 MQ 或事务做保障。

在复盘/面试时可以这么讲：有 MQ 就尽量用 MQ 做主通路，没有的话，线程池 + Redis 延时队列是一套性价比很高的过渡方案。

4. Redis 延时队列这套兜底方案，还有哪些边界和注意点？

这块虽然只是兜底，但有几个点可以心里有数：

  1. 1.

    Redis 本身不保证 100% 不丢

    • AOF/persistence 都是异步写盘，极端情况下可能丢一条；

    • 主从切换也可能丢部分尚未同步的写；

    • 所以文中强调：Redis 只是兜底，真的失败了可以人工补。

  2. 2.

    消费者线程是单线程死循环

    • 用 Executors.newSingleThreadExecutor 起了个守护线程，一直 take()；

    • 命名成 delay_coupon-task_send-num_consumer，方便线上排查；

    • 逻辑很简单：取一条 -> 查 DB -> 决定要不要执行 refreshCouponTaskSendNum。

如果未来这块要升级成更通用的“延时任务中心”，Redis 这套思路也能直接迁移到 RocketMQ 的延时消息或专门的延时队列组件上。

模板方法重构消息队列发送接口

1. 为什么还要引入模板方法模式重构？

直接在业务里写 MQ 发送，一开始确实挺爽，但时间一长问题会越来越明显：

  • 每个业务类都在手写一遍类似的逻辑：解析 Topic、拼 destination、构建 Message、设置 Keys、调用 syncSend、打日志、try-catch……

  • 想统一一点点东西，比如：

    • 日志格式统一（事件名、Keys、MsgId 要一样）；

    • 超时时间、是否用延时消息的策略；

    • 发送失败时的兜底处理方式。

就会发现改一次得满项目搜一遍，特别容易漏。

这次用模板方法模式做抽象，实际上就两个核心收益：

  1. 1.

    共性逻辑上收：Topic 拼接、是否延时消息的判断、统一日志输出、异常包装等，都放到了 AbstractCommonSendProduceTemplate 的 sendMessage() 里，业务不用重复写。

  2. 2.

    个性逻辑下沉：每个业务只管实现两个抽象方法：

2. 模板方法模式和策略模式、工厂模式这些比起来，这里为什么更适合用模板方法？

从这次场景来看，有几个特点：

  1. 1.

    整体流程是稳定的：不管是优惠券分发、模板延时关闭，还是以后别的消息，发送流程其实都一样：

    1. 1.

      准备扩展参数；

    2. 2.

      构建 destination；

    3. 3.

      根据是否延时选择不同的 RocketMQ API；

    4. 4.

      打统一日志。这就是典型的“算法骨架固定、少数步骤可变”。

  2. 2.

    变化点很集中，且数量不多：可变的只有两块：

    • 这条消息的“配置”：事件名、Topic/Tag、Keys、超时时间、延时参数；

    • 这条消息的“内容”：payload 怎么组织、header 里要塞什么。

这种情况下，模板方法模式非常对口：父类给出流程，子类负责把几个关键步骤实现掉。

如果强行上策略模式，通常会变成：

  • 一个 SendMessageStrategy 接口；

  • N 个策略类里既包含“构建 Message”的逻辑，又自己调用 rocketMQTemplate；

  • 最后还是会出现大量重复的 try-catch + 日志打印。

而工厂模式更适合“我要创建哪种 Producer/Client”，不是很适合描述“同一个发送动作的内部步骤”。所以综合下来，模板方法是这里最自然的选择。

优惠券模板缓存击穿/穿透场景

1. 为什么一定要给模板查询加缓存？用数据库硬扛不行吗？

从业务上看，优惠券模板这种东西有几个特点：

  • 被访问得非常频繁，尤其是大促、活动页、领券中心这种场景；

  • 单次查询的逻辑并不复杂，更多是读多写少；

  • 对响应时间很敏感，用户点开券中心或者下单页，几百毫秒和几十毫秒的体验完全不一样。

如果这种查询完全落在数据库上，高峰时有几个问题：

  • 所有请求都打到数据库上，容易把核心库的连接数、IO 撑爆；

  • 即便扛得住，数据库层面也很难做到毫秒级响应；

  • 一旦数据库抖一下（慢查询 / 抢锁 / 备份），前台页面体验会非常差。

而优惠券模板本身又是很适合缓存的：

  • 数据体积不算大；

  • 一个模板会被大量用户重复访问；

  • 有明确的有效期，可以用过期时间驱动缓存失效。

所以在牛券这种项目里，模板查询是天然的“热点读接口”，正确姿势就是：落缓存 + 做好缓存击穿 / 穿透防护，数据库只承担兜底与刷新职责。

2. 缓存击穿在优惠券查询这里具体是怎么发生的？

以优惠券模板为例，典型的缓存击穿场景是这样的：

  • 某个热门优惠券模板，活动期间有大量用户在访问，对应的 Key 是热点 Key；

  • 这个 Key 在 Redis 里刚好过期了，或者还没来得及预热进缓存；

  • 此时有一波并发请求同时查询这个模板，发现缓存都 miss，于是一起打到数据库上；

  • 数据库瞬间被一个热点模板的请求压垮，这就是缓存击穿。

和缓存穿透、雪崩两个概念的区别可以简单记一下：

  • 缓存穿透：请求的就是数据库中本来就不存在的数据，缓存再怎么加也命不中，请求直接打穿到 DB；

  • 缓存击穿：某一个热点 Key 在某个点上突然失效，大量请求集中去查这一条；

  • 缓存雪崩：一大片 Key 在同一时间段内集中失效，比如大批数据同一时间过期，导致大量不同的请求都回源数据库。

3. 为什么解决缓存击穿时，要用“双重判定锁”？只加分布式锁不就够了吗？

只加锁而不做双重判定，看起来是线程安全了，实际上会浪费很多资源。

不做双重判定的逻辑大概是：

  1. 1.

    线程 A 查询缓存发现没有，拿锁，查 DB，回写缓存；

  2. 2.

    线程 B、C、D… 也都查询缓存发现没有，排队拿锁；

  3. 3.

    A 释放锁后，B 拿到锁，再次查 DB + 回写缓存；

  4. 4.

    C、D 依然重复这一套。

理论上，只有第一个请求把 DB 数据加载进缓存就够了，后面的请求再去查 DB 属于“重复劳动”。

加了双重判定锁之后，流程会变成：

  1. 1.

    线程 A 查缓存无 -> 拿锁 -> 再查一次缓存仍无 -> 查 DB + 回写缓存；

  2. 2.

    线程 B 等待 A 释放锁 -> 拿到锁 -> 再查缓存，此时已有数据，直接返回，不再访问 DB。

双重判定的好处：

  • 在高并发场景下，大部分线程只是等待+读缓存，不会重复查 DB；

  • 能把数据库压力压到最低，真正有意义的查询只有“第一个拿锁的线程”。

在优惠券模板查询里，这一套直接落到了 findCouponTemplate 的实现里：先读 Redis Hash，不存在再拿 Redisson 的锁，再读一次 Hash，确定真的没有才查数据库并用 Lua 一次性写入 Hash + 过期时间。

4. 高并发极端情况下，双重判定锁有什么隐患？tryLock 和“分片锁”是怎么缓解的？

双重判定锁解决的是“重复查 DB”的问题，但在极端高并发下，还有一个坑：请求等待时间过长。

比如有 1 万个请求在同时查同一个模板：

  • 第一个线程拿锁，查 DB、写缓存，假设耗时 50ms；

  • 后面 9999 个线程都在 lock() 那里排队，最后一个线程要等上 9999 * 若干 ms，整体等待时间可能过 10 秒；

  • 应用层面大量线程阻塞在锁等待上，容易拖垮整个 JVM，甚至触发 OOM。

这时候可以考虑两种手段：

  1. 1.

    tryLock 快速失败 不排队抢锁，拿不到直接返回，比如：

    • 提示用户“当前访问人数较多，请稍后重试”；

    • 或者前端做个兜底文案 / 降级展示。

    好处是保护了服务端，不会因为锁排队把线程池塞满；缺点是用户体验会差一点，适合“可以重试、不影响核心流程”的接口。

  2. 2.

    分布式锁分片 思路是“不是所有请求都去抢同一把锁”，例如：

    • 对用户 id 取模，拆成 10 个锁 Key：coupon_template_lock:{templateId}:{idx}；

    • 同一时间可以有 10 个线程并行执行“双重判定 + 查 DB + 回写缓存”这段逻辑；

    • 热点非常高的时候，可以显著缩短整体等待时间。

在牛券这个项目里，模板查询本身不会到那种“秒杀”级别的极端 QPS，所以课程里主要是把这些手段当做思路讲清楚，实际落地时通常“双重判定锁 + 合理的限流 + 监控”就够用了。

5. 为什么解决穿透时要“布隆过滤器 + 空值缓存 + 分布式锁”一起上？

缓存穿透的问题是：请求的数据本身在数据库里就不存在，你再怎么查缓存都命不中，结果是每次都回源 DB。

单看三种方案，各有缺点：

  • 只用布隆过滤器： 能挡住绝大部分“明显不存在”的 Key，但布隆过滤器有误判率，遇到命中误判的 Key，还是会一路打到数据库。

  • 只缓存空值： 每次 DB 查不到就写一个“空标记”，下次直接从缓存判断。但如果有人恶意打很多不存在的 Key，你的 Redis 里会堆一堆“无意义空值”，占内存非常快。

  • 只靠分布式锁： 在穿透场景里，大家查的 Key 本来就都是不存在的，只靠锁会变成“高并发 + 全是浪费”，数据库压力依旧很大。

所以组合方案的逻辑是：

  1. 1.

    先用布隆过滤器挡掉大部分“根本不可能存在”的 Key；

  2. 2.

    过了布隆过滤器，再看是否命中“空值缓存”，命中就直接返回，不查 DB；

  3. 3.

    还没命中空值时，再用分布式锁把同一个 Key 的请求拦成一个，避免多线程一起查 DB；

  4. 4.

    查 DB 仍然不存在时，写一份空值缓存（短过期），后续请求直接短路。

这样三者结合起来，可以同时解决：

  • “绝大部分无效 Key 一步挡掉”（布隆）；

  • “短期内反复查同一个不存在 Key”（空值）；

  • “同一个 Key 的高并发挤在一个时间点上”（锁）。

在优惠券模板查询的最终版本里，你能看到完整的组合：

  • 先过 couponTemplateQueryBloomFilter.contains；

  • 再查 *_IS_NULL 这种空值 Key；

  • 再拿锁 + 双重判定；

  • 最后根据查库结果，要么写 Hash，要么写空值缓存。

6. 布隆过滤器如何预估数据规模？

布隆过滤器初始化时有两个核心参数：

  • expectedInsertions 预期插入数量；

  • falseProbability 允许的误判率。

项目里的 tryInit(640L, 0.001) 这一组只是示例，表达的意思是：

  • 当前场景下预估不会有特别离谱的优惠券模板数量，比如几百、几千个模板；

  • 允许的误判率是千分之一，也就是 1000 次里最多有一次“把本来不存在的 ID 误判为存在”。

真实项目里要考虑两件事：

  1. 1.

    业务量级：

    1. 1.

      如果你知道模板上限，比如“一个商家最多 1 万模板，平台总共几百商家”，那可以算一下预估总量，然后适当放一点余量；

    2. 2.

      粗暴一点就是：预估上限 * 2 或 * 3，不要卡死。

  2. 2.

    内存上限：布隆过滤器底层是 bit 数组，容量越大，占用内存越多，而且 Redisson 这种是初始化时一次性申请内存的。

    1. 1.

      比如：1 亿元素、误判率千分之一，大概需要 170M 内存，这个可以接受；

    2. 2.

      但你如果上来就配 30 亿，还要很低误判率，Redisson 直接给你报错，连初始化都过不了。

所以面对几十亿级的量级，一般做法和之前锁分片类似：分片布隆过滤器。

  • 把 30 亿划分成多个 Bloom 实例，比如 30 份，每份 1 亿；

  • 对模板 ID 做 hash 或取模，决定落到哪一个 Bloom 上；

  • 插入和查询都先算分片，再操作对应的 Bloom。

这样单个布隆的容量和内存都能控制住，同时整体逻辑还是统一的。

7. 为什么最终选的是 volatile-lfu 做 Redis 内存淘汰策略？

这里要同时考虑两个前提：

  1. 1.

    我们对部分 Key 做了“永不过期 + 预热”，比如大促期间的热点优惠券模板；

  2. 2.

    击穿防护方案是基于“热点 Key 尽量不要被 Redis 自己淘汰”的假设来设计的。

如果选错了淘汰策略，就有可能出现：

  • 你精心预热的热点 Key，被 Redis 的内存淘汰机制随机淘掉了；

  • 然后在一个峰值时刻，这个 Key 又突然被大量访问，等于自己制造了一次缓存击穿。

所有策略里，allkeys-* 这几种都存在这种风险：

  • allkeys-random：直接随机淘，热 Key 也会被干掉；

  • allkeys-lru / allkeys-lfu：理论上更偏向淘冷数据，但在某些时间窗口或异常访问行为下，热 Key 也可能中招。

而 volatile-* 这一组策略只会在“有过期时间的 Key”里做淘汰，对“永不过期的热点 Key”不下手，这就满足了我们对热点模板“尽量稳定”的要求。

在 volatile-* 里再选：

  • 为了避免 LRU 的“缓存污染”问题（一次性大批访问把真正的热点挤掉），更倾向于基于访问频率的 LFU；

  • 优惠券这种业务有很明显的冷热分布，LFU 更容易把真正没什么人用的模板淘掉。

所以在牛券里的选择是：volatile-lfu。

大体含义就是：只从设置了过期时间的 Key 里，淘那些访问频率比较低的，热点永不过期的 Key 尽量别动。

8. 什么是缓存污染？为什么说 LFU 比 LRU 更适合优惠券这类业务？

所谓缓存污染，大白话就是：一堆“路人数据”把真正有价值的热点数据挤出了缓存。

在 LRU 策略下，它只看“最近一次访问时间”。比如：

  • 你平时有一个真正热门的优惠券模板，一直都在被访问；

  • 某一天你跑一个批量任务，把很多“平时没人看的模板”都扫了一遍；

  • 这些冷数据突然都有了“最近访问时间”，在 LRU 眼里它们都“挺新鲜”；

  • 真正的热 Key 反而因为这一波冲击，被淘汰掉了，后面业务访问又变回查 DB + 写缓存。

这个场景在后端很常见：大批量导出、一次性导数、扫描任务等等，都可能短时间访问大量“不常用”的 Key。

LFU 看的是“访问频率”，而不是“最近一次访问时间”：

  • 真正的热点优惠券模板，一天之内被访问上万次，它的频率计数会一直很可观；

  • 那些偶尔被扫一次的冷 Key，即便最近刚刚访问过，频率也很低；

  • 淘汰时优先干掉这些低频数据，热点数据能持续留在缓存里。

对于有明显热区的业务（典型就是营销、券、活动、推荐），LFU 通常更合适，配合前面说的 volatile-lfu，可以在保障热点稳定的前提下，把有限的内存尽量留给“真的有人用的 Key”。

9. 怎么防止优惠券查询把数据库打挂的？

可以按“一个链路 + 三个问题”来讲：

  1. 1.

    先说业务场景

    • 优惠券模板是高频读接口，大促场景下 QPS 很高；

    • 直接查数据库扛不住，所以必须先落缓存。

  2. 2.

    然后分三块问题讲方案

    • 缓存击穿：

      • 热点模板用预热 + 永不过期处理；

      • 常规查询用 Redis Hash 缓存 + Redisson 分布式锁；

      • 锁里做双重判定，只有第一个拿锁的线程会查 DB，其它线程直接读缓存；

      • 极端高并发场景可以通过 tryLock 和锁分片进一步降低阻塞时间。

    • 缓存穿透：

      • 入口先做参数校验；

      • 布隆过滤器兜一层，不在集合里的 ID 直接拒绝；

      • 过滤后再查 Redis，如果是空值 Key，直接返回“模板不存在”；

      • 真的没缓存时，通过分布式锁 + 双重判定查 DB，查不到就写入空值缓存（短 TTL）。

    • 内存淘汰：

      • Redis 侧配置 maxmemory-policy=volatile-lfu；

      • 只在设置过期时间的 Key 中淘汰访问频率低的，永不过期的热点模板不轻易被赶出缓存；

      • 再配合监控和容量评估，确保热点 Key 稳定可用。

  3. 3.

    最后补一句整体效果

    • 在这套组合方案下，大部分请求都在 Redis 命中；

    • 即便遇到异常流量，对数据库的冲击也被锁和 Bloom Filter 抵挡住；

    • 真正打到 DB 的只会是极少数“首查 + 失效刷新”的请求。

这样一通说下来，面试官一般就能听出你不是只会喊“用布隆过滤器 + 分布式锁”，而是真的把“击穿 / 穿透 / 淘汰策略”和业务场景串到一块了。

优惠券 Excel 批量分发

1. Excel 驱动的优惠券分发整体流程是怎样的？

整体可以理解成「三段式」：

  1. 1.

    配置与准备阶段

    • 先在后管里创建优惠券模板，配好来源、库存、有效期、使用门槛等信息。

    • 通过单元测试或运营后台导出分发 Excel，里面主要就是用户 ID 列，测试时可以控制在几千条，线上可以到几十万甚至百万。

    • 创建一条优惠券分发任务，填上 Excel 的文件路径、关联的优惠券模板 ID、发送方式（立即 / 定时），任务信息会落到数据库，同时推一条延时消息到 RocketMQ。

  2. 2.

    v1 / v2 的分发执行阶段

    • RocketMQ 到点后，CouponTaskExecuteConsumer 消费到任务执行事件，先校验任务状态是不是「执行中」、优惠券模板是否「生效中」、库存是否合理。

    • 然后用 EasyExcel 按行读取分发 Excel，每一行代表一个待发券的用户，结合模板信息执行「校验 + 发券」逻辑。

    • v1 版本里，读到一行就立刻：扣缓存库存 → 扣数据库库存 → 写用户优惠券表 → 写用户领券列表缓存；

    • v2 版本开始，读 Excel 只负责把用户放进 Redis 集合，批量攒够一批再用 MQ 触发真正的「写库 + 写缓存」。

  3. 3.

    结果落地与任务收尾

    • 发券成功的用户会写入分库分表的 t_user_coupon_xx 中，并追加到对应用户的 Redis ZSet 里，ZSet 的 score 用领券时间，后续查询可以按时间倒序。

    • 发券失败（库存不足 / 已领过券）的记录，会写到 t_coupon_task_fail 表，后面可以按批次导出 Excel 给运营。

    • 当 Excel 全部扫完，且 Redis 中待处理的用户集合也被消费干净之后，分发任务状态会更新为 SUCCESS，填上完成时间，整个任务才算真正结束。

2. 用户优惠券表为什么要做分库分表？分片规则是怎么设计的？

用户优惠券属于那种天然会「长胖」的表： 用户多、营销活动多、每次活动又是成批地发券，不做分库分表，很快就会到单表几亿行。

这篇文章里有几个考虑点：

  • 数据量级预估：优惠券模板本身的数量是可以估的，但用户领券记录基本是「只增不减」，又配合各种渠道投放，很难准确估。干脆一开始就把 t_user_coupon 拆成 2 个库 * 32 张表，尽量把单表控制在亿级以内。

  • 分片键的选择：用户维度的场景通常围绕 userId 查，比如「查某个用户有哪些券」「某个用户的领券记录」。 所以分片键选 user_id，分片算法是简单的 Hash 取模：

    • 分库：user_id 做 mod 落到 ds_0 或 ds_1

    • 分表：user_id 再做 mod 落到 t_user_coupon_0 ~ t_user_coupon_31

  • 索引设计：表上有一个联合唯一索引 user_id + coupon_template_id + receive_count，用来控制「同一优惠券第 N 次领取」这种语义。

    • 业务上这列 receive_count 既是数据字段，也是限领规则的一部分。

    • 插入时如果违反唯一约束，直接通过异常知道用户已经领过，省掉一次额外查询。

整体下来，这套分片方案对准的就是两个目标：一是横向扩容空间够大，后面数据量再上来也不用立刻重构；二是按用户维度查时，不需要跨库跨表全扫。

3. v1 版本的优惠券分发逻辑主要有哪些问题？

v1 版本的逻辑从功能上是没问题的，但放到稍微大一点的量级上，就会暴露几个明显短板：

  • 单条处理太重 每读一行 Excel 都要做一整套动作：

    • Redis 扣一次库存

    • MySQL 扣一次库存

    • 插一条 t_user_coupon

    • 往 Redis ZSet 里加一条用户领券记录 5000 行就意味着几万次网络 I/O，CPU 大部分时间其实都在等网络。

  • 消息消费时间过长 Excel 一次性读完、发完，全都绑在一条 RocketMQ 消费里。 如果文件大一点、网络抖一抖，很容易让消费时间拉得很长，Broker 眼里看上去就像是「超时消费」，开始重投，等于给自己挖坑。

  • 失败场景不够细致 v1 对失败的处理比较粗：

    • 唯一索引冲突就 catch 掉直接 return，相当于静默忽略

    • 库存不足的情况也是简单 return 对运营来说，只能看到「有些人没收到券」，看不到到底是库存问题还是本来就领过。

  • 无法从中间点恢复 如果消费到一半应用挂了，消息重试会从头开始处理，之前成功的人还会再走一遍逻辑。 虽然靠唯一索引能挡一下重复插入，但整体来说既浪费时间，也不够优雅。

所以 v1 更像是「能跑通流程的版本」，而不是能扛住高并发、可观测性好的工程版本。

4. v2 为什么能把 5000 条记录的执行时间从 1 分钟压到 1 秒左右？

核心原因就一句话：所有会打网络的操作，能攒一起就绝不一条条调。

具体做了几件事：

  • Excel 读取阶段只做「攒人」 ReadExcelDistributionListener 在 v2 里不再直接插库，而是：

    • 用 Lua 脚本在 Redis 里做「扣库存 + 记录用户」这一整套逻辑；

    • 用户信息存到一个 Set 里，里面是 {"userId":xxx,"rowNum":yyy} 这种 JSON；

    • 当集合大小达到 5000，就发一条「批次就绪」的消息给下游消费者。

    这样读取 Excel 的那条消费，变成「纯内存 + 少数 Redis 调用」，极快。

  • 批量扣库存 + 批量插用户券 CouponExecuteDistributionConsumer 收到消息后，才会真正：

    • 用一条 SQL 扣减模板库存 stock = stock - N；

    • 从 Redis Set 里一次性 pop N 条用户记录出来，拼成 List<UserCouponDO>；

    • 用 MyBatis-Plus 自带的批量插入一次性写入。

    网络 I/O 的次数从「每人一次」变成了「每 5000 人一次」，性能差异非常明显。

  • 发券结果同步到缓存也走 Lua 批量 给用户追加领券记录时，同样是把一批用户的 ID 和券 ID 序列化成 JSON，交给 Lua 脚本在 Redis 里批量处理，避免在 Java 侧狂发单条命令。

  • 进度点位 + 宕机恢复 每读完一行 Excel，就把当前行号刷到 Redis，重试的时候直接从上次停的地方接着走，避免重复跑一遍前面的流程。

这些优化叠加起来，同样 5000 条记录，从「很多次网络往返」压成「少量几次」，1 分钟降到 1 秒就不奇怪了。

5. 为什么要把消息队列拆成两个消费者，而不是一个里全干完？

从业务上看，一个消费者里「读 Excel + 校验模板 + 扣库存 + 插库 + 写缓存」也能干完，拆分确实多了点工程工作量。但拆完之后有几个明显好处：

  • 消费时长可控

    • CouponTaskExecuteConsumer 只负责读 Excel 和做前置校验，逻辑非常轻，不会因为单个任务太大拖垮整个集群的消费进度；

    • 真正「重活」集中在 CouponExecuteDistributionConsumer，而且它的是批量执行，可以根据情况增加消费者数量、水平扩展。

  • 职责边界清晰 一个专注「解析任务 & 投递批次」，一个专注「批次落库 & 写缓存」，出问题时排查思路会清晰很多。

  • 适配顺序消息 最终「Excel 读取完毕」那条消息必须在所有「批次分发」消息之后消费，否则会有状态错乱的风险。 通过拆 topic + 按分发任务 ID 做 Hash 投递到同一队列，可以比较轻松地做到「单任务内顺序，任务之间并行」。

  • 后续扩展余地 如果后面想支持「重放某个批次」「单独重试某个批次」，现在这个拆分就很好做，几乎不用碰 Excel 解析那块逻辑。

所以不是「一个消费者做不到」，而是拆开之后整个系统的可维护性、可观测性和扩展性都更好。

6. Lua 脚本在整个方案里到底解决了什么问题？

Lua 脚本主要解决两类问题：原子性和网络 I/O 次数。

  1. 1.

    原子性问题 在 Redis 里，如果用多条命令完成一件事，比如：

    • 先 HGET stock 看库存够不够；

    • 再 HINCRBY stock -1 扣库存；

    • 再 SADD 把用户加进 Set； 中间任何一步被其他请求插队，都可能产生竞态。

    换成 Lua 后，这些逻辑在 Redis 侧一次性执行完，要么都成功，要么都失败，对库存这种敏感数据来说安全很多。

  2. 2.

    减少网络往返 原来一行 Excel 可能要发 3～4 条命令到 Redis，现在变成「单条 EVAL 调 Lua」，网络往返延迟直接砍几刀。

  3. 3.

    小技巧：用位运算「一条 Long 带两段信息」 这个地方更多是玩了一下：

    • 脚本既要告诉 Java「本次扣库存是否成功」，又要告诉你「当前用户集合的大小」，正常写法是返回一个结构或字符串自己切；

    • 这里改成：用高位存布尔值，低位存集合大小；

    • Java 这边用一个工具类按位还原两个值，性能比字符串 split 要好不少。

说白了，Lua 不是必须的，但它很适合「需要在 Redis 里做一点小逻辑，又不想来回打太多网络」的场景，这个分发流程刚好很适配。

7. 发券过程中，如何保证宕机重启后可以从上次进度继续？

这里的思路很简单：用 Redis 记录「Excel 已经读到第几行」，并且严格只递增不回退。

大致有两段逻辑：

  • 读取前先看进度 在 ReadExcelDistributionListener#invoke 的开头，每次读到一行，先去 Redis 里拿这次分发任务对应的进度值：

    • 如果缓存里是空的，说明还没记录过，正常处理；

    • 如果缓存里有值，并且已经大于等于当前 rowCount，说明这一行在之前的某次执行里已经处理过了，直接跳过自增 rowCount。

  • 读取后立刻写进度 当一行真正处理完（不管是成功入批次，还是因为库存不足记到失败表），都会把当前 rowCount 写回 Redis。 下一次从 MQ 重试时，读 Excel 还是从头读，但所有「行号小于等于进度值」的记录都会自动被 skip。

这种方式的好处是：

  • 不需要对 Excel 做复杂的「断点续传」，

  • 即便重试很多次，对数据库和缓存也几乎没有重复写入，

  • 开销只是每行多一次轻量级的 Redis set 操作，换来的是相对可靠的「幂等+续跑」能力。

8. 用户已经领过券或者库存不够时，是怎么记录失败原因并给前端看的？

这块的思路是：所有失败都落到一张单独的「失败记录表」，最后再导出成 Excel 给运营看。

具体有几个步骤：

  1. 1.

    建一张简单的失败表 t_coupon_task_fail 字段很克制：

    • batch_id：对应这次分发任务的批次号；

    • json_object：一段 JSON 文本，比如 {"rowNum": 94, "cause": "用户已领取该优惠券"}。 不试图把失败原因拆很多列，直接 JSON 存，后面导出时再解析。

  2. 2.

    两类典型失败场景

    • Excel 读取阶段库存就用完了： Lua脚本返回库存不足，监听器直接写一条 cause = 优惠券模板无库存。

    • 批量插库阶段发现有用户已领过券： 批量插入抛 BatchExecutorException 后，走单条插入，插入失败再查一次当前用户是否已领过这张券，如果是，就写一条 cause = 用户已领取该优惠券。

  3. 3.

    在分发任务结束时清理尾巴 当 distributionEndFlag = TRUE 的最终消息消费时，如果 Redis 里还残留了待发用户集合，说明这些人是「库存不够了，迟来的那批」，也会统一写入失败表，相应的 cause 为「优惠券模板库存不足」。

  4. 4.

    失败记录导出成 Excel 后续会有一个任务，把同一批次下的失败记录按分页从 DB 里捞出来，写到 Excel 文件，关联回优惠券分发任务。运营在后台点开就能直接下载，看到第几行失败、为什么失败。

这样做的好处是：

成功与失败走两条线，成功走业务主流程，失败集中到一个地方，既不影响主流程性能，也方便运营排查问题。

9. RocketMQ 的延时配置

分发任务是依赖 RocketMQ 的延时消息来「按计划执行」的，这里有两个细节要注意：

  • 最大延时时间的限制 默认的 timerMaxDelaySec 是 3600 * 24 * 3，也就是最长只能延时 3 天。 如果创建优惠券模板时，要求「N 天后自动开始分发」，而这个 N 超过 3 天，就会在发送消息时直接报错，broker 会返回类似：

    timer message illegal, the delay time should not be bigger than the max delay…

    公共云上的 RocketMQ 我这边已经把这个值调成了一年：

    textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                    
    timerMaxDelaySec = 31622400

    本地或自建环境的话，自己记得改一下；否则模板有效期和定时时间的校验逻辑就得限制在 3 天之内。

  • 延时消息和过期清理不会互相打架 RocketMQ 有一套「消息存储多久后清理」的配置，默认是 48 小时。 实际测下来，即便把清理时间调成 1 小时、延时时间设成 2 小时，延时消息依然能正常触达，这说明延时消息用的是一套特殊队列，不会被常规的过期策略直接清掉。

对业务同学来说，比较实用的点就是：

  • 要么调整 broker 配置，把 timerMaxDelaySec 放宽；

  • 要么在创建优惠券模板时就做校验，不允许「有效期开始时间」超过当前时间 + 最大延时上限。

10. 深分页问题是怎么暴露出来的？

深分页主要是出现在「查看某批次失败记录」这个场景里：

  • 正常情况下，失败记录不多，随手翻几页问题不大；

  • 但一旦 Excel 里大部分行都失败（比如库存完全没配对），t_coupon_task_fail 可能有几十万甚至几百万记录，这时如果还用 limit offset 的模式往后翻，性能就会急速下降。

在这篇文章里大致对比了几类方案：

  • 简单 offset 分页 limit (pageNo-1)*pageSize, pageSize，实现简单，但 offset 越大，数据库需要扫描的行数越多，后面几页会明显变慢。

  • 基于主键或时间的「大于某个值」分页 每次把当前页最后一条记录的主键 ID 或时间戳带回前端，下一页查询时则用：

    textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                    
    where id > lastId
order by id
limit pageSize

    这种通常被叫做「书签分页」或「游标分页」，在大表下性能非常稳定。

  • 配合缓存做书签记录（适合固定批次的浏览） 对于失败记录这种「一次分发、一批失败」的表，再引入分页的时候，可以把当前浏览的位置信息（比如最后一条的 ID）临时放在缓存里，前端只传一个轻量级的 token 上来，后端根据 token 解析出继续查的「游标」。

最后落地的是书签型分页方案：

在模拟 4000 万行数据时，书签分页依然能保持在毫秒级甚至更好的查询耗时，而 offset 已经是人眼可见的慢了。

失败记录这种场景，阅读体验能保持「翻到第 100 页也跟前几页一样快」，对运营来说就友好很多。

消息队列幂等消费

1. 为什么消息队列本身已经保证“不丢消息”，消费端还要做幂等？

消息队列像 RocketMQ、Kafka 一般只保证 “至少投递一次”（At Least Once），而不是 “恰好一次”。 只要消息没被标记为消费成功，Broker 就会不断重试投递，这就意味着：

  • 消费端重启、网络抖动、长 GC 等情况，都可能导致同一条消息被多次投递。

  • 对 MQ 来说，它只关心“最终一定要投递成功”，并不会关心你业务是不是被多次执行。

在很多业务里（比如发券、扣余额、扣库存），多执行一次和少执行一次一样致命：多发了券、重复扣了钱，都属于数据错乱。所以消息系统把“不丢消息”的责任兜住了，而“避免重复执行”的责任，就必须落在应用自己的幂等逻辑上，这也是为什么文档里一直强调“消费端必须自行实现幂等”。

2. 为什么这套方案要用 Redis + 消息去重表，而不是只用数据库？

核心考虑有几点：

  • 从性能角度：消息消费通常是高 QPS 的，尤其削峰、异步化之后，每条消息都访问数据库做幂等，会把 DB 压得很难受，而 Redis 在读写和并发控制上的性能更适合做高频的状态标记。

  • 从职责角度：

    • 数据库消息表更适合记录“业务状态”和历史，例如消费记录、调试排查日志。

    • Redis 更适合做短期、轻量的“并发控制 + 去重挡板”，比如：消费中 / 已消费。

  • 从实现复杂度：利用 Redis 的 SET NX PX 语义和 Lua 脚本，可以一条命令搞定“只抢一次 + 设置过期时间 + 取旧值”，逻辑简单、成本低。

所以设计大致是：消息表负责记录和兜底，Redis 幂等 Key 负责高性能挡板，两者配合起来既能保证性能，又能兼顾排查能力。

3. 为什么幂等状态要设置过期时间？2 分钟时间是怎么考虑的？

幂等状态如果不设置过期时间，一旦消费过程中出现“半途死机”的情况，就会出现：

  • 第一条消息刚标记为“消费中”，进程就挂了。

  • 之后所有相同消息再来，看到状态一直是“消费中”，就会不停延迟重试。

  • 最后既没真正消费成功，也没机会重新进入消费逻辑，最终都进死信队列。

为了避免这种“永远消费中”的僵尸状态，一般会给幂等 Key 加一个最长生存时间，比如：

  • 数据库消息表里：可以设置 10 分钟的“最长消费时限”，超时视为失败。

  • Redis 幂等 Key 里：根据具体业务选取更贴近实际的时间，例如文中使用 120 秒。

时间怎么选，大致看两个点：

  • 正常情况下，这类消息消费逻辑需要多长时间能跑完

  • 比较极端但不至于离谱的情况（如下游 RPC 慢一点）需要预留多少冗余

所以 2 分钟 / 10 分钟本质上只是经验值，你可以根据自己的业务链路耗时做调整，核心原则是：能覆盖绝大部分正常消费场景，又不至于把异常消息卡死太久。

4. 这套幂等方案是不是就能把重复消费的问题完全解决了？

不能算“完全解决”，更准确一点是：大部分“重复进入消费方法”的问题被解决了，但方法内部的业务逻辑还得自己兜住。

例如文中举的那种复杂流程：

  1. 1.

    检查库存（RPC）；

  2. 2.

    锁库存（RPC）；

  3. 3.

    开事务，插入订单；

  4. 4.

    调用下游服务；

  5. 5.

    更新订单状态；

  6. 6.

    提交事务。

即便有幂等挡板，如果在第 3 步插入订单时因为数据库异常失败了，消息会被重试：

  • 幂等 Key 会被删除，让重试时有机会重新进入消费逻辑。

  • 但是像“锁库存”这种操作，如果下游本身没有幂等或者补偿机制，就可能会被调用多次。

所以可以这么理解这套方案的定位：

  • 它可以解决 99% 的“消息重复投递 / 并发重复消费”问题。

  • 但无法替你把所有业务内部的副作用都变成幂等，这一层还是要依靠：

    • 下游接口的幂等设计。

    • 本地事务 + 唯一约束。

    • 或者单独的业务补偿方案。

5. 2 分钟幂等结束后，如果再来一条一模一样的请求怎么办

这个问题面试官比较爱问，理论上确实存在，但在实际业务里一般会拆开看：

  • 大部分 MQ 重投递的间隔和次数都比较集中，主要集中在业务执行的那几秒到几十秒内。

  • 两分钟都过去了，消息才再次出现，要么是非常极端的网络问题，要么就是上游又产生了一次同样的业务请求，这本身就属于 业务重复 了。

如果对方非要抠这个点，可以顺着往下讲两种思路：

  • 真要兜这种“长时间间隔的重复业务”，可以把幂等 Key 持久化在 MySQL 里，做分表存储，保留 7 天甚至 30 天也没问题，再通过定时任务清理过期数据。

  • 但是要看业务的性价比：很多场景里，这种“隔了几分钟还再来一模一样请求”的概率很低，往往只需要在关键链路做一点额外兜底就可以了。

简单说就是：短期幂等靠 Redis，长期幂等看业务需求决定要不要上数据库。

秒杀优惠券功能

1. 优惠券秒杀和普通“领券接口”相比，最大的差别在哪里？

普通领券场景下，基本就是做几件事情：校验模板是否存在、校验活动时间、扣一条库存、插一条用户领券记录，整体并发量一般也不算夸张，更多是“正确性”优先。

秒杀场景不一样，一旦发的是大额券或者热门券，流量会在短时间内集中冲击过来，系统要同时面对三件事：

  • 顶住瞬时高并发，不能一窝蜂全打到数据库上；

  • 控制库存，不允许超卖；

  • 控制单用户限领次数，不能超领。

所以在这套实现里，前置用了 Redis + Lua 做缓存挡板和用户限领；后置又用编程式事务和行锁扣减 MySQL 库存保证不超卖；再配合 RocketMQ、Canal 等机制把“慢操作”挪到异步链路上去处理，整体思路是：前台快进快出，后台慢慢把账补齐。

2. 扣减数据库库存为什么要用“行锁 + 条件判断”，不是已经在 Redis 里扣过了吗？

Redis 的扣减是“第一道坝”，更多是防止瞬时流量把数据库打爆，以及降低超卖概率；但它本质上是缓存，不具备强一致性保证。真正能兜底的是数据库里的那一行记录。

SQL 里这段条件：

UPDATE t_coupon_template
SET stock = stock - #{decrementStock}
WHERE shop_number = #{shopNumber}
  AND id = #{couponTemplateId}
  AND stock >= #{decrementStock}

有两个关键点：

  • stock >= #{decrementStock}：防止在极端并发下出现“Redis 认为还有 1，MySQL 实际已经减到 0 了”这种情况，多加这一条件后，多出来的那次扣减会直接返回 0 行受影响；

  • 这条 UPDATE 会走行锁，同一行上的库存扣减是串行的，不会出现两个线程同时对同一库存做运算再覆盖的情况。

可以理解为：Redis 负责挡住大部分脏并发，MySQL 负责兜底保证数据库里这笔账不会错。

3. 往 Redis 里写用户领券缓存，为什么要“写后再查一次”？

从代码逻辑看确实有点“八股”，但背景是这样的：在 Redis 持久化和主从复制都比较极端的情况下，我们没法完全信任“写入返回成功”就等于数据真的稳定落地了。

几个典型风险场景：

  • 只开 AOF，刷盘策略不是 always，那就有可能刚写完还没刷到磁盘就宕机了；

  • 主从复制是异步的，主节点写成功返回客户端，但还没来得及同步到从节点，主节点刚好宕机，从节点被提升为主，就丢掉了那条数据。

所以在写完 ZSet 之后，再来一次 score 查询：

  • 能查到就当做一切正常；

  • 查不到，就再尝试写一次，尽量把“因为异常导致的漏写概率”再压一压；

  • 查的时候异常了，就直接兜底再写一遍。

这套操作不是为了“绝对不丢”，而是把丢的概率尽量压到很低，并且逻辑都集中在一个地方，后续要改可以统一改。

4. v1 版本里，整个扣库存 + 写 Redis + 发 MQ 都是在一个事务里做的，会有什么问题？

从代码上看，v1 的主流程大概是这样的：

  • Redis Lua 扣减库存、校验限领；

  • 进入事务：扣减 MySQL 库存、插入用户领券记录、写 Redis 用户优惠券 ZSet、写后查校验、发送延时 MQ。

从“正确性”角度看，事情都做完了再提交，顺序非常安全；但从“秒杀性能”角度看，这么设计有几个明显的问题：

  • 事务里做了大量非必要的耗时操作（访问 Redis、访问 MQ），事务时间被拉长，数据库连接占用时间也更久；

  • 秒杀活动一旦压上来，事务多、占用时间长，很容易把连接池耗干，反过来拖慢整个服务。

所以你可以把 v1 理解成“功能正确但偏保守”的版本，适合流量没那么夸张、又希望流程一条链闭环的场景。当真正需要压吞吐的时候，就得像后面那样：把慢操作从主事务里剥出去，用异步把链条拆开。

5. 引入 Canal + Binlog 之后，架构上到底解决了什么痛点？

痛点主要来自 v1 里那句：“在一个事务中干太多事”。

Canal 这条链的思路是：

  • 让业务主流程只负责“写好数据库的真相”，例如插入一条 t_user_coupon 的记录；

  • MySQL 把这次变更写入 Binlog；

  • Canal 订阅 Binlog，解析出变更数据，推到 RocketMQ 的 Canal Topic；

  • 引擎里的 CanalBinlogSyncUserCouponConsumer 消费这条消息，再去写 Redis 缓存、发延时 MQ。

这样有几个直接收益：

  1. 1.

    接口事务里只包含“库内的那几步”，Redis 和 MQ 都从主链路中拿掉，接口耗时会明显下降；

  2. 2.

    即便 Redis 或 MQ 临时抖一下，对数据库事务也没有影响，最多只是“缓存晚一点建好”或者“延时消息晚一点发出”；

  3. 3.

    Binlog 天然记录了数据变更的完整历史，对排查问题也很有帮助。

你可以把它看成是：数据库负责写“账本”，Canal 负责把账本里的新记录抄一份发给订阅者，Redis 和 MQ 都只是账本的派生物。

6. 面对 Redis 丢数据、消息异步这些不一致风险，整体怎么跟面试官或同事解释这套取舍？

可以分两层说：

  1. 1.

    先明确场景差异

    • 像订单、转账、12306 这类业务，每一笔都必须“账账对齐”，哪怕牺牲一些吞吐量，也要优先保证强一致，通常会采用数据库主导的扣减方案，Redis 只是配合做缓存；

    • 优惠券这种，偶尔多发一张或者个别请求因为极端情况失败，更多是体验问题，损失可控，不值得为了这一点，强行把所有流量堆到数据库上。

  2. 2.

    再解释具体方案

    • 前置用 Redis + Lua 扣减库存和限领，扛住高并发、降低超卖概率；

    • 后置用 MQ 把“插库 + 写缓存 + 发延时消息”异步化，缩短接口耗时；

    • 如果强调体验，可以在“用券环节”做一次兜底：发现用户缓存里有券但数据库里没记录，可以把缓存删掉、打标记、甚至补发一张券给用户，这属于业务补偿层面的设计。

总结就是：消息队列架构并不是完美无缺，而是它刚好匹配“优惠券秒杀”这种业务的特点，性能、成本和一致性之间的平衡点放在了这里。

优惠券预约通知功能

1. 为什么预约提醒用 RocketMQ 5.x 延时消息，而不是 Redis 或定时任务？

一开始也对比过几种方案：

  • Redis 延时队列 / 自己滚轮时间轮 逻辑实现不难，但本质上还是把大量“几小时、几天后才触发”的数据放在内存里。几百万条预约一上来，Redis 内存会膨胀得很快，性价比不太高，而且一旦做持久化，又会回到 IO 压力的问题。

  • MySQL 存储 + 定时任务扫描 写入简单，但读的压力很大。比如每分钟跑一次任务去扫“即将触发的预约”，大量 where 条件 + 索引扫描，对库的 QPS、磁盘 IO 都很伤。后面还得自己做分批处理、翻页扫描、过期清理，复杂度也不低。

  • RocketMQ 5.x 任意延时消息 延迟这一层交给 MQ 做，数据落盘，不占业务内存，几百万条消息也能扛住。业务侧只需要在创建预约时发送一条延时消息，到点自然会推给消费者，整个链路会简单很多。

综合下来，对于“海量、延迟较长、对时效性有要求”的预约提醒，RocketMQ 5.x 的任意延时消息更贴业务场景，所以最终选了这条路。

2. 用户预约提醒为什么要用位图（bitmap）存到一个 Long 字段里？

如果从建模上讲，“一条提醒一条记录”是最直观的：user_id + coupon_template_id + remind_time + type 做唯一索引就完事了。但真正落到业务上会有几个问题：

  1. 1.

    一个券往往会有很多时间点和提醒方式组合 比如同一张券，用户可能勾了：

    • 开抢前 30 分钟 App 通知

    • 开抢前 15 分钟 App 通知

    • 开抢前 5 分钟 邮件提醒 用行记录存的话，光一张券就三条记录，用户多了以后数据量会非常可观。

  2. 2.

    位图能极大压缩存储 我们约定：

    • 每 5 分钟一个刻度，最多支持提前 60 分钟 → 12 个时间点；

    • 一共最多 5 种提醒方式（目前只用了 APP、邮件两种，但为未来预留）； 于是一个 Long 有 64 位足够用了：

    • 0~11 位表示【提醒方式 0】从 5 分钟到 60 分钟的开关

    • 12~23 位表示【提醒方式 1】……以此类推

    这样一来，一个用户对某张券所有预约信息，就都压在 information 这一个字段里了。

  3. 3.

    位运算读写效率很高

    • 新增提醒：算出对应 bit 的位置，做一次 information ^ bitMap 就能“合并”进去；

    • 判断是否重复：(information & bitMap) != 0 直接知道这个时间点+提醒方式有没有设置过；

    • 取消提醒：同样用异或把对应的位“抹掉”； 对 CPU 来说，这些都是极快的常数时间操作。

所以整体思路是：用少量存储换更好的扩展性和吞吐，而不是把预约当成一堆散落的行记录来操作。

3. 为什么用户预约提醒的表不用分库分表？

这个表专门用来存“用户某张券的预约信息”，主键就是 (user_id, coupon_template_id)。里面没有太多宽字段，所以整体算下来单表容量其实不小：

  • 主键两个 bigint，按 MySQL 页大小 16KB 粗略估算，三层 B+ 树结构可以顶到 2 亿条左右。

  • 我们假设用户量 5000 万，人均预约 4 张券，这个表也还能撑住。

再加上有定时任务清理过期预约记录，数据始终在一个可控的区间，不至于一路膨胀，所以没必要一开始就搞分库分表。

4. 创建优惠券预约提醒整体流程

大致可以分成三步：

  1. 1.

    校验 + 查询券信息

    • 先根据 shopNumber + couponTemplateId 去查优惠券模板；

    • 顺便解决缓存穿透/击穿问题；

    • 再看开抢时间是不是还没开始，已经开始的直接不允许创建预约。

  2. 2.

    创建/更新预约记录（位图操作）

    • 从 t_coupon_template_remind 里查一条 (user_id, coupon_template_id) 记录：

      • 不存在：说明是第一次对这张券做预约

        • 算出 information 的初始位图（根据提醒时间、提醒方式）

        • 把券的 validStartTime 也带进去，后面解析预约时间需要用到

        • 插入新记录

      • 存在：说明这张券已经预约过了

        • 根据 request 计算一个新的 bitMap

        • 先用 information & bitMap 判重，如果已经设过就直接给出提示

        • 没设过的话，用 information ^ bitMap 合并。

  3. 3.

    发送 RocketMQ 延时消息

    • 构造一个 CouponRemindDelayEvent，带上：

      • 用户 ID

      • 券 ID

      • 店铺编号

      • 提醒方式、提醒时间（比如提前 5 分钟）

      • 开抢时间 & 真实触发时间（startTime - remindTime）

    • 用 RocketMQ 5.x 的任意延时能力发送出去，到点由消费者拉起提醒逻辑。

主流程里只做一次 DB 写 + 一次 MQ 发送，复杂计算都在位图工具类里，整体比较轻。

5. 消费者收到延时消息后，为什么还要用线程池进行并行发送提醒？

如果不加线程池，消费者的模式基本就是：一条消息处理完再处理下一条。对于普通业务还好，但在预约场景里，会出现某一刻集中倾斜的情况：

比如 18:00 开抢前 5 分钟，17:55 这一个时间点集中推一波消息。

这个时候消息堆在 MQ 里，如果消费者一条条串行执行，用户能收到通知，但有可能收到得比较晚，体验会有落差。

引入线程池主要是两点考虑：

  1. 1.

    彻底把发送 IO 和 MQ 消费解耦

    • MQ 消费线程只负责把消息转成 DTO 丢给线程池，自己赶紧返回；

    • 真正调 App 推送、邮件服务这些 IO 调用，都放到线程池里异步处理。

  2. 2.

    利用多核 + IO 密集特性 线程池的配置也是针对 IO 密集型任务调过的：

    • 核心线程数：CPU * 2

    • 最大线程数：CPU * 4

    • 队列：SynchronousQueue，尽量不排队，要么直接交给新线程，要么调用方自己执行（拒绝策略是 CallerRunsPolicy）

这样可以在一段时间内压榨出机器的 IO 能力，把这波提醒尽快刷出去，减少“消息已经到点，但用户迟迟没收到通知”的情况。

6. 线程池里任务万一在执行过程中机器宕机，提醒就丢了怎么办？

这个地方专门做了一层“兜底”：

  1. 1.

    先写 Redis，再丢线程池

    • 每条提醒消息会先在 Redis 里写一条 Key，内容是这次提醒的 DTO；

    • Key 的格式里会带上用户 ID、券 ID、提醒时间、提醒类型，确保唯一。

  2. 2.

    同时往 Redisson 延迟队列塞一条“检查任务”

    • 使用 Redisson 的 RDelayedQueue，给这个 Key 延迟 10 秒；

    • 10 秒后，有一个后台线程会从阻塞队列里消费这个 Key。

  3. 3.

    10 秒后检查任务是否完成

    • 如果线程池正常执行完任务，会主动把这个 Redis Key 删掉；

    • 后台线程取到 Key 后：

      • 如果 Key 已经不存在，说明这条提醒已经完整发完，可以忽略；

      • 如果 Key 还存在，说明任务很可能卡在执行过程中，例如机器中途挂了；

        • 这时会把原始 DTO 重新发一条 MQ 消息，再走一遍提醒流程；

        • 最后删掉 Key，避免死循环。

为什么这个方案接受度还挺高？

  • 一方面提醒类任务本身不算强一致，只要大多数能发出去，个别多发、少发对业务影响不致命；

  • 另一方面，这套 Redis 延迟队列是跑在多实例上的，只要不是全体实例一起挂，总会有人起来把这批“待检查 Key”给捞走。

7. 用户取消预约提醒，怎么通过位运算做到“只删某个时间点/提醒方式”？

取消逻辑其实是创建逻辑的一个镜像操作，关键也是位运算：

  1. 1.

    先找出这条记录

    • 还是按 user_id + coupon_template_id 查 t_coupon_template_remind；

    • 没找到就直接提示“模板预约信息不存在”。

  2. 2.

    算出这次要取消的 bit

    • 根据入参里的 remindTime 和 type 调用 calculateBitMap；

    • 拿到一个只在相应位置为 1 的 bitMap。

  3. 3.

    用按位与判断是否真的预约过

    • (bitMap & information) == 0 说明这个 bit 在原来的 information 里就是 0；

    • 换句话说，用户根本没预约这个时间点的提醒，直接提示“您没有预约该时间点的提醒”。

  4. 4.

    用异或把这个 bit“抹掉”

    • bitMap ^= information 之后，得到的是“取消这个时间点之后”的新位图；

    • 如果新的位图是 0，说明这张券已经没有任何提醒了，直接把这条记录删掉；

    • 否则就更新 information 字段，保留其它时间点的提醒。

配合一层乐观锁（update/delete 时带上老的 information 条件），还能顺带防一下“同一时刻新增+取消一起操作”的并发问题。

8. 消费者怎么判断一条延时消息对应的预约是不是已经被取消？为什么要引入布隆过滤器？

判断逻辑分两层：

  1. 1.

    先过布隆过滤器（快速挡一批）

    • 在用户取消提醒时，会把 (couponTemplateId, userId, remindTime, type) 四元组算个 hash，塞到 cancelRemindBloomFilter 里；

    • 消费者拿到消息后，先把这四个字段算同一个 hash，去布隆过滤器里问一声：

      • 不存在：说明这条预约极大概率没有被取消，可以直接认为是有效提醒；

      • 存在：要么是真的取消了，要么是布隆过滤器误判，这时候再查 DB 做精确判断。

  2. 2.

    落到数据库做精确校验

    • 先查 t_coupon_template_remind 有没有这条 (user_id, coupon_template_id) 记录；

      • 没有，说明整张券的所有预约都被删光了，返回“已取消”；

    • 有的话，再用位图算一遍 (bitMap & information)：

      • 如果结果是 0，说明这个时间点的提醒位已经被清除，也是“已取消”；

      • 否则才算“还有效”。

布隆过滤器的作用就是：绝大部分没取消的消息，直接在内存里快速通过，不需要每条都压到 DB。只有少量处于“可能取消”的消息才去查库，大幅降低数据库压力。

优惠券查询 & 折扣金额计算

1. 接口为什么既要查“可用/不可用优惠券”，还要顺带算优惠金额？

从业务上看，前端在结算页其实要的不是“用户有哪几张券”，而是：

  1. 1.

    哪些券当前这笔订单能用，哪些不能用；

  2. 2.

    能用的券里面，各自能减多少钱（立减多少、折多少）；

  3. 3.

    最后按优惠力度从大到小排一排，好让用户一眼看到“最划算”的那张。

所以这个接口干的事其实就是：在查询优惠券列表的基础上，把每张券套到当前订单上算一遍“能减多少钱”，再按金额排个序。

从代码层面来说，查询和计算这两件事本身就强绑定在一起了，拆开反而会让前后端配合更复杂，还得多一个接口做二次计算。

2. 立减券、满减券、折扣券分别是怎么判断可用、怎么计算优惠金额的？

这里的规则基本是按“常见电商玩法”来的，只是写到了代码里：

  1. 1.

    立减券（type = 0）

    • 不看门槛，拿到就能用（当然，实际可用还要看适用范围，比如商品券是否匹配商品）；

    • 计算方式简单粗暴：优惠金额 = maximumDiscountAmount。

  2. 2.

    满减券（type = 1）

    • 需要满足条件金额：

      • 店铺券看的是 orderAmount；

      • 商品券看的是对应 goodsAmount；

    • 如果金额 >= termsOfUse，这张券就“点亮”，优惠金额 = maximumDiscountAmount；

    • 否则这张券就进不可用列表。

  3. 3.

    折扣券（type = 2）

    • 同样有是否满足 termsOfUse 的判断；

    • 可用时先算一个“原始折扣金额”：amount * discountRate；

    • 再跟 maximumDiscountAmount 比一下，上限封顶：

      • 如果“打完折减掉的钱”大于上限，就用上限；

      • 否则用实际折扣额。

这样做的好处是：所有规则都放在券的 consumeRule 里，以 JSON 形式配置，服务层只负责解析并执行规则，不把规则写死在代码里。

3. 多线程版本里，为什么要用 Collections.synchronizedList 来存储可用/不可用优惠券？

因为在并行版本里：

  • 每一个 CompletableFuture.runAsync 任务都会根据规则，往 availableCouponList 或 notAvailableCouponList 里 add 一条记录；

  • 这些 add 操作是同时发生的，并不是一个任务结束后再开始下一个。

如果还是用普通的 new ArrayList<>()，在多线程环境里会有几个隐患：

  • 多个线程同时修改内部数组，size 还没更新完就又来一次 add，可能直接抛异常；

  • 严重点会出现数组越界、数据覆盖等问题，特别难排查。

Collections.synchronizedList 的底层做法其实很直接：

  • 内部包了一层 SynchronizedList，所有对底层 list 的操作都加了一把 mutex 锁；

  • 多线程环境下，同一时刻只有一个线程能执行 add / remove 等写操作。

对我们的场景来说，这些集合基本都是“写多读少”，只要能保证写入不乱就够用了，所以用这个方式就比较合适。

4. 为什么不用 CopyOnWriteArrayList，也支持并发写？

CopyOnWriteArrayList 的设计思路是：写操作不加锁，但每次写都复制一份新数组。

这个结构非常适合“读很多、写很少”的场景，比如监听器列表、配置快照等：

  • 绝大多数线程在读，不会被卡住；

  • 偶尔有一次写，多复制一次数组问题也不大。

但我们现在这个场景刚好反过来：

  • 在一次请求生命周期里，这两个列表会被频繁 add，几乎没什么读取操作；

  • 每一次 add 都复制整个数组的话，开销其实比加锁还大，特别是优惠券数量多的时候。

所以这里用 Collections.synchronizedList(new ArrayList<>()) 会更稳一些：

  • 写操作简单粗暴地上锁；

  • 不会频繁复制数组；

  • 这两个集合只在最后排序和返回前端的时候读一次，对读性能没那么敏感。

5. 多线程并行以后，一定会比原来的同步版本快吗？

不一定，甚至在一些压测场景下，多线程版本反而不如单线程稳定，原因大概有这么几类：

  1. 1.

    线程切换 & 调度开销

    • 每个优惠券计算逻辑其实很轻量，几行 BigDecimal 运算 + 一两个 JSON 解析；

    • 如果任务本身不到 1ms，线程创建、调度、上下文切换的成本反而更明显。

  2. 2.

    共享资源竞争

    • 虽然用 synchronizedList 保证了线程安全，但所有线程都在抢同一把锁；

    • 持券数量较多时，锁竞争会比较激烈，多线程就变成了“排队加锁”。

  3. 3.

    JMeter 高并发下，线程池本身也会成为瓶颈

    • 外层还有 Web 容器线程（比如 Tomcat/NIO 线程），内层我们又开一层业务线程池；

    • 压高并发时，两个线程池叠在一起，很容易出现 CPU 飙高、上下文切换过多的情况。

所以这章节最后也特意提了一句：

多线程不是银弹，用得不对，性能不一定提升，有时甚至会掉。真正要不要并行，还得结合实际持券数量、单券计算复杂度、机器配置等因素，用压测数据说话。

6. 既然多线程优化不一定有收益，为什么还要写个多线程版本呢？

这章更像是一个“实践+反思”的过程，而不是单纯炫技：

  • 一方面，把如何用 CompletableFuture 做并行计算，以及线程安全、线程池参数设置这些细节走了一遍，方便以后遇到类似场景可以直接复用；

  • 另一方面，也顺带告诉大家：

    • 并发编程需要结合场景，不能一上来就觉得“多线程 = 性能提升”；

    • 真正是否有收益，要看实际压测数据，而不是凭感觉。

后面再接上“压测章节”，给出实测的 QPS、响应时间对比，这三章连在一起，其实就是一套完整的思考路径：

创建优惠券模板责任链

1. 为什么要用责任链模式？

在没有引入责任链之前，创建优惠券模板的参数校验通常会写成下面几种形式：

  • 在 createCouponTemplate 方法里堆一长串 if / else 判断；

  • 或者抽一个 validateXXX(requestParam) 大方法，里面塞满各种校验逻辑。

这种写法有几个明显问题：

  1. 1.

    职责不清晰、方法越来越臃肿：所有校验揉在一起，一个方法里既判断必填项、又判断格式、还要查库校验业务约束，导致方法越来越长，很难快速看懂「这一段是在干嘛」。

  2. 2.

    扩展性差，改动成本高：新增一个校验规则要么去改那段 if / else，要么继续往 validateXXX 里塞逻辑，很难做到「增加功能不修改原有代码」，违反开闭原则。

  3. 3.

    复用困难：某些校验逻辑（比如时间范围合法性、店铺是否存在等）本来可以复用到其他业务（比如修改模板、复制模板），但因为写死在方法里，想抽出来又很痛苦。

  4. 4.

    测试不友好：大方法里什么逻辑都有，单元测试要覆盖每个分支非常麻烦，也不方便针对某个校验规则单独写测试。

引入责任链后，把复杂的校验拆成多个「处理器」，每个处理器只关注一件事（比如非空校验、基础格式校验、业务校验等），既符合单一职责原则，又方便新增/下线某个规则，整体结构会清晰很多。

2. 执行创建优惠券会走哪些责任链处理器？

例如：

  1. 1.

    必填项非空校验处理器

    • 校验优惠券名称、优惠类型、有效时间、库存等是否为空；

    • 类：CouponTemplateCreateParamNotNullChainFilter。

  2. 2.

    基础格式与范围校验处理器

    • 校验时间区间 valid_start_time < valid_end_time；

    • 校验库存必须是正数；

    • 校验 JSON 字段结构是否符合预期、数值是否在合理范围内；

    • 类：CouponTemplateCreateParamBaseVerifyChainFilter。

  3. 3.

    业务一致性校验处理器

    • 校验店铺编号是否存在、是否属于当前登录用户；

    • 校验商品编码是否存在、商品是否属于该店铺；

    • 校验平台券/店铺券与来源、成本承担逻辑是否匹配；

    • 类：CouponTemplateCreateParamBizVerifyChainFilter。

  4. 4.

    扩展规则校验处理器（可选）

    • 比如校验「同一时间同一店铺类似优惠活动是否超出上限」；

    • 校验运营侧通用规则（如某些品类禁止打折等）。

每个处理器都实现统一接口 MerchantAdminAbstractChainHandler<T>，对外暴露一个 handler(T requestParam) 方法，责任明确、粒度清晰，后续想加某个新校验，只需要新增一个实现类接入责任链即可。

    启动时扫描 Bean：

    把 Spring 容器中所有责任链处理器 Bean 拿出来。

  2. 2.

    按 mark 分组

    • 遍历这些 Bean，调用每个 Bean 的 mark() 方法；

    • 以 mark 为 key，把属于同一场景（例如「创建优惠券模板」）的处理器放入同一个 List<MerchantAdminAbstractChainHandler> 里。

  3. 3.

    按优先级排序

    • 各处理器都实现了 Ordered 接口；

    • 通过 unsortedChainHandlers.sort(Comparator.comparing(Ordered::getOrder));

    • 实现「order 值越小，处理越靠前」，比如：

      • 0：非空校验

      • 10：基础格式校验

      • 20：业务校验

    执行业务链 当业务中调用：

    merchantAdminChainContext.handler(mark, requestParam);

    时，就会拿到这个 mark 对应的处理器列表，然后顺序执行：

这样一来，责任链的组装、排序、执行都被封装到了 MerchantAdminChainContext 里，开发者只需要关心「我传哪个 mark、requestParam 是什么」就够了。

要实现「失败即中断」的效果，最常见也是最简单的做法是：在处理器内部抛出异常，例如统一的业务异常 BizException / ClientException 等：

  • 当前处理器的后续逻辑不会执行；

  • forEach 会立即终止；

  • 上层 createCouponTemplate 可以捕获异常并返回统一的错误响应。

  • 最终会通过 Web 全局异常拦截器捕获并返回前端。

扩展思路：

如果以后想支持「不中断，只记录告警」的场景，也可以在责任链模型上做扩展，例如：

  • 在 handler 方法里返回一个状态对象；

  • 状态对象中包含 pass / fail / warn 等标记；

  • 上层根据状态决定是否继续执行、是否告警等。

但在牛券实现「参数校验」场景下，校验失败直接抛异常中断，是最简单也最常见的实践。

创建优惠券模板分库分表

1. 为什么优惠券模板这张表需要考虑分库分表？单表顶不住吗？

从业务侧看，优惠券的主体是商家。按“3000 万商家，每个商家平均创建 100 张优惠券模板”来估算，单表数据量大概会到 30 亿行。而且这个数字还是“当下的保守估计”，随着商家增长和运营玩法迭代，未来只会越来越大。

单表撑不住主要体现在几方面：

  • 存储压力：几十亿行堆在一张表里，备份、迁移、DDL 调整都非常痛苦。

  • 查询性能：即便走索引，页分裂、索引层级增加后，磁盘 IO 次数会明显上升，延迟抖动会变大。

  • 写入性能：高并发写入场景下，行锁/页锁竞争会越来越明显。

所以与其等到单表撑爆再救火，不如在设计之初就按「海量数据 + 未来增长」的维度规划好分库分表方案，把优惠券模板做成天然可扩展的存储结构。

2. 为什么单表上限控制在大约 2000 万？

单表到底能撑多少数据，没有绝对标准，取决于：

  • SQL 是否复杂，是否大量走全表/联合查询；

  • 是否能稳定命中索引；

  • 底层存储和硬件条件（磁盘、IOPS 等）。

在优惠券模板这个场景里：

  • 查询模式相对简单，大部分都是带分片键、走单表索引的分页查询；

  • 不需要跨表 join，也没有太重的分析类 SQL。

在这种前提下，把单表控制在 2000 万左右 是一个比较安全、留有余量的经验值：

  • 数据量不到特别夸张时，通常 3 次左右磁盘 IO 就能命中到目标记录，性能比较稳定；

  • 后续考虑备份、迁移、分区、DDL 等操作，也不会因为单表太大而“动一次就抖一次”。

所以用 30 亿 ÷ 2000 万 ≈ 150 张表 作为规划基准，再配合分库，把压力摊薄，是一个比较务实的折中方案。

3. 优惠券模板为什么“只分表就行”还要讨论分库？

对于优惠券模板这个实体，可以从两个维度看是否需要分库：

  1. 1.

    写入并发是否逼近 MySQL 实例上限？

    • 单台 MySQL 的写入瓶颈大约在 4000–5000 TPS 左右；

    • 如果创建优惠券模板的 QPS 不高（商家配置优惠券的操作本身就不算高频），其实可以只分表、不分库。

  2. 2.

    是否有后续复用的需求？

    • 后面真正高并发的是「优惠券发放 & 领取」业务，那一块大概率要分库；

    • 为了避免后面再重复做一次拆表、迁库动作，示例中就直接用「分库 + 分表」的形态演示一套完整方案。

按现状只分表就够用，但从整体架构演进和教学示例的角度，直接展示分库分表的完整形态更有价值。

4. 为什么选择店铺编号作为分片键？

分片键的选型主要考虑三点：数据均匀、业务友好、不可变。放到优惠券模板业务里，就是：

  1. 1.

    业务查询路径决定了分片键

    • 商家后台的典型需求是“查询当前店铺创建的优惠券模板列表”，也就是：

      textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                      
      WHERE shop_number = ? ORDER BY create_time LIMIT ?, ?

    • 用 shop_number 做分片键，可以保证一间店铺的数据都落在同一个分片库/表里，分页查询只打一个分片，不需要跨库跨表扫。

  2. 2.

    数据分布相对均匀

    • 店铺数量巨大，店铺 ID 本身就是一个天然分散的维度；

    • 对 shop_number 做 Hash 取模，能比较自然地把不同店铺均匀打散到各个分片。

  3. 3.

    字段稳定，不会变更

    • 店铺编号一旦生成，就不应该被修改；

    • 用这种“业务主键级别”的字段做分片键，可以避免后续「改值 + 搬迁数据」的尴尬。

而如果选主键 ID 或创建时间：

  • 用 ID：你分页时一般是按 shop_number + create_time 排序，很容易出现跨分片范围查询的问题；

  • 用时间：优惠券创建行为早期店铺少，后期店铺多，会出现「时间切片明显不均匀」的问题，而且按店铺维度查询会变得非常难看。

所以对这个场景来说，shop_number 是一个同时满足“读路径友好 + 分布均匀 + 稳定不变”的理想分片键。

5. 为什么选 ShardingSphere，而不是 MyCat 或直接用 TiDB 这类分布式数据库？

回答如下：

  1. 1.

    ShardingSphere vs MyCat（都是“分库分表框架”）

    • 生态和社区

      • MyCat：社区相对小，版本更新和新特性节奏偏慢；

      • ShardingSphere：Apache 顶级项目，文档齐全，社区活跃度高，踩坑能搜到答案。

    • 功能和策略丰富度

      • MyCat：实现了基础的水平分表、垂直拆库，策略相对有限；

      • ShardingSphere：支持标准分片、范围分片、复合分片、自定义算法、读写分离、分布式事务等，扩展能力强。

    • 代码侵入

      • ShardingSphere-JDBC 模式可以直接嵌入到 SpringBoot 项目里，基本不改业务 SQL，改的主要是 DataSource 配置和分片规则文件，开发体验更好。

  2. 2.

    ShardingSphere vs 分布式数据库（PolarDB/TDSQL/TiDB）

    • 兼容性和迁移成本

      • 分布式数据库常常标榜兼容 MySQL，但在某些 SQL 语法、系统变量、运维方式上依然有差异，“几乎兼容”不等于“平滑迁移”。

    • 技术储备要求更高

      • 真出了集群层面的故障，需要团队里有人对这类分布式引擎有比较深的理解，否则线上事故处理风险很大。

    • 成本 & 成熟度

      • 公有云版 PolarDB、TDSQL 都是付费产品，总体成本明显高于自建 MySQL 集群；

      • TiDB 虽然有开源版，但社区 Issue 较多，踩坑成本不低，商业版又是另一套成本模型。

在“现有业务是 MySQL + SpringBoot，团队以 Java + 中间件为主”的前提下，用 ShardingSphere 做分库分表是一条更加务实、可控的路径。

这是典型的「读扩散（查询放大）」问题。

当 SQL 是：

  • 只好把这条 SQL 广播到所有库、所有分片表，再用 UNION ALL 合并结果，类似：

  • 极端情况下，稍有慢表就会拖垮整个查询，导致调用超时。

创建优惠券模板操作日志

1. 为什么要专门给优惠券模板做操作日志？

简单的业务，打两行 info 日志确实也能看个大概。但优惠券这种东西，有几个特点：

  • 商家自己会不断改规则：改库存、改门槛、改有效期，甚至关掉某个券；

  • 一旦出问题，影响的是钱：多给钱、少给钱、没给到钱，都会有人来追责；

  • 操作链路又长：运营、商家、平台后台都有可能改到同一张券。

这时候，你只靠程序日志（按时间滚动那种），排查成本会非常高，很难一句话看到“谁在什么时间对哪张券做了什么改动”。

专门搞一张 t_coupon_template_log：

  • 直接挂在店铺 + 优惠券模板 ID 上；

  • 把“原始数据 / 修改后数据 / 文案日志”都记下来；

后面商家问“为什么这张券昨天还能领，今天就不能用了”，你就有一条完整的审计线，既方便自己排查，也方便甩证据。

2. 为什么需要使用 biz-log 框架打印？

直接在 createCouponTemplate 里面手写插日志 String.format 也行。一开始确实没啥问题，代码大概长这样：

textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                
String operationLog = String.format("xxx %s xxx %s", ...);
couponTemplateLogMapper.insert(couponTemplateLogDO);

但你会慢慢发现几个坑：

  1. 1.

    业务方法越来越“花”：创建优惠券本身要做一堆校验、落库、缓存等逻辑，再加上操作日志那坨拼字符串，方法一下子变得很长，读起来很费劲。

  2. 2.

    所有地方都要手抄一份：不止创建要记日志，修改、上下线、停用、批量操作……都要记。每个方法都 copy 一段拼接逻辑，后面想改文案，得到处搜。

  3. 3.

    字段一变，全线跟着改：你在请求 DTO 里加了一个字段，比如“券标签”，原来的日志里没这个信息。你就得回头把所有日志拼接的地方都重新撸一遍。

所以才有了咱们的方案：用 Spring AOP 把“记录日志”这件事从业务方法里剥出去，对业务来说就一句注解，日志内容交给框架和 SpEL 表达式去处理。

3. 为什么不是自己写而是用开源框架？

自己写肯定能写，但你会踩不少“重复的坑”，比如：

  • 注解怎么设计？只支持简单字符串，还是支持变量、函数、条件？

  • 日志模版里需要取方法参数、返回值、当前用户信息，表达式怎么写才不丑？

  • 要不要支持“自定义函数”，比如把枚举值转成中文、做个格式化之类的？

  • 日志持久化怎么扩展？后面想发 MQ、落 ES，还得再加一层抽象。

mzt-biz-log 把这些活基本都帮你干了：

  • 注解语法设计好了一套，支持变量、SpEL 表达式、自定义函数；

  • 跟 SpringBoot 贴合得比较紧，直接加依赖、加 @EnableLogRecord 就能用；

  • 预留了 ILogRecordService 扩展点（还有很多自定义函数解析、缓存性能），你只管实现具体的“怎么保存”。

所以这个地方用现成的轮子，主要图省时间以及开源质量比自己写好很多。真要自己写，通常是在这套能力还“兜不住需求”的时候，再考虑造轮子。

4. 操作日志记录失败，是否要把整个业务操作失误回滚？

这个就看对日志这件事的态度了，课程里的选择是比较务实的一种：

  • 记录日志失败，不回滚业务

    • 优惠券创建是主业务，日志只是旁路记录；

    • 真让日志异常把主流程打挂了，商家那边直接感知到的是“券创建失败”，体验很差；

    • 正常做法是：捕获异常，打错误日志 + 告警，有问题再人工补。

  • 要不要异步？

    • 并发小、业务不敏感：直接同步落库就行，简单粗暴；

    • 并发大、链路比较长：可以在 record 里发一条 MQ，把 LogRecord 交给消费端慢慢落库，这样不拖慢主链路。

创建优惠券模板防重复提交

1. 为什么做“防重复提交”？

前端禁用按钮、加 loading 是第一道防线，但真要保险一点，后端还是得兜底。几个现实情况：

  • 用户网络抖一下，浏览器“卡在加载中”，人一急就疯狂点按钮；

  • 页面被刷新、回退再提交，请求其实已经发出去了，用户自己也分不清；

  • 系统本身有延迟，用户以为没点上，再点一次。

如果操作只是“多查了一次列表”，问题不大；但创建的是优惠券、订单、退款单这种带业务意义的东西，一旦重复，就是真金白银出去了，所以：

前端能拦一部分，真正兜底的逻辑还是要放在后端。

2. JVM 本地锁能不能直接用来防重复提交？

不够用，原因主要有两个：

  1. 1.

    只管当前进程，管不了集群

    • 单机 demo 里，synchronized 和 ReentrantLock 都是好用的；

    • 一上生产，服务一般都是多实例部署，你锁的是“这台机器上的这个方法”， 别的机器完全不知道这回事。

  2. 2.

    粒度太粗，不好区分“不同用户 / 不同参数”

    • 你要是真在方法上来个 synchronized，那等于所有人按顺序排队——吞吐量直接打死；

    • 想支持“同一个用户相同参数不能重复，不同用户互不影响”，本地锁要搞复杂的 Map 来管理，没啥必要。

所以，实际项目中直接把本地锁排除掉，一步到位使用分布式锁。

3. 分布式锁 Key 如何定义？

你可以把分布式锁理解成：“这一次操作的指纹”。

这一节里拼出来的 Key 结构是：

textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                
no-duplicate-submit:path:{请求路径}:currentUserId:{用户ID}:md5:{参数MD5}

拆开来看：

  • path：区分不同接口，比如“创建优惠券”和“修改优惠券”；

  • currentUserId：同一个用户重复点按钮要防掉，不同用户互不影响；

  • md5(参数)：同一个用户、同一套参数才算重复提交，换了参数就当新请求。

这样有几个好处：

  • 粒度比较合理，“谁 + 调的哪个接口 + 提交了什么” 都在里头；

  • 保证“同一个人提交同一份表单”会被拦住；

  • 不会影响其它用户正常提交，也不会误伤参数不同的请求。

4. 用 Redisson 分布式锁是不是就完美了？

锁只是控制并发窗口，并不能解决所有场景的问题。


时序图里演的是这么个情况：

  1. 1.

    请求 1 进来，加锁成功，0.2s 内执行业务并释放锁；

  2. 2.

    请求 2 稍微晚一点到，等它到的时候锁已经释放了，又加锁成功，又执行了一遍。

也就是说：只要两个请求没真正重叠在“锁持有期间”，它们就会被视为两次合法操作。

在不少业务里，这是可以接受的（比如抢接口、配置变更类操作）； 但像“支付回调、防止重复扣款”这类场景，你可能会想要更硬一点的约束，这时候就会考虑：

  • 除了锁，还在 Redis 里建一条标记，例如：

    textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                    
    SET key 1 NX EX 5

    • 第一次能成功 set，后面的在过期时间内都失败；

    • 就算上一个请求瞬间结束，这个标记也能挡住一段时间的重复。

所以最后想表达的是：

分布式锁是一种手段，不是银弹。不同业务对“重复”的定义不一样，要结合具体场景看是用锁、用 Redis Key 标记、还是干脆业务上做“幂等校验”。

优惠券模板操作库存

1. 并发增加发行量，会不会把库存加乱？

接口逻辑是这样的：

textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                
UPDATE t_coupon_template
SET stock = stock + #{number}
WHERE shop_number = #{shopNumber}
  AND id = #{couponTemplateId}

很多人第一反应是：

万一张三、李四同时操作同一个模板，都会在原来 10 的基础上加 10，会不会最后只变成 20，而不是 30？

这个担心其实是把“读出来再 +10 回写”和“在 SQL 里直接 +10”混一起了。

这里我们用的是原地自增：stock = stock + ?，加上 MySQL 的行级排他锁，行为其实是这样的：

  • 第一个线程拿到这行的锁，执行 stock = 10 + 10 -> 20，提交；

  • 第二个线程会在 UPDATE 时 阻塞，等前一个提交后，再以最新的 stock 做加法：20 + 10 -> 30；

  • 所以最终落库的值是 30，而不是 20。

只要你让更新逻辑尽可能在一条 SQL 里完成，再配合 MySQL 默认的行锁机制，并发更新不会像“先查再改”那样容易踩坑。

优惠券模板 RocketMQ 定时到期

1. 定时任务不也能做吗？为啥还要上 RocketMQ？

两个方案都能做成，但侧重点不一样：

  • 定时任务/XXL-Job 更像是扫库型：隔一段时间去查“哪些券已经过期但还没关”，然后批量处理。数据量大了以后，扫库这件事本身就会给 DB 造成压力，还得考虑分片、并发、补偿之类的问题。

  • RocketMQ 定时消息更像是提前约好闹钟：创建模板的时候，就把「这张券在 X 时间点要关闭」这件事交给 MQ，到了时间 MQ 把消息推给你，你只要按消息把状态改掉就行了。

对于“优惠券模板有一个明确的失效时间”这种业务场景，MQ 定时消息刚好对上：

  • 精度够，按毫秒时间戳直接丢；

  • 不用自己维护一堆扫描任务；

  • 跟已有的异步链路也比较契合。

后面你再讲 XXL-Job，可以当做是另一种思路：一个偏“批处理”，一个偏“事件驱动”，都对，只是适用场景不一样。

2. RocketMQ 5.x 的任意延时消息，跟以前的固定延时等级比，体验差别在哪里？

早期版本是“档位制延迟”，比如只支持：

1s、5s、10s、30s、1min、2min、5min、10min…

你的业务如果刚好要在 2025-12-01 20:00:07 执行，就会比较别扭：不是提前很多，就是晚一点，只能折中。

5.x 之后支持“任意时间戳”，你在代码里直接用优惠券的失效时间：

textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                
Long deliverTimeStamp = couponTemplateDO.getValidEndTime().getTime();
rocketMQTemplate.syncSendDeliverTimeMills(topic, message, deliverTimeStamp);

简单理解：

  • 以前是「你去迁就 RocketMQ 的固定档位」；

  • 现在是「RocketMQ 配合你的业务时间点」，哪个毫秒触发都可以。

对于优惠券到期关闭、订单超时关闭这类精确到具体时间点的需求，5.x 的任意延时体验会好很多。

3. 延时关闭优惠券，消费者需要幂等处理吗？

这里的操作是把状态改成“已结束”，多次执行结果是一样的。即使同一条消息被重复投递几次，最终状态都还是 ENDED，不会出现“扣多次库存”这种问题，所以不做复杂幂等也没关系。

EasyExcel 解析百万 Excel 批量分发

1. 为什么优惠券分发是通过 Excel 进行的？

这背后其实有一些背景需要先了解，首先是 Excel 中的用户数据是怎么来的。

我们日常在淘宝、京东等大型电商平台上浏览或购买商品时，都会被埋点采集数据。这些埋点可以精确到你点击了哪个商品、浏览了多长时间、访问了几次店铺等。这些行为数据会被汇总到用户画像系统中（不同公司可能叫法不同），用于识别潜在意向客户。基于这些画像，平台运营人员可以有针对性地进行优惠券投放或发送营销短信。

针对如何将优惠券分发给这些潜在客户，通常有两种模式：

  1. 1.

    Excel 导出模式：运营人员根据需求向画像平台提报，画像平台返回一个符合条件的用户列表（Excel 文件）。然后，平台通过内部运营系统，选择优惠券并将其分发给 Excel 中的用户。

  2. 2.

    标签查询模式：运营人员向画像平台提需求，画像平台将用户打上统一标识。平台根据这个标识，在分发时结合优惠券执行用户发放。

在实际企业中，这两种方案都存在，且各有适用场景。

我们当前的方案采用的是第一种 Excel 导入模式，原因也很简单：我们并没有真正接入用户画像平台，因此通过模拟生成 Excel 数据的方式，更容易实现并演示整个分发流程。

如果在面试中有面试官对此提出质疑，也可以补充说明第二种标签模式的实现逻辑，大部分人其实都能理解和认可。

例如，如果我们要上线一家高端服装店，为了提升其生意，我们可以从意向客户中提取长期浏览高端服装或已经购买过类似品牌或价位的用户信息，然后将优惠券和通知发送到这些用户的账户。这样可以精准地锁定潜在客户，提高营销效果。

“我把整个 Excel 读成一个 List，给你，你爱怎么用怎么用。”

而 EasyExcel 的监听器模式更像是：

“我一行一行读，每读到一行就回调给你，你处理完我就可以把这一行扔掉了。”

你这次的实现非常克制：

public class RowCountListener extends AnalysisEventListener<Object> {
​

    private int rowCount = 0;
​

    }
}

  • 每读到一行，只做 rowCount++；

  • 不把整行数据存到内存里；

  • 读完马上释放，内存自然就下来了。

所以可以这么跟同学解释： EasyExcel 真正帮你的地方不止是“API 好看”，而是它天然支持“边读边处理”，不用你自己写底层流式解析逻辑，就避免了大文件 OOM 的坑。

3. 分发接口中统计 Excel 行数有什么意义？

两个点都挺实用：

  1. 1.

    任务规模预览

    • 管理后台展示“本次任务计划发放 X 人”，运营同学心里就有个数；

    • 配合状态和时间，也能大概判断这个任务会跑多久、是否需要拆批。

  2. 2.

    数据完整性校验（可扩展）

    • 理论上，Excel 行数 = 成功发放数 + 失败数；

    • 如果你后续在任务执行完之后补一段校验逻辑，就能自动发现“漏处理”的情况：

      • 比如中途挂了一个节点；

      • 或某个分片没跑完；

    • 先把“行数”写进库里，后续要做这种校验就有基础数据了。

简单说： 行数本身不是目标，但“有这个全量基数”之后，很多后续能力才有落脚点。

线程池和延时队列优化接口响应

1. 为什么要把 Excel 行数统计异步化？

百万行 Excel，用 EasyExcel 数一遍行，差不多要 4～5 秒。

在后管系统里，这就会有几个问题：

  1. 1.

    接口响应太慢

    • 创建优惠券任务的接口，本质只是“登记一个任务 + 做些基础校验”；

    • 用户点一下按钮，要傻等 5 秒才看到“创建成功”，体验会很割裂。

  2. 2.

    链路上耦合太重

    • 行数统计只是个“增强信息”，是为了后续做进度、校验用；

    • 不值得把整个创建任务流程都绑在这个耗时步骤上。

所以做法就变成：

  • 接口里只做：参数校验 + 任务入库，马上返回成功；

  • 行数统计这类耗时活，丢给线程池后台慢慢跑；

  • 真正的瓶颈从“用户等待时间”挪到了“后台异步任务”，对体验影响就小很多了。

一句话：行数一定要算，但没必要绑死在接口响应时间上。

2. 如何设置线程池参数？为啥不用 Executors.newFixedThreadPool 这种快捷方式？

这块主要是两层考虑：

  1. 1.

    场景本身决定了配置范围

    • 属于后台管理任务，调用频率不会像前台接口那样高；

    • Excel 解析是 IO + 一点点计算的混合型任务，所以：

      • corePoolSize = CPU 核数：正常情况下就够用了；

      • maximumPoolSize = 核数 * 2：偶尔高峰来了，可以多开一点线程兜一兜；

      • workQueue = SynchronousQueue：不排队，来了就立刻交给线程执行，要么新建线程，要么走拒绝策略。

  2. 2.

    为什么不用 Executors 快捷方法

    • newFixedThreadPool / newSingleThreadExecutor：底层是无界队列，任务堆多了直接把内存撑爆；

    • newCachedThreadPool：线程数量理论上无限创建，高并发下可能把系统拖跨；

    • 简单就是：方便是方便，但默认参数太“乐观”，一旦遇到大任务就容易翻车。

线程数有限，队列不堆积，超出直接丢弃（但有 Redis 延时队列兜底）。

3. 为什么这里还要用 Redis 延时队列？能不能用 RocketMQ？

这块主要是“环境现实”问题，而不是技术优劣：

  • 理论上，用消息队列做异步 + 延时，是更标准的做法：

    • 持久化能力更强；

    • 消费模型更丰富；

    • 重试、堆积、监控都更专业。

  • 但在实际项目里常见情况是：

    • 有的项目本身就没接入 MQ，引入一套 RocketMQ/Kafka 成本不低；

    • 或者 MQ 主要留给“强一致、强可靠”的业务，这种“统计 Excel 行数”的辅助任务就不一定值得占坑。

所以这里的定位是：

线程池 = 主力，Redis 延时队列 = 兜底辅助。

  • Redis 本身定位还是缓存，持久化和主从同步都有丢数据的可能；

  • 但“统计行数”这件事，属于可补偿、可人工处理的类型，用 Redis 做兜底完全够用；

  • 真正强一致的发券流水，还会在后面的核心链路里通过 MQ 或事务做保障。

在复盘/面试时可以这么讲：有 MQ 就尽量用 MQ 做主通路，没有的话，线程池 + Redis 延时队列是一套性价比很高的过渡方案。

4. Redis 延时队列这套兜底方案，还有哪些边界和注意点？

这块虽然只是兜底，但有几个点可以心里有数：

  1. 1.

    Redis 本身不保证 100% 不丢

    • AOF/persistence 都是异步写盘，极端情况下可能丢一条；

    • 主从切换也可能丢部分尚未同步的写；

    • 所以文中强调：Redis 只是兜底，真的失败了可以人工补。

  2. 2.

    消费者线程是单线程死循环

    • 用 Executors.newSingleThreadExecutor 起了个守护线程，一直 take()；

    • 命名成 delay_coupon-task_send-num_consumer，方便线上排查；

    • 逻辑很简单：取一条 -> 查 DB -> 决定要不要执行 refreshCouponTaskSendNum。

如果未来这块要升级成更通用的“延时任务中心”，Redis 这套思路也能直接迁移到 RocketMQ 的延时消息或专门的延时队列组件上。

模板方法重构消息队列发送接口

1. 为什么还要引入模板方法模式重构？

直接在业务里写 MQ 发送，一开始确实挺爽，但时间一长问题会越来越明显：

  • 每个业务类都在手写一遍类似的逻辑：解析 Topic、拼 destination、构建 Message、设置 Keys、调用 syncSend、打日志、try-catch……

  • 想统一一点点东西，比如：

    • 日志格式统一（事件名、Keys、MsgId 要一样）；

    • 超时时间、是否用延时消息的策略；

    • 发送失败时的兜底处理方式。

就会发现改一次得满项目搜一遍，特别容易漏。

这次用模板方法模式做抽象，实际上就两个核心收益：

  1. 1.

    共性逻辑上收：Topic 拼接、是否延时消息的判断、统一日志输出、异常包装等，都放到了 AbstractCommonSendProduceTemplate 的 sendMessage() 里，业务不用重复写。

  2. 2.

    个性逻辑下沉：每个业务只管实现两个抽象方法：

    • buildBaseSendExtendParam()：这个事件叫什么名、发到哪个 Topic、要不要延时、超时时间多少；

    • buildMessage()：消息体长啥样、Keys 放哪、Tag 要不要。

最终在业务里就变成一句：

2. 模板方法模式和策略模式、工厂模式这些比起来，这里为什么更适合用模板方法？

从这次场景来看，有几个特点：

  1. 1.

    整体流程是稳定的：不管是优惠券分发、模板延时关闭，还是以后别的消息，发送流程其实都一样：

    1. 1.

      准备扩展参数；

    2. 2.

      构建 destination；

    3. 3.

      根据是否延时选择不同的 RocketMQ API；

    4. 4.

      打统一日志。这就是典型的“算法骨架固定、少数步骤可变”。

  2. 2.

    变化点很集中，且数量不多：可变的只有两块：

    • 这条消息的“配置”：事件名、Topic/Tag、Keys、超时时间、延时参数；

    • 这条消息的“内容”：payload 怎么组织、header 里要塞什么。

这种情况下，模板方法模式非常对口：父类给出流程，子类负责把几个关键步骤实现掉。

如果强行上策略模式，通常会变成：

  • 一个 SendMessageStrategy 接口；

  • N 个策略类里既包含“构建 Message”的逻辑，又自己调用 rocketMQTemplate；

  • 最后还是会出现大量重复的 try-catch + 日志打印。

而工厂模式更适合“我要创建哪种 Producer/Client”，不是很适合描述“同一个发送动作的内部步骤”。所以综合下来，模板方法是这里最自然的选择。

优惠券模板缓存击穿/穿透场景

1. 为什么一定要给模板查询加缓存？用数据库硬扛不行吗？

从业务上看，优惠券模板这种东西有几个特点：

  • 被访问得非常频繁，尤其是大促、活动页、领券中心这种场景；

  • 单次查询的逻辑并不复杂，更多是读多写少；

  • 对响应时间很敏感，用户点开券中心或者下单页，几百毫秒和几十毫秒的体验完全不一样。

如果这种查询完全落在数据库上，高峰时有几个问题：

  • 所有请求都打到数据库上，容易把核心库的连接数、IO 撑爆；

  • 即便扛得住，数据库层面也很难做到毫秒级响应；

  • 一旦数据库抖一下（慢查询 / 抢锁 / 备份），前台页面体验会非常差。

而优惠券模板本身又是很适合缓存的：

  • 数据体积不算大；

  • 一个模板会被大量用户重复访问；

  • 有明确的有效期，可以用过期时间驱动缓存失效。

所以在牛券这种项目里，模板查询是天然的“热点读接口”，正确姿势就是：落缓存 + 做好缓存击穿 / 穿透防护，数据库只承担兜底与刷新职责。

2. 缓存击穿在优惠券查询这里具体是怎么发生的？

以优惠券模板为例，典型的缓存击穿场景是这样的：

  • 某个热门优惠券模板，活动期间有大量用户在访问，对应的 Key 是热点 Key；

  • 这个 Key 在 Redis 里刚好过期了，或者还没来得及预热进缓存；

  • 此时有一波并发请求同时查询这个模板，发现缓存都 miss，于是一起打到数据库上；

  • 数据库瞬间被一个热点模板的请求压垮，这就是缓存击穿。

和缓存穿透、雪崩两个概念的区别可以简单记一下：

  • 缓存穿透：请求的就是数据库中本来就不存在的数据，缓存再怎么加也命不中，请求直接打穿到 DB；

  • 缓存击穿：某一个热点 Key 在某个点上突然失效，大量请求集中去查这一条；

  • 缓存雪崩：一大片 Key 在同一时间段内集中失效，比如大批数据同一时间过期，导致大量不同的请求都回源数据库。

3. 为什么解决缓存击穿时，要用“双重判定锁”？只加分布式锁不就够了吗？

只加锁而不做双重判定，看起来是线程安全了，实际上会浪费很多资源。

不做双重判定的逻辑大概是：

  1. 1.

    线程 A 查询缓存发现没有，拿锁，查 DB，回写缓存；

  2. 2.

    线程 B、C、D… 也都查询缓存发现没有，排队拿锁；

  3. 3.

    A 释放锁后，B 拿到锁，再次查 DB + 回写缓存；

  4. 4.

    C、D 依然重复这一套。

理论上，只有第一个请求把 DB 数据加载进缓存就够了，后面的请求再去查 DB 属于“重复劳动”。

加了双重判定锁之后，流程会变成：

  1. 1.

    线程 A 查缓存无 -> 拿锁 -> 再查一次缓存仍无 -> 查 DB + 回写缓存；

  2. 2.

    线程 B 等待 A 释放锁 -> 拿到锁 -> 再查缓存，此时已有数据，直接返回，不再访问 DB。

双重判定的好处：

  • 在高并发场景下，大部分线程只是等待+读缓存，不会重复查 DB；

  • 能把数据库压力压到最低，真正有意义的查询只有“第一个拿锁的线程”。

在优惠券模板查询里，这一套直接落到了 findCouponTemplate 的实现里：先读 Redis Hash，不存在再拿 Redisson 的锁，再读一次 Hash，确定真的没有才查数据库并用 Lua 一次性写入 Hash + 过期时间。

4. 高并发极端情况下，双重判定锁有什么隐患？tryLock 和“分片锁”是怎么缓解的？

双重判定锁解决的是“重复查 DB”的问题，但在极端高并发下，还有一个坑：请求等待时间过长。

比如有 1 万个请求在同时查同一个模板：

  • 第一个线程拿锁，查 DB、写缓存，假设耗时 50ms；

  • 后面 9999 个线程都在 lock() 那里排队，最后一个线程要等上 9999 * 若干 ms，整体等待时间可能过 10 秒；

  • 应用层面大量线程阻塞在锁等待上，容易拖垮整个 JVM，甚至触发 OOM。

这时候可以考虑两种手段：

  1. 1.

    tryLock 快速失败 不排队抢锁，拿不到直接返回，比如：

    • 提示用户“当前访问人数较多，请稍后重试”；

    • 或者前端做个兜底文案 / 降级展示。

    好处是保护了服务端，不会因为锁排队把线程池塞满；缺点是用户体验会差一点，适合“可以重试、不影响核心流程”的接口。

  2. 2.

    分布式锁分片 思路是“不是所有请求都去抢同一把锁”，例如：

    • 对用户 id 取模，拆成 10 个锁 Key：coupon_template_lock:{templateId}:{idx}；

    • 同一时间可以有 10 个线程并行执行“双重判定 + 查 DB + 回写缓存”这段逻辑；

    • 热点非常高的时候，可以显著缩短整体等待时间。

在牛券这个项目里，模板查询本身不会到那种“秒杀”级别的极端 QPS，所以课程里主要是把这些手段当做思路讲清楚，实际落地时通常“双重判定锁 + 合理的限流 + 监控”就够用了。

5. 为什么解决穿透时要“布隆过滤器 + 空值缓存 + 分布式锁”一起上？

缓存穿透的问题是：请求的数据本身在数据库里就不存在，你再怎么查缓存都命不中，结果是每次都回源 DB。

单看三种方案，各有缺点：

  • 只用布隆过滤器： 能挡住绝大部分“明显不存在”的 Key，但布隆过滤器有误判率，遇到命中误判的 Key，还是会一路打到数据库。

  • 只缓存空值： 每次 DB 查不到就写一个“空标记”，下次直接从缓存判断。但如果有人恶意打很多不存在的 Key，你的 Redis 里会堆一堆“无意义空值”，占内存非常快。

  • 只靠分布式锁： 在穿透场景里，大家查的 Key 本来就都是不存在的，只靠锁会变成“高并发 + 全是浪费”，数据库压力依旧很大。

所以组合方案的逻辑是：

  1. 1.

    先用布隆过滤器挡掉大部分“根本不可能存在”的 Key；

  2. 2.

    过了布隆过滤器，再看是否命中“空值缓存”，命中就直接返回，不查 DB；

  3. 3.

    还没命中空值时，再用分布式锁把同一个 Key 的请求拦成一个，避免多线程一起查 DB；

  4. 4.

    查 DB 仍然不存在时，写一份空值缓存（短过期），后续请求直接短路。

这样三者结合起来，可以同时解决：

  • “绝大部分无效 Key 一步挡掉”（布隆）；

  • “短期内反复查同一个不存在 Key”（空值）；

  • “同一个 Key 的高并发挤在一个时间点上”（锁）。

在优惠券模板查询的最终版本里，你能看到完整的组合：

  • 先过 couponTemplateQueryBloomFilter.contains；

  • 再查 *_IS_NULL 这种空值 Key；

  • 再拿锁 + 双重判定；

  • 最后根据查库结果，要么写 Hash，要么写空值缓存。

6. 布隆过滤器如何预估数据规模？

布隆过滤器初始化时有两个核心参数：

  • expectedInsertions 预期插入数量；

  • falseProbability 允许的误判率。

项目里的 tryInit(640L, 0.001) 这一组只是示例，表达的意思是：

  • 当前场景下预估不会有特别离谱的优惠券模板数量，比如几百、几千个模板；

  • 允许的误判率是千分之一，也就是 1000 次里最多有一次“把本来不存在的 ID 误判为存在”。

真实项目里要考虑两件事：

  1. 1.

    业务量级：

    1. 1.

      如果你知道模板上限，比如“一个商家最多 1 万模板，平台总共几百商家”，那可以算一下预估总量，然后适当放一点余量；

    2. 2.

      粗暴一点就是：预估上限 * 2 或 * 3，不要卡死。

  2. 2.

    内存上限：布隆过滤器底层是 bit 数组，容量越大，占用内存越多，而且 Redisson 这种是初始化时一次性申请内存的。

    1. 1.

      比如：1 亿元素、误判率千分之一，大概需要 170M 内存，这个可以接受；

    2. 2.

      但你如果上来就配 30 亿，还要很低误判率，Redisson 直接给你报错，连初始化都过不了。

所以面对几十亿级的量级，一般做法和之前锁分片类似：分片布隆过滤器。

  • 把 30 亿划分成多个 Bloom 实例，比如 30 份，每份 1 亿；

  • 对模板 ID 做 hash 或取模，决定落到哪一个 Bloom 上；

  • 插入和查询都先算分片，再操作对应的 Bloom。

这样单个布隆的容量和内存都能控制住，同时整体逻辑还是统一的。

7. 为什么最终选的是 volatile-lfu 做 Redis 内存淘汰策略？

这里要同时考虑两个前提：

  1. 1.

    我们对部分 Key 做了“永不过期 + 预热”，比如大促期间的热点优惠券模板；

  2. 2.

    击穿防护方案是基于“热点 Key 尽量不要被 Redis 自己淘汰”的假设来设计的。

如果选错了淘汰策略，就有可能出现：

  • 你精心预热的热点 Key，被 Redis 的内存淘汰机制随机淘掉了；

  • 然后在一个峰值时刻，这个 Key 又突然被大量访问，等于自己制造了一次缓存击穿。

所有策略里，allkeys-* 这几种都存在这种风险：

  • allkeys-random：直接随机淘，热 Key 也会被干掉；

  • allkeys-lru / allkeys-lfu：理论上更偏向淘冷数据，但在某些时间窗口或异常访问行为下，热 Key 也可能中招。

而 volatile-* 这一组策略只会在“有过期时间的 Key”里做淘汰，对“永不过期的热点 Key”不下手，这就满足了我们对热点模板“尽量稳定”的要求。

在 volatile-* 里再选：

  • 为了避免 LRU 的“缓存污染”问题（一次性大批访问把真正的热点挤掉），更倾向于基于访问频率的 LFU；

  • 优惠券这种业务有很明显的冷热分布，LFU 更容易把真正没什么人用的模板淘掉。

所以在牛券里的选择是：volatile-lfu。

大体含义就是：只从设置了过期时间的 Key 里，淘那些访问频率比较低的，热点永不过期的 Key 尽量别动。

8. 什么是缓存污染？为什么说 LFU 比 LRU 更适合优惠券这类业务？

所谓缓存污染，大白话就是：一堆“路人数据”把真正有价值的热点数据挤出了缓存。

在 LRU 策略下，它只看“最近一次访问时间”。比如：

  • 你平时有一个真正热门的优惠券模板，一直都在被访问；

  • 某一天你跑一个批量任务，把很多“平时没人看的模板”都扫了一遍；

  • 这些冷数据突然都有了“最近访问时间”，在 LRU 眼里它们都“挺新鲜”；

  • 真正的热 Key 反而因为这一波冲击，被淘汰掉了，后面业务访问又变回查 DB + 写缓存。

这个场景在后端很常见：大批量导出、一次性导数、扫描任务等等，都可能短时间访问大量“不常用”的 Key。

LFU 看的是“访问频率”，而不是“最近一次访问时间”：

  • 真正的热点优惠券模板，一天之内被访问上万次，它的频率计数会一直很可观；

  • 那些偶尔被扫一次的冷 Key，即便最近刚刚访问过，频率也很低；

  • 淘汰时优先干掉这些低频数据，热点数据能持续留在缓存里。

对于有明显热区的业务（典型就是营销、券、活动、推荐），LFU 通常更合适，配合前面说的 volatile-lfu，可以在保障热点稳定的前提下，把有限的内存尽量留给“真的有人用的 Key”。

9. 怎么防止优惠券查询把数据库打挂的？

可以按“一个链路 + 三个问题”来讲：

  1. 1.

    先说业务场景

    • 优惠券模板是高频读接口，大促场景下 QPS 很高；

    • 直接查数据库扛不住，所以必须先落缓存。

  2. 2.

    然后分三块问题讲方案

    • 缓存击穿：

      • 热点模板用预热 + 永不过期处理；

      • 常规查询用 Redis Hash 缓存 + Redisson 分布式锁；

      • 锁里做双重判定，只有第一个拿锁的线程会查 DB，其它线程直接读缓存；

      • 极端高并发场景可以通过 tryLock 和锁分片进一步降低阻塞时间。

    • 缓存穿透：

      • 入口先做参数校验；

      • 布隆过滤器兜一层，不在集合里的 ID 直接拒绝；

      • 过滤后再查 Redis，如果是空值 Key，直接返回“模板不存在”；

      • 真的没缓存时，通过分布式锁 + 双重判定查 DB，查不到就写入空值缓存（短 TTL）。

    • 内存淘汰：

      • Redis 侧配置 maxmemory-policy=volatile-lfu；

      • 只在设置过期时间的 Key 中淘汰访问频率低的，永不过期的热点模板不轻易被赶出缓存；

      • 再配合监控和容量评估，确保热点 Key 稳定可用。

  3. 3.

    最后补一句整体效果

    • 在这套组合方案下，大部分请求都在 Redis 命中；

    • 即便遇到异常流量，对数据库的冲击也被锁和 Bloom Filter 抵挡住；

    • 真正打到 DB 的只会是极少数“首查 + 失效刷新”的请求。

这样一通说下来，面试官一般就能听出你不是只会喊“用布隆过滤器 + 分布式锁”，而是真的把“击穿 / 穿透 / 淘汰策略”和业务场景串到一块了。

优惠券 Excel 批量分发

1. Excel 驱动的优惠券分发整体流程是怎样的？

整体可以理解成「三段式」：

  1. 1.

    配置与准备阶段

    • 先在后管里创建优惠券模板，配好来源、库存、有效期、使用门槛等信息。

    • 通过单元测试或运营后台导出分发 Excel，里面主要就是用户 ID 列，测试时可以控制在几千条，线上可以到几十万甚至百万。

    • 创建一条优惠券分发任务，填上 Excel 的文件路径、关联的优惠券模板 ID、发送方式（立即 / 定时），任务信息会落到数据库，同时推一条延时消息到 RocketMQ。

  2. 2.

    v1 / v2 的分发执行阶段

    • RocketMQ 到点后，CouponTaskExecuteConsumer 消费到任务执行事件，先校验任务状态是不是「执行中」、优惠券模板是否「生效中」、库存是否合理。

    • 然后用 EasyExcel 按行读取分发 Excel，每一行代表一个待发券的用户，结合模板信息执行「校验 + 发券」逻辑。

    • v1 版本里，读到一行就立刻：扣缓存库存 → 扣数据库库存 → 写用户优惠券表 → 写用户领券列表缓存；

    • v2 版本开始，读 Excel 只负责把用户放进 Redis 集合，批量攒够一批再用 MQ 触发真正的「写库 + 写缓存」。

  3. 3.

    结果落地与任务收尾

    • 发券成功的用户会写入分库分表的 t_user_coupon_xx 中，并追加到对应用户的 Redis ZSet 里，ZSet 的 score 用领券时间，后续查询可以按时间倒序。

    • 发券失败（库存不足 / 已领过券）的记录，会写到 t_coupon_task_fail 表，后面可以按批次导出 Excel 给运营。

    • 当 Excel 全部扫完，且 Redis 中待处理的用户集合也被消费干净之后，分发任务状态会更新为 SUCCESS，填上完成时间，整个任务才算真正结束。

2. 用户优惠券表为什么要做分库分表？分片规则是怎么设计的？

用户优惠券属于那种天然会「长胖」的表： 用户多、营销活动多、每次活动又是成批地发券，不做分库分表，很快就会到单表几亿行。

这篇文章里有几个考虑点：

  • 数据量级预估：优惠券模板本身的数量是可以估的，但用户领券记录基本是「只增不减」，又配合各种渠道投放，很难准确估。干脆一开始就把 t_user_coupon 拆成 2 个库 * 32 张表，尽量把单表控制在亿级以内。

  • 分片键的选择：用户维度的场景通常围绕 userId 查，比如「查某个用户有哪些券」「某个用户的领券记录」。 所以分片键选 user_id，分片算法是简单的 Hash 取模：

    • 分库：user_id 做 mod 落到 ds_0 或 ds_1

    • 分表：user_id 再做 mod 落到 t_user_coupon_0 ~ t_user_coupon_31

  • 索引设计：表上有一个联合唯一索引 user_id + coupon_template_id + receive_count，用来控制「同一优惠券第 N 次领取」这种语义。

    • 业务上这列 receive_count 既是数据字段，也是限领规则的一部分。

    • 插入时如果违反唯一约束，直接通过异常知道用户已经领过，省掉一次额外查询。

整体下来，这套分片方案对准的就是两个目标：一是横向扩容空间够大，后面数据量再上来也不用立刻重构；二是按用户维度查时，不需要跨库跨表全扫。

3. v1 版本的优惠券分发逻辑主要有哪些问题？

v1 版本的逻辑从功能上是没问题的，但放到稍微大一点的量级上，就会暴露几个明显短板：

  • 单条处理太重 每读一行 Excel 都要做一整套动作：

    • Redis 扣一次库存

    • MySQL 扣一次库存

    • 插一条 t_user_coupon

    • 往 Redis ZSet 里加一条用户领券记录 5000 行就意味着几万次网络 I/O，CPU 大部分时间其实都在等网络。

  • 消息消费时间过长 Excel 一次性读完、发完，全都绑在一条 RocketMQ 消费里。 如果文件大一点、网络抖一抖，很容易让消费时间拉得很长，Broker 眼里看上去就像是「超时消费」，开始重投，等于给自己挖坑。

  • 失败场景不够细致 v1 对失败的处理比较粗：

    • 唯一索引冲突就 catch 掉直接 return，相当于静默忽略

    • 库存不足的情况也是简单 return 对运营来说，只能看到「有些人没收到券」，看不到到底是库存问题还是本来就领过。

  • 无法从中间点恢复 如果消费到一半应用挂了，消息重试会从头开始处理，之前成功的人还会再走一遍逻辑。 虽然靠唯一索引能挡一下重复插入，但整体来说既浪费时间，也不够优雅。

所以 v1 更像是「能跑通流程的版本」，而不是能扛住高并发、可观测性好的工程版本。

4. v2 为什么能把 5000 条记录的执行时间从 1 分钟压到 1 秒左右？

核心原因就一句话：所有会打网络的操作，能攒一起就绝不一条条调。

具体做了几件事：

  • Excel 读取阶段只做「攒人」 ReadExcelDistributionListener 在 v2 里不再直接插库，而是：

    • 用 Lua 脚本在 Redis 里做「扣库存 + 记录用户」这一整套逻辑；

    • 用户信息存到一个 Set 里，里面是 {"userId":xxx,"rowNum":yyy} 这种 JSON；

    • 当集合大小达到 5000，就发一条「批次就绪」的消息给下游消费者。

    这样读取 Excel 的那条消费，变成「纯内存 + 少数 Redis 调用」，极快。

  • 批量扣库存 + 批量插用户券 CouponExecuteDistributionConsumer 收到消息后，才会真正：

    • 用一条 SQL 扣减模板库存 stock = stock - N；

    • 从 Redis Set 里一次性 pop N 条用户记录出来，拼成 List<UserCouponDO>；

    • 用 MyBatis-Plus 自带的批量插入一次性写入。

    网络 I/O 的次数从「每人一次」变成了「每 5000 人一次」，性能差异非常明显。

  • 发券结果同步到缓存也走 Lua 批量 给用户追加领券记录时，同样是把一批用户的 ID 和券 ID 序列化成 JSON，交给 Lua 脚本在 Redis 里批量处理，避免在 Java 侧狂发单条命令。

  • 进度点位 + 宕机恢复 每读完一行 Excel，就把当前行号刷到 Redis，重试的时候直接从上次停的地方接着走，避免重复跑一遍前面的流程。

这些优化叠加起来，同样 5000 条记录，从「很多次网络往返」压成「少量几次」，1 分钟降到 1 秒就不奇怪了。

5. 为什么要把消息队列拆成两个消费者，而不是一个里全干完？

从业务上看，一个消费者里「读 Excel + 校验模板 + 扣库存 + 插库 + 写缓存」也能干完，拆分确实多了点工程工作量。但拆完之后有几个明显好处：

  • 消费时长可控

    • CouponTaskExecuteConsumer 只负责读 Excel 和做前置校验，逻辑非常轻，不会因为单个任务太大拖垮整个集群的消费进度；

    • 真正「重活」集中在 CouponExecuteDistributionConsumer，而且它的是批量执行，可以根据情况增加消费者数量、水平扩展。

  • 职责边界清晰 一个专注「解析任务 & 投递批次」，一个专注「批次落库 & 写缓存」，出问题时排查思路会清晰很多。

  • 适配顺序消息 最终「Excel 读取完毕」那条消息必须在所有「批次分发」消息之后消费，否则会有状态错乱的风险。 通过拆 topic + 按分发任务 ID 做 Hash 投递到同一队列，可以比较轻松地做到「单任务内顺序，任务之间并行」。

  • 后续扩展余地 如果后面想支持「重放某个批次」「单独重试某个批次」，现在这个拆分就很好做，几乎不用碰 Excel 解析那块逻辑。

所以不是「一个消费者做不到」，而是拆开之后整个系统的可维护性、可观测性和扩展性都更好。

6. Lua 脚本在整个方案里到底解决了什么问题？

Lua 脚本主要解决两类问题：原子性和网络 I/O 次数。

  1. 1.

    原子性问题 在 Redis 里，如果用多条命令完成一件事，比如：

    • 先 HGET stock 看库存够不够；

    • 再 HINCRBY stock -1 扣库存；

    • 再 SADD 把用户加进 Set； 中间任何一步被其他请求插队，都可能产生竞态。

    换成 Lua 后，这些逻辑在 Redis 侧一次性执行完，要么都成功，要么都失败，对库存这种敏感数据来说安全很多。

  2. 2.

    减少网络往返 原来一行 Excel 可能要发 3～4 条命令到 Redis，现在变成「单条 EVAL 调 Lua」，网络往返延迟直接砍几刀。

  3. 3.

    小技巧：用位运算「一条 Long 带两段信息」 这个地方更多是玩了一下：

    • 脚本既要告诉 Java「本次扣库存是否成功」，又要告诉你「当前用户集合的大小」，正常写法是返回一个结构或字符串自己切；

    • 这里改成：用高位存布尔值，低位存集合大小；

    • Java 这边用一个工具类按位还原两个值，性能比字符串 split 要好不少。

说白了，Lua 不是必须的，但它很适合「需要在 Redis 里做一点小逻辑，又不想来回打太多网络」的场景，这个分发流程刚好很适配。

7. 发券过程中，如何保证宕机重启后可以从上次进度继续？

这里的思路很简单：用 Redis 记录「Excel 已经读到第几行」，并且严格只递增不回退。

大致有两段逻辑：

  • 读取前先看进度 在 ReadExcelDistributionListener#invoke 的开头，每次读到一行，先去 Redis 里拿这次分发任务对应的进度值：

    • 如果缓存里是空的，说明还没记录过，正常处理；

    • 如果缓存里有值，并且已经大于等于当前 rowCount，说明这一行在之前的某次执行里已经处理过了，直接跳过自增 rowCount。

  • 读取后立刻写进度 当一行真正处理完（不管是成功入批次，还是因为库存不足记到失败表），都会把当前 rowCount 写回 Redis。 下一次从 MQ 重试时，读 Excel 还是从头读，但所有「行号小于等于进度值」的记录都会自动被 skip。

这种方式的好处是：

  • 不需要对 Excel 做复杂的「断点续传」，

  • 即便重试很多次，对数据库和缓存也几乎没有重复写入，

  • 开销只是每行多一次轻量级的 Redis set 操作，换来的是相对可靠的「幂等+续跑」能力。

8. 用户已经领过券或者库存不够时，是怎么记录失败原因并给前端看的？

这块的思路是：所有失败都落到一张单独的「失败记录表」，最后再导出成 Excel 给运营看。

具体有几个步骤：

  1. 1.

    建一张简单的失败表 t_coupon_task_fail 字段很克制：

    • batch_id：对应这次分发任务的批次号；

    • json_object：一段 JSON 文本，比如 {"rowNum": 94, "cause": "用户已领取该优惠券"}。 不试图把失败原因拆很多列，直接 JSON 存，后面导出时再解析。

  2. 2.

    两类典型失败场景

    • Excel 读取阶段库存就用完了： Lua脚本返回库存不足，监听器直接写一条 cause = 优惠券模板无库存。

    • 批量插库阶段发现有用户已领过券： 批量插入抛 BatchExecutorException 后，走单条插入，插入失败再查一次当前用户是否已领过这张券，如果是，就写一条 cause = 用户已领取该优惠券。

  3. 3.

    在分发任务结束时清理尾巴 当 distributionEndFlag = TRUE 的最终消息消费时，如果 Redis 里还残留了待发用户集合，说明这些人是「库存不够了，迟来的那批」，也会统一写入失败表，相应的 cause 为「优惠券模板库存不足」。

  4. 4.

    失败记录导出成 Excel 后续会有一个任务，把同一批次下的失败记录按分页从 DB 里捞出来，写到 Excel 文件，关联回优惠券分发任务。运营在后台点开就能直接下载，看到第几行失败、为什么失败。

这样做的好处是：

成功与失败走两条线，成功走业务主流程，失败集中到一个地方，既不影响主流程性能，也方便运营排查问题。

9. RocketMQ 的延时配置

分发任务是依赖 RocketMQ 的延时消息来「按计划执行」的，这里有两个细节要注意：

  • 最大延时时间的限制 默认的 timerMaxDelaySec 是 3600 * 24 * 3，也就是最长只能延时 3 天。 如果创建优惠券模板时，要求「N 天后自动开始分发」，而这个 N 超过 3 天，就会在发送消息时直接报错，broker 会返回类似：

    timer message illegal, the delay time should not be bigger than the max delay…

    公共云上的 RocketMQ 我这边已经把这个值调成了一年：

    textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                    
    timerMaxDelaySec = 31622400

    本地或自建环境的话，自己记得改一下；否则模板有效期和定时时间的校验逻辑就得限制在 3 天之内。

  • 延时消息和过期清理不会互相打架 RocketMQ 有一套「消息存储多久后清理」的配置，默认是 48 小时。 实际测下来，即便把清理时间调成 1 小时、延时时间设成 2 小时，延时消息依然能正常触达，这说明延时消息用的是一套特殊队列，不会被常规的过期策略直接清掉。

对业务同学来说，比较实用的点就是：

  • 要么调整 broker 配置，把 timerMaxDelaySec 放宽；

  • 要么在创建优惠券模板时就做校验，不允许「有效期开始时间」超过当前时间 + 最大延时上限。

10. 深分页问题是怎么暴露出来的？

深分页主要是出现在「查看某批次失败记录」这个场景里：

  • 正常情况下，失败记录不多，随手翻几页问题不大；

  • 但一旦 Excel 里大部分行都失败（比如库存完全没配对），t_coupon_task_fail 可能有几十万甚至几百万记录，这时如果还用 limit offset 的模式往后翻，性能就会急速下降。

在这篇文章里大致对比了几类方案：

  • 简单 offset 分页 limit (pageNo-1)*pageSize, pageSize，实现简单，但 offset 越大，数据库需要扫描的行数越多，后面几页会明显变慢。

  • 基于主键或时间的「大于某个值」分页 每次把当前页最后一条记录的主键 ID 或时间戳带回前端，下一页查询时则用：

    textjavascripttypescriptcsshtmlbashjsonmarkdownpythonjavaccpprubygorustphpsqlyaml Copy 
                    
    where id > lastId
order by id
limit pageSize

    这种通常被叫做「书签分页」或「游标分页」，在大表下性能非常稳定。

  • 配合缓存做书签记录（适合固定批次的浏览） 对于失败记录这种「一次分发、一批失败」的表，再引入分页的时候，可以把当前浏览的位置信息（比如最后一条的 ID）临时放在缓存里，前端只传一个轻量级的 token 上来，后端根据 token 解析出继续查的「游标」。

消息队列幂等消费

1. 为什么消息队列本身已经保证“不丢消息”，消费端还要做幂等？

消息队列像 RocketMQ、Kafka 一般只保证 “至少投递一次”（At Least Once），而不是 “恰好一次”。 只要消息没被标记为消费成功，Broker 就会不断重试投递，这就意味着：

  • 消费端重启、网络抖动、长 GC 等情况，都可能导致同一条消息被多次投递。

  • 对 MQ 来说，它只关心“最终一定要投递成功”，并不会关心你业务是不是被多次执行。

在很多业务里（比如发券、扣余额、扣库存），多执行一次和少执行一次一样致命：多发了券、重复扣了钱，都属于数据错乱。所以消息系统把“不丢消息”的责任兜住了，而“避免重复执行”的责任，就必须落在应用自己的幂等逻辑上，这也是为什么文档里一直强调“消费端必须自行实现幂等”。

2. 为什么这套方案要用 Redis + 消息去重表，而不是只用数据库？

核心考虑有几点：

  • 从性能角度：消息消费通常是高 QPS 的，尤其削峰、异步化之后，每条消息都访问数据库做幂等，会把 DB 压得很难受，而 Redis 在读写和并发控制上的性能更适合做高频的状态标记。

  • 从职责角度：

    • 数据库消息表更适合记录“业务状态”和历史，例如消费记录、调试排查日志。

    • Redis 更适合做短期、轻量的“并发控制 + 去重挡板”，比如：消费中 / 已消费。

  • 从实现复杂度：利用 Redis 的 SET NX PX 语义和 Lua 脚本，可以一条命令搞定“只抢一次 + 设置过期时间 + 取旧值”，逻辑简单、成本低。

所以设计大致是：消息表负责记录和兜底，Redis 幂等 Key 负责高性能挡板，两者配合起来既能保证性能，又能兼顾排查能力。

3. 为什么幂等状态要设置过期时间？2 分钟时间是怎么考虑的？

幂等状态如果不设置过期时间，一旦消费过程中出现“半途死机”的情况，就会出现：

  • 第一条消息刚标记为“消费中”，进程就挂了。

  • 之后所有相同消息再来，看到状态一直是“消费中”，就会不停延迟重试。

  • 最后既没真正消费成功，也没机会重新进入消费逻辑，最终都进死信队列。

为了避免这种“永远消费中”的僵尸状态，一般会给幂等 Key 加一个最长生存时间，比如：

  • 数据库消息表里：可以设置 10 分钟的“最长消费时限”，超时视为失败。

  • Redis 幂等 Key 里：根据具体业务选取更贴近实际的时间，例如文中使用 120 秒。

时间怎么选，大致看两个点：

  • 正常情况下，这类消息消费逻辑需要多长时间能跑完

  • 比较极端但不至于离谱的情况（如下游 RPC 慢一点）需要预留多少冗余

所以 2 分钟 / 10 分钟本质上只是经验值，你可以根据自己的业务链路耗时做调整，核心原则是：能覆盖绝大部分正常消费场景，又不至于把异常消息卡死太久。

4. 这套幂等方案是不是就能把重复消费的问题完全解决了？

不能算“完全解决”，更准确一点是：大部分“重复进入消费方法”的问题被解决了，但方法内部的业务逻辑还得自己兜住。

例如文中举的那种复杂流程：

  1. 1.

    检查库存（RPC）；

  2. 2.

    锁库存（RPC）；

  3. 3.

    开事务，插入订单；

  4. 4.

    调用下游服务；

  5. 5.

    更新订单状态；

  6. 6.

    提交事务。

即便有幂等挡板，如果在第 3 步插入订单时因为数据库异常失败了，消息会被重试：

  • 幂等 Key 会被删除，让重试时有机会重新进入消费逻辑。

  • 但是像“锁库存”这种操作，如果下游本身没有幂等或者补偿机制，就可能会被调用多次。

所以可以这么理解这套方案的定位：

  • 它可以解决 99% 的“消息重复投递 / 并发重复消费”问题。

  • 但无法替你把所有业务内部的副作用都变成幂等，这一层还是要依靠：

    • 下游接口的幂等设计。

    • 本地事务 + 唯一约束。

    • 或者单独的业务补偿方案。

5. 2 分钟幂等结束后，如果再来一条一模一样的请求怎么办

这个问题面试官比较爱问，理论上确实存在，但在实际业务里一般会拆开看：

  • 大部分 MQ 重投递的间隔和次数都比较集中，主要集中在业务执行的那几秒到几十秒内。

  • 两分钟都过去了，消息才再次出现，要么是非常极端的网络问题，要么就是上游又产生了一次同样的业务请求，这本身就属于 业务重复 了。

如果对方非要抠这个点，可以顺着往下讲两种思路：

  • 真要兜这种“长时间间隔的重复业务”，可以把幂等 Key 持久化在 MySQL 里，做分表存储，保留 7 天甚至 30 天也没问题，再通过定时任务清理过期数据。

  • 但是要看业务的性价比：很多场景里，这种“隔了几分钟还再来一模一样请求”的概率很低，往往只需要在关键链路做一点额外兜底就可以了。

简单说就是：短期幂等靠 Redis，长期幂等看业务需求决定要不要上数据库。

秒杀优惠券功能

1. 优惠券秒杀和普通“领券接口”相比，最大的差别在哪里？

普通领券场景下，基本就是做几件事情：校验模板是否存在、校验活动时间、扣一条库存、插一条用户领券记录，整体并发量一般也不算夸张，更多是“正确性”优先。

秒杀场景不一样，一旦发的是大额券或者热门券，流量会在短时间内集中冲击过来，系统要同时面对三件事：

  • 顶住瞬时高并发，不能一窝蜂全打到数据库上；

  • 控制库存，不允许超卖；

  • 控制单用户限领次数，不能超领。

所以在这套实现里，前置用了 Redis + Lua 做缓存挡板和用户限领；后置又用编程式事务和行锁扣减 MySQL 库存保证不超卖；再配合 RocketMQ、Canal 等机制把“慢操作”挪到异步链路上去处理，整体思路是：前台快进快出，后台慢慢把账补齐。

2. 扣减数据库库存为什么要用“行锁 + 条件判断”，不是已经在 Redis 里扣过了吗？

Redis 的扣减是“第一道坝”，更多是防止瞬时流量把数据库打爆，以及降低超卖概率；但它本质上是缓存，不具备强一致性保证。真正能兜底的是数据库里的那一行记录。

SQL 里这段条件：

UPDATE t_coupon_template
SET stock = stock - #{decrementStock}
WHERE shop_number = #{shopNumber}
  AND id = #{couponTemplateId}
  AND stock >= #{decrementStock}

有两个关键点：

  • stock >= #{decrementStock}：防止在极端并发下出现“Redis 认为还有 1，MySQL 实际已经减到 0 了”这种情况，多加这一条件后，多出来的那次扣减会直接返回 0 行受影响；

  • 这条 UPDATE 会走行锁，同一行上的库存扣减是串行的，不会出现两个线程同时对同一库存做运算再覆盖的情况。

可以理解为：Redis 负责挡住大部分脏并发，MySQL 负责兜底保证数据库里这笔账不会错。

3. 往 Redis 里写用户领券缓存，为什么要“写后再查一次”？

从代码逻辑看确实有点“八股”，但背景是这样的：在 Redis 持久化和主从复制都比较极端的情况下，我们没法完全信任“写入返回成功”就等于数据真的稳定落地了。

几个典型风险场景：

  • 只开 AOF，刷盘策略不是 always，那就有可能刚写完还没刷到磁盘就宕机了；

  • 主从复制是异步的，主节点写成功返回客户端，但还没来得及同步到从节点，主节点刚好宕机，从节点被提升为主，就丢掉了那条数据。

所以在写完 ZSet 之后，再来一次 score 查询：

  • 能查到就当做一切正常；

  • 查不到，就再尝试写一次，尽量把“因为异常导致的漏写概率”再压一压；

  • 查的时候异常了，就直接兜底再写一遍。

这套操作不是为了“绝对不丢”，而是把丢的概率尽量压到很低，并且逻辑都集中在一个地方，后续要改可以统一改。

4. v1 版本里，整个扣库存 + 写 Redis + 发 MQ 都是在一个事务里做的，会有什么问题？

从代码上看，v1 的主流程大概是这样的：

  • Redis Lua 扣减库存、校验限领；

  • 进入事务：扣减 MySQL 库存、插入用户领券记录、写 Redis 用户优惠券 ZSet、写后查校验、发送延时 MQ。

从“正确性”角度看，事情都做完了再提交，顺序非常安全；但从“秒杀性能”角度看，这么设计有几个明显的问题：

  • 事务里做了大量非必要的耗时操作（访问 Redis、访问 MQ），事务时间被拉长，数据库连接占用时间也更久；

  • 秒杀活动一旦压上来，事务多、占用时间长，很容易把连接池耗干，反过来拖慢整个服务。

所以你可以把 v1 理解成“功能正确但偏保守”的版本，适合流量没那么夸张、又希望流程一条链闭环的场景。当真正需要压吞吐的时候，就得像后面那样：把慢操作从主事务里剥出去，用异步把链条拆开。

5. 引入 Canal + Binlog 之后，架构上到底解决了什么痛点？

痛点主要来自 v1 里那句：“在一个事务中干太多事”。

Canal 这条链的思路是：

  • 让业务主流程只负责“写好数据库的真相”，例如插入一条 t_user_coupon 的记录；

  • MySQL 把这次变更写入 Binlog；

  • Canal 订阅 Binlog，解析出变更数据，推到 RocketMQ 的 Canal Topic；

  • 引擎里的 CanalBinlogSyncUserCouponConsumer 消费这条消息，再去写 Redis 缓存、发延时 MQ。

这样有几个直接收益：

  1. 1.

    接口事务里只包含“库内的那几步”，Redis 和 MQ 都从主链路中拿掉，接口耗时会明显下降；

  2. 2.

    即便 Redis 或 MQ 临时抖一下，对数据库事务也没有影响，最多只是“缓存晚一点建好”或者“延时消息晚一点发出”；

  3. 3.

    Binlog 天然记录了数据变更的完整历史，对排查问题也很有帮助。

你可以把它看成是：数据库负责写“账本”，Canal 负责把账本里的新记录抄一份发给订阅者，Redis 和 MQ 都只是账本的派生物。

6. 面对 Redis 丢数据、消息异步这些不一致风险，整体怎么跟面试官或同事解释这套取舍？

可以分两层说：

  1. 1.

    先明确场景差异

    • 像订单、转账、12306 这类业务，每一笔都必须“账账对齐”，哪怕牺牲一些吞吐量，也要优先保证强一致，通常会采用数据库主导的扣减方案，Redis 只是配合做缓存；

    • 优惠券这种，偶尔多发一张或者个别请求因为极端情况失败，更多是体验问题，损失可控，不值得为了这一点，强行把所有流量堆到数据库上。

  2. 2.

    再解释具体方案

    • 前置用 Redis + Lua 扣减库存和限领，扛住高并发、降低超卖概率；

    • 后置用 MQ 把“插库 + 写缓存 + 发延时消息”异步化，缩短接口耗时；

    • 如果强调体验，可以在“用券环节”做一次兜底：发现用户缓存里有券但数据库里没记录，可以把缓存删掉、打标记、甚至补发一张券给用户，这属于业务补偿层面的设计。

总结就是：消息队列架构并不是完美无缺，而是它刚好匹配“优惠券秒杀”这种业务的特点，性能、成本和一致性之间的平衡点放在了这里。

优惠券预约通知功能

1. 为什么预约提醒用 RocketMQ 5.x 延时消息，而不是 Redis 或定时任务？

一开始也对比过几种方案：

  • Redis 延时队列 / 自己滚轮时间轮 逻辑实现不难，但本质上还是把大量“几小时、几天后才触发”的数据放在内存里。几百万条预约一上来，Redis 内存会膨胀得很快，性价比不太高，而且一旦做持久化，又会回到 IO 压力的问题。

  • MySQL 存储 + 定时任务扫描 写入简单，但读的压力很大。比如每分钟跑一次任务去扫“即将触发的预约”，大量 where 条件 + 索引扫描，对库的 QPS、磁盘 IO 都很伤。后面还得自己做分批处理、翻页扫描、过期清理，复杂度也不低。

  • RocketMQ 5.x 任意延时消息 延迟这一层交给 MQ 做，数据落盘，不占业务内存，几百万条消息也能扛住。业务侧只需要在创建预约时发送一条延时消息，到点自然会推给消费者，整个链路会简单很多。

综合下来，对于“海量、延迟较长、对时效性有要求”的预约提醒，RocketMQ 5.x 的任意延时消息更贴业务场景，所以最终选了这条路。

2. 用户预约提醒为什么要用位图（bitmap）存到一个 Long 字段里？

如果从建模上讲，“一条提醒一条记录”是最直观的：user_id + coupon_template_id + remind_time + type 做唯一索引就完事了。但真正落到业务上会有几个问题：

  1. 1.

    一个券往往会有很多时间点和提醒方式组合 比如同一张券，用户可能勾了：

    • 开抢前 30 分钟 App 通知

    • 开抢前 15 分钟 App 通知

    • 开抢前 5 分钟 邮件提醒 用行记录存的话，光一张券就三条记录，用户多了以后数据量会非常可观。

  2. 2.

    位图能极大压缩存储 我们约定：

    • 每 5 分钟一个刻度，最多支持提前 60 分钟 → 12 个时间点；

    • 一共最多 5 种提醒方式（目前只用了 APP、邮件两种，但为未来预留）； 于是一个 Long 有 64 位足够用了：

    • 0~11 位表示【提醒方式 0】从 5 分钟到 60 分钟的开关

    • 12~23 位表示【提醒方式 1】……以此类推

    这样一来，一个用户对某张券所有预约信息，就都压在 information 这一个字段里了。

  3. 3.

    位运算读写效率很高

    • 新增提醒：算出对应 bit 的位置，做一次 information ^ bitMap 就能“合并”进去；

    • 判断是否重复：(information & bitMap) != 0 直接知道这个时间点+提醒方式有没有设置过；

    • 取消提醒：同样用异或把对应的位“抹掉”； 对 CPU 来说，这些都是极快的常数时间操作。

所以整体思路是：用少量存储换更好的扩展性和吞吐，而不是把预约当成一堆散落的行记录来操作。

3. 为什么用户预约提醒的表不用分库分表？

这个表专门用来存“用户某张券的预约信息”，主键就是 (user_id, coupon_template_id)。里面没有太多宽字段，所以整体算下来单表容量其实不小：

  • 主键两个 bigint，按 MySQL 页大小 16KB 粗略估算，三层 B+ 树结构可以顶到 2 亿条左右。

  • 我们假设用户量 5000 万，人均预约 4 张券，这个表也还能撑住。

再加上有定时任务清理过期预约记录，数据始终在一个可控的区间，不至于一路膨胀，所以没必要一开始就搞分库分表。

4. 创建优惠券预约提醒整体流程

大致可以分成三步：

  1. 1.

    校验 + 查询券信息

    • 先根据 shopNumber + couponTemplateId 去查优惠券模板；

    • 顺便解决缓存穿透/击穿问题；

    • 再看开抢时间是不是还没开始，已经开始的直接不允许创建预约。

  2. 2.

    创建/更新预约记录（位图操作）

    • 从 t_coupon_template_remind 里查一条 (user_id, coupon_template_id) 记录：

      • 不存在：说明是第一次对这张券做预约

        • 算出 information 的初始位图（根据提醒时间、提醒方式）

        • 把券的 validStartTime 也带进去，后面解析预约时间需要用到

        • 插入新记录

      • 存在：说明这张券已经预约过了

        • 根据 request 计算一个新的 bitMap

        • 先用 information & bitMap 判重，如果已经设过就直接给出提示

        • 没设过的话，用 information ^ bitMap 合并。

  3. 3.

    发送 RocketMQ 延时消息

    • 构造一个 CouponRemindDelayEvent，带上：

      • 用户 ID

      • 券 ID

      • 店铺编号

      • 提醒方式、提醒时间（比如提前 5 分钟）

      • 开抢时间 & 真实触发时间（startTime - remindTime）

    • 用 RocketMQ 5.x 的任意延时能力发送出去，到点由消费者拉起提醒逻辑。

主流程里只做一次 DB 写 + 一次 MQ 发送，复杂计算都在位图工具类里，整体比较轻。

5. 消费者收到延时消息后，为什么还要用线程池进行并行发送提醒？

如果不加线程池，消费者的模式基本就是：一条消息处理完再处理下一条。对于普通业务还好，但在预约场景里，会出现某一刻集中倾斜的情况：

比如 18:00 开抢前 5 分钟，17:55 这一个时间点集中推一波消息。

这个时候消息堆在 MQ 里，如果消费者一条条串行执行，用户能收到通知，但有可能收到得比较晚，体验会有落差。

引入线程池主要是两点考虑：

  1. 1.

    彻底把发送 IO 和 MQ 消费解耦

    • MQ 消费线程只负责把消息转成 DTO 丢给线程池，自己赶紧返回；

    • 真正调 App 推送、邮件服务这些 IO 调用，都放到线程池里异步处理。

  2. 2.

    利用多核 + IO 密集特性 线程池的配置也是针对 IO 密集型任务调过的：

    • 核心线程数：CPU * 2

    • 最大线程数：CPU * 4

    • 队列：SynchronousQueue，尽量不排队，要么直接交给新线程，要么调用方自己执行（拒绝策略是 CallerRunsPolicy）

这样可以在一段时间内压榨出机器的 IO 能力，把这波提醒尽快刷出去，减少“消息已经到点，但用户迟迟没收到通知”的情况。

6. 线程池里任务万一在执行过程中机器宕机，提醒就丢了怎么办？

这个地方专门做了一层“兜底”：

  1. 1.

    先写 Redis，再丢线程池

    • 每条提醒消息会先在 Redis 里写一条 Key，内容是这次提醒的 DTO；

    • Key 的格式里会带上用户 ID、券 ID、提醒时间、提醒类型，确保唯一。

  2. 2.

    同时往 Redisson 延迟队列塞一条“检查任务”

    • 使用 Redisson 的 RDelayedQueue，给这个 Key 延迟 10 秒；

    • 10 秒后，有一个后台线程会从阻塞队列里消费这个 Key。

  3. 3.

    10 秒后检查任务是否完成

    • 如果线程池正常执行完任务，会主动把这个 Redis Key 删掉；

    • 后台线程取到 Key 后：

      • 如果 Key 已经不存在，说明这条提醒已经完整发完，可以忽略；

      • 如果 Key 还存在，说明任务很可能卡在执行过程中，例如机器中途挂了；

        • 这时会把原始 DTO 重新发一条 MQ 消息，再走一遍提醒流程；

        • 最后删掉 Key，避免死循环。

为什么这个方案接受度还挺高？

  • 一方面提醒类任务本身不算强一致，只要大多数能发出去，个别多发、少发对业务影响不致命；

  • 另一方面，这套 Redis 延迟队列是跑在多实例上的，只要不是全体实例一起挂，总会有人起来把这批“待检查 Key”给捞走。

7. 用户取消预约提醒，怎么通过位运算做到“只删某个时间点/提醒方式”？

取消逻辑其实是创建逻辑的一个镜像操作，关键也是位运算：

  1. 1.

    先找出这条记录

    • 还是按 user_id + coupon_template_id 查 t_coupon_template_remind；

    • 没找到就直接提示“模板预约信息不存在”。

  2. 2.

    算出这次要取消的 bit

    • 根据入参里的 remindTime 和 type 调用 calculateBitMap；

    • 拿到一个只在相应位置为 1 的 bitMap。

  3. 3.

    用按位与判断是否真的预约过

    • (bitMap & information) == 0 说明这个 bit 在原来的 information 里就是 0；

    • 换句话说，用户根本没预约这个时间点的提醒，直接提示“您没有预约该时间点的提醒”。

  4. 4.

    用异或把这个 bit“抹掉”

    • bitMap ^= information 之后，得到的是“取消这个时间点之后”的新位图；

    • 如果新的位图是 0，说明这张券已经没有任何提醒了，直接把这条记录删掉；

    • 否则就更新 information 字段，保留其它时间点的提醒。

配合一层乐观锁（update/delete 时带上老的 information 条件），还能顺带防一下“同一时刻新增+取消一起操作”的并发问题。

8. 消费者怎么判断一条延时消息对应的预约是不是已经被取消？为什么要引入布隆过滤器？

判断逻辑分两层：

  1. 1.

    先过布隆过滤器（快速挡一批）

    • 在用户取消提醒时，会把 (couponTemplateId, userId, remindTime, type) 四元组算个 hash，塞到 cancelRemindBloomFilter 里；

    • 消费者拿到消息后，先把这四个字段算同一个 hash，去布隆过滤器里问一声：

      • 不存在：说明这条预约极大概率没有被取消，可以直接认为是有效提醒；

      • 存在：要么是真的取消了，要么是布隆过滤器误判，这时候再查 DB 做精确判断。

  2. 2.

    落到数据库做精确校验

    • 先查 t_coupon_template_remind 有没有这条 (user_id, coupon_template_id) 记录；

      • 没有，说明整张券的所有预约都被删光了，返回“已取消”；

    • 有的话，再用位图算一遍 (bitMap & information)：

      • 如果结果是 0，说明这个时间点的提醒位已经被清除，也是“已取消”；

      • 否则才算“还有效”。

布隆过滤器的作用就是：绝大部分没取消的消息，直接在内存里快速通过，不需要每条都压到 DB。只有少量处于“可能取消”的消息才去查库，大幅降低数据库压力。

优惠券查询 & 折扣金额计算

1. 接口为什么既要查“可用/不可用优惠券”，还要顺带算优惠金额？

从业务上看，前端在结算页其实要的不是“用户有哪几张券”，而是：

  1. 1.

    哪些券当前这笔订单能用，哪些不能用；

  2. 2.

    能用的券里面，各自能减多少钱（立减多少、折多少）；

  3. 3.

    最后按优惠力度从大到小排一排，好让用户一眼看到“最划算”的那张。

所以这个接口干的事其实就是：在查询优惠券列表的基础上，把每张券套到当前订单上算一遍“能减多少钱”，再按金额排个序。

从代码层面来说，查询和计算这两件事本身就强绑定在一起了，拆开反而会让前后端配合更复杂，还得多一个接口做二次计算。

2. 立减券、满减券、折扣券分别是怎么判断可用、怎么计算优惠金额的？

这里的规则基本是按“常见电商玩法”来的，只是写到了代码里：

  1. 1.

    立减券（type = 0）

    • 不看门槛，拿到就能用（当然，实际可用还要看适用范围，比如商品券是否匹配商品）；

    • 计算方式简单粗暴：优惠金额 = maximumDiscountAmount。

  2. 2.

    满减券（type = 1）

    • 需要满足条件金额：

      • 店铺券看的是 orderAmount；

      • 商品券看的是对应 goodsAmount；

    • 如果金额 >= termsOfUse，这张券就“点亮”，优惠金额 = maximumDiscountAmount；

    • 否则这张券就进不可用列表。

  3. 3.

    折扣券（type = 2）

    • 同样有是否满足 termsOfUse 的判断；

    • 可用时先算一个“原始折扣金额”：amount * discountRate；

    • 再跟 maximumDiscountAmount 比一下，上限封顶：

      • 如果“打完折减掉的钱”大于上限，就用上限；

      • 否则用实际折扣额。

这样做的好处是：所有规则都放在券的 consumeRule 里，以 JSON 形式配置，服务层只负责解析并执行规则，不把规则写死在代码里。

3. 多线程版本里，为什么要用 Collections.synchronizedList 来存储可用/不可用优惠券？

因为在并行版本里：

  • 每一个 CompletableFuture.runAsync 任务都会根据规则，往 availableCouponList 或 notAvailableCouponList 里 add 一条记录；

  • 这些 add 操作是同时发生的，并不是一个任务结束后再开始下一个。

如果还是用普通的 new ArrayList<>()，在多线程环境里会有几个隐患：

  • 多个线程同时修改内部数组，size 还没更新完就又来一次 add，可能直接抛异常；

  • 严重点会出现数组越界、数据覆盖等问题，特别难排查。

Collections.synchronizedList 的底层做法其实很直接：

  • 内部包了一层 SynchronizedList，所有对底层 list 的操作都加了一把 mutex 锁；

  • 多线程环境下，同一时刻只有一个线程能执行 add / remove 等写操作。

对我们的场景来说，这些集合基本都是“写多读少”，只要能保证写入不乱就够用了，所以用这个方式就比较合适。

4. 为什么不用 CopyOnWriteArrayList，也支持并发写？

CopyOnWriteArrayList 的设计思路是：写操作不加锁，但每次写都复制一份新数组。

这个结构非常适合“读很多、写很少”的场景，比如监听器列表、配置快照等：

  • 绝大多数线程在读，不会被卡住；

  • 偶尔有一次写，多复制一次数组问题也不大。

但我们现在这个场景刚好反过来：

  • 在一次请求生命周期里，这两个列表会被频繁 add，几乎没什么读取操作；

  • 每一次 add 都复制整个数组的话，开销其实比加锁还大，特别是优惠券数量多的时候。

所以这里用 Collections.synchronizedList(new ArrayList<>()) 会更稳一些：

  • 写操作简单粗暴地上锁；

  • 不会频繁复制数组；

  • 这两个集合只在最后排序和返回前端的时候读一次，对读性能没那么敏感。

5. 多线程并行以后，一定会比原来的同步版本快吗？

不一定，甚至在一些压测场景下，多线程版本反而不如单线程稳定，原因大概有这么几类：

  1. 1.

    线程切换 & 调度开销

    • 每个优惠券计算逻辑其实很轻量，几行 BigDecimal 运算 + 一两个 JSON 解析；

    • 如果任务本身不到 1ms，线程创建、调度、上下文切换的成本反而更明显。

  2. 2.

    共享资源竞争

    • 虽然用 synchronizedList 保证了线程安全，但所有线程都在抢同一把锁；

    • 持券数量较多时，锁竞争会比较激烈，多线程就变成了“排队加锁”。

  3. 3.

    JMeter 高并发下，线程池本身也会成为瓶颈

    • 外层还有 Web 容器线程（比如 Tomcat/NIO 线程），内层我们又开一层业务线程池；

    • 压高并发时，两个线程池叠在一起，很容易出现 CPU 飙高、上下文切换过多的情况。

所以这章节最后也特意提了一句：

多线程不是银弹，用得不对，性能不一定提升，有时甚至会掉。真正要不要并行，还得结合实际持券数量、单券计算复杂度、机器配置等因素，用压测数据说话。

6. 既然多线程优化不一定有收益，为什么还要写个多线程版本呢？

这章更像是一个“实践+反思”的过程，而不是单纯炫技：

  • 一方面，把如何用 CompletableFuture 做并行计算，以及线程安全、线程池参数设置这些细节走了一遍，方便以后遇到类似场景可以直接复用；

  • 另一方面，也顺带告诉大家：

    • 并发编程需要结合场景，不能一上来就觉得“多线程 = 性能提升”；

    • 真正是否有收益，要看实际压测数据，而不是凭感觉。

后面再接上“压测章节”，给出实测的 QPS、响应时间对比，这三章连在一起，其实就是一套完整的思考路径：

串行实现 → 并行改造 → 压测验证 → 结果分析
