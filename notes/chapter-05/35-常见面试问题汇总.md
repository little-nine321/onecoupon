## 3. 创建优惠券模板：责任链模式

### 3.1 高频问题

第 35 小节首先复盘创建优惠券模板的责任链问题：

- 为什么要用责任链模式？
- 创建优惠券模板会走哪些责任链处理器？
- 责任链模式如何实现？
- 责任链执行遇到异常如何中断？
- 如何复用责任链模式？

### 3.2 项目中的业务背景

创建优惠券模板时，需要做很多校验：

- 参数非空校验。
- 优惠券基础规则校验。
- 库存、时间、领取规则校验。
- 券类型和消费规则匹配校验。

如果全部写在一个 `createCouponTemplate` 方法里，这个方法会越来越长，后续新增校验规则也容易改坏老逻辑。责任链模式把每个校验步骤拆成独立处理器，主流程只负责按顺序执行。

### 3.3 责任链的简化代码示例

```java
public interface ChainFilter<T> {

    void handler(T requestParam);
}
```

```java
@Component
public class NotNullChainFilter implements ChainFilter<CreateCouponTemplateReqDTO> {

    @Override
    public void handler(CreateCouponTemplateReqDTO requestParam) {
        if (requestParam == null || requestParam.getName() == null) {
            throw new ClientException("优惠券模板参数不能为空");
        }
    }
}
```

```java
@Component
public class BaseRuleChainFilter implements ChainFilter<CreateCouponTemplateReqDTO> {

    @Override
    public void handler(CreateCouponTemplateReqDTO requestParam) {
        if (requestParam.getValidEndTime().before(new Date())) {
            throw new ClientException("优惠券结束时间不能早于当前时间");
        }
    }
}
```

执行责任链时，只要某个处理器抛出异常，后续处理器不会继续执行。

```java
for (ChainFilter<CreateCouponTemplateReqDTO> chainFilter : chainFilters) {
    chainFilter.handler(requestParam);
}
```

### 3.4 Spring 语法解释

`@Component` 表示把当前类交给 Spring 容器管理。

```java
@Component
public class DemoHandler {
}
```

被 Spring 管理后，其他类就可以通过构造器注入使用它。

```java
@Service
@RequiredArgsConstructor
public class DemoService {

    private final DemoHandler demoHandler;
}
```

`@RequiredArgsConstructor` 是 Lombok 注解，会为 `final` 字段生成构造方法。Spring Boot 推荐构造器注入，因为依赖关系更清晰，也方便测试。

## 4. 创建优惠券模板：分库分表

### 4.1 高频问题

- 为什么优惠券模板表需要考虑分库分表？
- 为什么单表上限常按 2000 万左右估算？
- 为什么模板表主要按店铺编号分片？
- 如果查询没有带分片键会发生什么？
- 为什么使用 ShardingSphere，而不是直接上分布式数据库？

### 4.2 项目中的业务背景

优惠券模板是商家维度的数据。大型平台里商家数量多，每个商家可能长期创建大量活动券。如果所有模板都堆在一张表，后续查询、索引维护、归档、备份都会越来越慢。

项目按 `shop_number` 做分片，原因是大多数模板查询都天然带商家维度。

典型查询：

```sql
select *
from t_coupon_template
where shop_number = ?
  and status = ?;
```

如果 SQL 带了分片键，ShardingSphere 可以把请求路由到具体分片。如果没有分片键，就可能广播到所有分片，性能和稳定性都会下降。

### 4.3 ShardingSphere 配置示例

```yaml
spring:
  shardingsphere:
    rules:
      sharding:
        tables:
          t_coupon_template:
            actual-data-nodes: ds_0.t_coupon_template_${0..15}
            table-strategy:
              standard:
                sharding-column: shop_number
                sharding-algorithm-name: coupon_template_hash_mod
        sharding-algorithms:
          coupon_template_hash_mod:
            type: HASH_MOD
            props:
              sharding-count: 16
```

这段配置表示：

- 逻辑表：`t_coupon_template`。
- 实际表：`t_coupon_template_0` 到 `t_coupon_template_15`。
- 分片字段：`shop_number`。
- 分片算法：哈希取模。

### 4.4 回答边界

分库分表不是银弹。它解决容量和单表性能问题，但也带来复杂度：

- 跨分片查询成本高。
- 分布式事务更复杂。
- SQL 写法要尽量带分片键。
- 后期扩容迁移成本高。

面试回答时要说明：项目选择分库分表，是因为优惠券模板、用户优惠券这类表具有明显的商家或用户维度，适合水平拆分。

## 5. 操作日志与防重复提交

### 5.1 操作日志

优惠券模板是商家后台的核心资产。创建、修改、关闭模板都需要可追踪。操作日志解决的是“谁在什么时候改了什么”的问题。

项目使用操作日志框架，而不是每个接口手写日志，主要是为了统一格式、减少侵入、避免遗漏。

简化示例：

```java
@LogRecord(
        success = "创建优惠券模板，模板名称：{{#requestParam.name}}",
        type = "CouponTemplate",
        bizNo = "{{#requestParam.shopNumber}}"
)
public void createCouponTemplate(CreateCouponTemplateReqDTO requestParam) {
    couponTemplateMapper.insert(convert(requestParam));
}
```

这里的表达式会从方法参数中取值，生成业务可读的日志。

### 5.2 日志失败是否回滚业务

通常不应该因为日志记录失败而回滚主业务。优惠券模板创建成功后，即使日志写入失败，也不应该让商家感知为创建失败。更合理的做法是：

- 主业务事务和日志记录边界分开。
- 日志失败记录错误日志或进入补偿。
- 核心链路优先保证业务正确。

### 5.3 防重复提交

防重复提交解决的是用户或前端短时间内重复点击导致重复创建、重复发放的问题。

分布式部署下，JVM 本地锁不能解决问题。请求可能被网关负载均衡到不同实例，所以项目使用 Redis/Redisson 分布式锁。

```java
RLock lock = redissonClient.getLock("coupon:create:" + shopNumber + ":" + requestId);
boolean locked = lock.tryLock(0, 10, TimeUnit.SECONDS);

if (!locked) {
    throw new ClientException("请求处理中，请勿重复提交");
}

try {
    doCreateCouponTemplate();
} finally {
    lock.unlock();
}
```

`tryLock` 比直接阻塞等待更适合接口防重。如果拿不到锁，说明同一个请求正在处理中，直接提示用户即可。

## 6. 库存操作与 RocketMQ 延时关闭模板

### 6.1 库存并发修改

优惠券模板库存是典型高并发字段。并发增加发行量、并发领取、并发秒杀都可能修改库存。

数据库层面常见兜底方式是条件更新：

```sql
update t_coupon_template
set stock = stock - 1
where id = #{couponTemplateId}
  and stock > 0;
```

这条 SQL 的关键是 `stock > 0`。多个请求并发执行时，数据库行锁会串行化同一行更新，条件判断可以避免超卖。

### 6.2 为什么需要 RocketMQ 延时消息

优惠券模板到期后需要自动关闭。可以用定时任务扫描，也可以用 MQ 延时消息。

定时任务扫描的问题：

- 扫描频率低，关闭不够及时。
- 扫描频率高，又会增加数据库压力。
- 多实例部署时还要处理任务竞争。

RocketMQ 5.x 支持任意延时消息，创建模板时发送一条“到期关闭”的延时消息。到点后消费者处理关闭逻辑，天然按事件触发。

```java
rocketMQTemplate.syncSendDelayTimeSeconds(
        "coupon-template-close-topic",
        couponTemplateId,
        delaySeconds
);
```

消费者仍然需要幂等，因为延时消息也可能重复投递。

```java
@RocketMQMessageListener(
        topic = "coupon-template-close-topic",
        consumerGroup = "coupon-template-close-group"
)
public class CouponTemplateCloseConsumer implements RocketMQListener<String> {

    @Override
    public void onMessage(String couponTemplateId) {
        closeCouponTemplateIfNotClosed(couponTemplateId);
    }
}
```

`@RocketMQMessageListener` 表示当前类是 RocketMQ 消费者。`topic` 是消费的主题，`consumerGroup` 是消费者组。

## 7. EasyExcel 批量分发与线程池优化

### 7.1 为什么用 Excel 分发

商家运营活动中，经常需要给指定用户批量发券。Excel 是运营人员最熟悉的载体，适合导入用户 ID、手机号、券模板编号等批量数据。

普通 POI 读取大文件时容易把整份 Excel 加载到内存。EasyExcel 使用流式读取，更适合百万级数据。

```java
EasyExcel.read(file.getInputStream(), CouponTaskExcelObject.class, listener)
        .sheet()
        .doRead();
```

### 7.2 为什么统计行数要异步

上传 Excel 后，如果同步统计行数、解析文件、创建任务，接口会等待很久。项目将耗时步骤异步化，让接口尽快返回任务创建结果。

```java
threadPoolExecutor.execute(() -> {
    int rowCount = countExcelRows(filePath);
    updateTaskRowCount(taskId, rowCount);
});
```

### 7.3 为什么不用 `Executors.newFixedThreadPool`

`Executors.newFixedThreadPool` 默认使用无界队列，任务堆积时可能导致内存压力。生产项目更推荐显式创建 `ThreadPoolExecutor`。

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
        8,
        16,
        60,
        TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(1000),
        new ThreadPoolExecutor.CallerRunsPolicy()
);
```

这样可以明确控制线程数、队列长度和拒绝策略。

## 8. 模板方法重构 MQ 发送

模板方法模式适合“流程固定，但某些步骤不同”的场景。

MQ 发送通常包含固定步骤：

1. 构建消息。
2. 设置 topic/tag/key。
3. 发送消息。
4. 记录发送结果。
5. 失败处理。

可以把固定流程放在抽象父类里，把变化点交给子类。

```java
public abstract class AbstractSendMessageTemplate<T> {

    public final void send(T message) {
        Message<?> mqMessage = buildMessage(message);
        doSend(mqMessage);
        afterSend(message);
    }

    protected abstract Message<?> buildMessage(T message);

    protected void afterSend(T message) {
    }
}
```

`final` 方法表示子类不能重写主流程，防止不同消息发送器把流程改乱。

## 9. 缓存击穿、缓存穿透与 Redis 淘汰策略

### 9.1 缓存击穿

缓存击穿是热点 key 失效后，大量请求同时打到数据库。

优惠券模板查询就是典型场景：热门券模板被很多用户同时访问，如果模板缓存突然过期，数据库会被瞬时请求打满。

项目思路：

1. 先查缓存。
2. 缓存未命中，尝试加分布式锁。
3. 拿到锁后再次查缓存。
4. 仍未命中才查数据库。
5. 写回缓存。

简化代码：

```java
String cache = stringRedisTemplate.opsForValue().get(cacheKey);
if (StrUtil.isNotBlank(cache)) {
    return JSON.parseObject(cache, CouponTemplateDTO.class);
}

RLock lock = redissonClient.getLock("lock:coupon-template:" + templateId);
lock.lock();
try {
    cache = stringRedisTemplate.opsForValue().get(cacheKey);
    if (StrUtil.isNotBlank(cache)) {
        return JSON.parseObject(cache, CouponTemplateDTO.class);
    }

    CouponTemplateDO template = couponTemplateMapper.selectById(templateId);
    stringRedisTemplate.opsForValue().set(cacheKey, JSON.toJSONString(template), 30, TimeUnit.MINUTES);
    return convert(template);
} finally {
    lock.unlock();
}
```

第二次查缓存叫“双重判定”。它能避免多个线程排队拿锁后重复查询数据库。

### 9.2 缓存穿透

缓存穿透是请求查询根本不存在的数据。如果攻击者大量请求不存在的模板 ID，缓存永远查不到，数据库会持续被打。

项目组合使用：

- 布隆过滤器：快速判断 ID 是否可能存在。
- 空值缓存：对不存在结果短暂缓存。
- 分布式锁：避免同一个不存在 key 被并发打穿。

布隆过滤器有误判但没有漏判：它说不存在，一定不存在；它说可能存在，不代表一定存在。

### 9.3 Redis 淘汰策略

教程中强调 Redis 内存淘汰策略，项目适合使用 `volatile-lfu` 这类策略。

原因是优惠券业务有明显热点：热门活动券会被频繁查询，冷门券访问频率低。LFU 按访问频率淘汰，比单纯按最近访问时间的 LRU 更适合热点稳定的场景。

## 10. Excel 分发、深分页与断点续传

### 10.1 批量分发整体流程

Excel 分发大致流程：

1. 商家上传 Excel。
2. 创建分发任务。
3. 解析 Excel 行数据。
4. 通过 MQ 分发任务。
5. 消费者校验用户、库存、限领规则。
6. 写入用户优惠券表。
7. 写入 Redis 用户优惠券列表。
8. 失败记录落表。
9. 前端查询任务进度和失败原因。

### 10.2 为什么拆两个消费者

如果一个消费者里完成所有事情，单条消息处理会很重，失败重试也会牵连所有步骤。拆消费者后，可以把任务解析、用户发券、失败记录等职责拆开，方便扩展和排查。

### 10.3 Lua 在分发中的作用

Lua 脚本可以把 Redis 中的多个操作做成原子执行。例如检查库存、扣库存、判断用户是否领取过，可以放在一个脚本中完成。

```lua
local stock = tonumber(redis.call('HGET', KEYS[1], 'stock'))
if stock <= 0 then
    return 0
end

redis.call('HINCRBY', KEYS[1], 'stock', -1)
redis.call('SADD', KEYS[2], ARGV[1])
return 1
```

Redis 执行 Lua 时是单线程原子执行，中间不会被其他命令打断。

### 10.4 深分页

失败记录可能很多。如果使用：

```sql
select *
from t_coupon_task_fail
where task_id = ?
limit 1000000, 20;
```

数据库需要跳过大量记录，越往后越慢。

更适合用书签分页：

```sql
select *
from t_coupon_task_fail
where task_id = ?
  and id > ?
order by id asc
limit 20;
```

前端或缓存记录上一页最后一条 `id`，下一页从这个位置继续查。

## 11. 消息队列幂等消费

### 11.1 为什么 MQ 不等于业务幂等

RocketMQ 可以保证消息尽力投递，但不保证你的业务只执行一次。只要消费端未成功确认，Broker 就可能重投。

对优惠券系统来说，重复消费可能导致：

- 重复发券。
- 重复扣库存。
- 重复发送提醒。
- 重复写失败记录。

所以消费端必须实现幂等。

### 11.2 Redis + 去重表的组合

Redis 适合做高频挡板：

```java
Boolean success = stringRedisTemplate.opsForValue()
        .setIfAbsent("mq:idempotent:" + messageId, "consuming", 120, TimeUnit.SECONDS);

if (Boolean.FALSE.equals(success)) {
    return;
}
```

去重表适合做记录和兜底：

```sql
create table t_mq_idempotent (
    id bigint primary key,
    message_id varchar(128) not null,
    consumer_group varchar(128) not null,
    status int not null,
    unique key uk_msg_group(message_id, consumer_group)
);
```

Redis 负责快，数据库负责可追踪。

### 11.3 为什么幂等 key 要过期

如果消费中进程宕机，Redis key 永远保留会导致消息一直无法重新消费。设置过期时间后，异常消息有机会再次进入消费逻辑。

但过期时间也不能太短，否则业务还没处理完 key 就过期，重复消息可能进入。时间要根据链路耗时评估。

## 12. 秒杀优惠券

### 12.1 秒杀和普通领券的区别

普通领券更关注正确性，秒杀领券同时关注高并发、库存不超卖、用户不超领和接口快速响应。

项目整体思路是：

- Redis + Lua 做前置库存和限领拦截。
- MySQL 条件更新做最终库存兜底。
- MQ/Canal/Binlog 把后置同步动作异步化。
- 用户领券记录和缓存最终保持一致。

### 12.2 为什么 Redis 扣了还要 MySQL 扣

Redis 是性能挡板，不是最终事实来源。Redis 可能丢数据，也可能和数据库短暂不一致。最终库存必须由数据库条件更新兜底。

```sql
update t_coupon_template
set stock = stock - 1
where id = #{couponTemplateId}
  and stock > 0;
```

如果影响行数为 0，说明数据库侧库存已经不足，必须回滚或补偿 Redis 侧结果。

### 12.3 Canal + Binlog 的意义

如果在一个事务里同时扣数据库、写 Redis、发 MQ，接口耗时会增加，事务持有时间也会变长。

引入 Canal/Binlog 后，可以监听数据库变化，把缓存同步、异步消息等操作从主事务中拆出去。核心思想是：主链路只做必须强一致的写入，其他动作通过异步链路最终一致。

## 13. 优惠券预约提醒

### 13.1 为什么用 RocketMQ 延时消息

预约提醒天然是“未来某个时间触发”的业务。RocketMQ 延时消息比定时任务扫描更贴合事件模型。

用户预约提醒后，系统发送一条延时消息。到时间后消费者检查预约是否仍然有效，再发送提醒。

### 13.2 为什么使用 Bitmap

用户可能选择多个提醒时间、多个提醒方式。如果每种组合都建一条记录，数据量和查询复杂度会上升。

Bitmap 可以用一个整数的二进制位表示多个开关。

```java
long value = 0L;

// 打开第 3 位
value = value | (1L << 3);

// 判断第 3 位是否打开
boolean enabled = (value & (1L << 3)) != 0;

// 关闭第 3 位
value = value & ~(1L << 3);
```

这种方式适合固定数量的开关型状态。

### 13.3 取消预约后如何避免误提醒

消费者收到延时消息后，不能直接发送提醒。必须重新查询预约状态，确认用户没有取消。

如果用户取消了预约，延时消息可能已经发出，不能撤回。所以消费时二次校验是必须的。

## 14. 优惠券查询与折扣金额计算

### 14.1 为什么查询时要计算金额

前端展示用户优惠券时，只展示“可用”不够。用户还需要知道哪张券更划算。结算服务在查询时直接计算优惠金额，可以让前端按抵扣金额展示或默认推荐最优券。

### 14.2 策略模式计算优惠金额

不同券类型计算方式不同，所以项目使用策略模式。

```java
public interface DiscountCalculationStrategy {

    BigDecimal calculate(BigDecimal amount, BigDecimal maximumDiscountAmount, BigDecimal termsOfUse);
}
```

```java
public class FixedDiscountCalculationStrategy implements DiscountCalculationStrategy {

    @Override
    public BigDecimal calculate(BigDecimal amount, BigDecimal maximumDiscountAmount, BigDecimal termsOfUse) {
        if (amount.compareTo(termsOfUse) < 0) {
            return BigDecimal.ZERO;
        }
        return maximumDiscountAmount;
    }
}
```

策略模式的好处是新增券类型时，只需要新增策略实现，而不是改一大段 `if else`。

### 14.3 并发计算不一定更快

第 30 小节使用 `CompletableFuture` 并发计算优惠券，但并发不一定总是更快。

如果用户只有 2 张券，线程调度成本可能比计算成本还高。如果用户有几十张券，并且每张券规则复杂，并发才更可能体现收益。

因此回答时要强调：并发是针对持券数量多、计算链路较重场景的优化，不是无脑替代同步逻辑。

## 15. Spring Boot 与框架语法复盘

### 15.1 Controller / Service / Mapper 分层

```java
@RestController
public class CouponController {

    @PostMapping("/coupon")
    public Result<Void> create(@RequestBody CreateCouponReqDTO requestParam) {
        couponService.create(requestParam);
        return Results.success();
    }
}
```

Controller 负责接收 HTTP 请求，不应该写复杂业务。

```java
@Service
public class CouponServiceImpl implements CouponService {

    @Override
    public void create(CreateCouponReqDTO requestParam) {
        // 业务逻辑
    }
}
```

Service 负责业务编排。

```java
@Mapper
public interface CouponMapper extends BaseMapper<CouponDO> {
}
```

Mapper 负责数据库访问。

### 15.2 Lombok 常见注解

```java
@Data
public class DemoDTO {
    private Long id;
    private String name;
}
```

`@Data` 会生成 getter、setter、toString、equals、hashCode。

```java
@Builder
public class DemoRespDTO {
    private Long id;
    private String name;
}
```

`@Builder` 支持链式构造对象：

```java
DemoRespDTO response = DemoRespDTO.builder()
        .id(1L)
        .name("coupon")
        .build();
```

### 15.3 `@Transactional`

`@Transactional` 表示方法执行在事务中。

```java
@Transactional(rollbackFor = Exception.class)
public void create() {
    insertA();
    insertB();
}
```

如果 `insertB` 抛异常，`insertA` 也会回滚。

注意：事务通常绑定当前线程，异步线程不会自动继承外层事务。
