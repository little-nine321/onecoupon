## 新手先读

## 2. 为什么要并发计算优惠券

用户下单时可能持有很多张优惠券。每张优惠券都需要解析规则、判断商品范围、计算金额。如果全部串行执行，耗时会随着优惠券数量线性增长。

同步版本大致是：

```java
for (CouponTemplateQueryRespDTO each : couponTemplateList) {
    calculate(each);
}
```

并发版本希望变成：

```java
CompletableFuture<Void> task = CompletableFuture.runAsync(() -> calculate(each), executorService);
```

这样多张优惠券可以同时计算。对于优惠券数量较多、单张计算逻辑较复杂的场景，并发能降低接口整体响应时间。

需要注意：并发不是无条件更快。如果优惠券数量很少，并发创建任务、线程调度和结果合并也会有额外开销。

## 3. 线程池定义

项目在 `CouponQueryServiceImpl` 中定义了一个专门用于结算计算的线程池。

```java
private final ExecutorService executorService = new ThreadPoolExecutor(
        Runtime.getRuntime().availableProcessors(),
        Runtime.getRuntime().availableProcessors(),
        9999,
        TimeUnit.SECONDS,
        new SynchronousQueue<>(),
        new ThreadPoolExecutor.CallerRunsPolicy()
);
```

参数解释如下：

- `corePoolSize`：核心线程数，这里使用 CPU 核心数。
- `maximumPoolSize`：最大线程数，也使用 CPU 核心数。
- `keepAliveTime`：非核心线程空闲存活时间。这里核心数和最大线程数相同，所以这个参数影响很小。
- `SynchronousQueue`：不存储任务的阻塞队列，提交任务时需要立即交给工作线程。
- `CallerRunsPolicy`：当线程池无法接收任务时，由提交任务的线程自己执行任务，避免直接丢任务。

如果你不熟悉 Java 线程池，可以先看一个简化示例：

```java
ExecutorService executorService = Executors.newFixedThreadPool(4);

executorService.execute(() -> {
    System.out.println("异步执行任务");
});

executorService.shutdown();
```

项目没有使用 `Executors.newFixedThreadPool`，而是直接使用 `ThreadPoolExecutor`，原因是后者能显式控制队列、拒绝策略和线程数量，更适合生产系统。

## 4. 并发实现的核心代码

并发版本的主流程和上一节一致，区别在于对全场券和指定商品券分别创建异步任务。

```java
List<QueryCouponsDetailRespDTO> availableCouponList = Collections.synchronizedList(new ArrayList<>());
List<QueryCouponsDetailRespDTO> notAvailableCouponList = Collections.synchronizedList(new ArrayList<>());

CompletableFuture<Void> emptyGoodsTasks = CompletableFuture.allOf(goodsEmptyList.stream()
        .map(each -> CompletableFuture.runAsync(() -> {
            JSONObject consumeRule = JSON.parseObject(each.getConsumeRule());
            BigDecimal maximumDiscountAmount = consumeRule.getBigDecimal("maximumDiscountAmount");
            BigDecimal termsOfUse = consumeRule.getBigDecimal("termsOfUse");
            BigDecimal couponAmount = CouponFactory.getCouponByDiscountType(each.getType())
                    .calculate(requestParam.getOrderAmount(), maximumDiscountAmount, termsOfUse);

            QueryCouponsDetailRespDTO queryCouponsDetailRespDTO = BeanUtil.toBean(each, QueryCouponsDetailRespDTO.class);
            queryCouponsDetailRespDTO.setCouponAmount(couponAmount);

            if (couponAmount.compareTo(BigDecimal.ZERO) > 0) {
                availableCouponList.add(queryCouponsDetailRespDTO);
            } else {
                notAvailableCouponList.add(queryCouponsDetailRespDTO);
            }
        }, executorService))
        .toArray(CompletableFuture[]::new));

Map<String, QueryCouponGoodsReqDTO> goodsRequestMap = requestParam.getGoodsList().stream()
        .collect(Collectors.toMap(
                QueryCouponGoodsReqDTO::getGoodsNumber,
                Function.identity(),
                (existing, replacement) -> existing
        ));

CompletableFuture<Void> notEmptyGoodsTasks = CompletableFuture.allOf(goodsNotEmptyList.stream()
        .map(each -> CompletableFuture.runAsync(() -> {
            JSONObject consumeRule = JSON.parseObject(each.getConsumeRule());
            BigDecimal maximumDiscountAmount = consumeRule.getBigDecimal("maximumDiscountAmount");
            BigDecimal termsOfUse = consumeRule.getBigDecimal("termsOfUse");
            List<String> goodsNumbers = JSON.parseArray(each.getGoods(), String.class);

            BigDecimal goodsAmount = goodsNumbers.stream()
                    .map(goodsRequestMap::get)
                    .filter(Objects::nonNull)
                    .map(QueryCouponGoodsReqDTO::getGoodsAmount)
                    .reduce(BigDecimal.ZERO, BigDecimal::add);

            BigDecimal couponAmount = CouponFactory.getCouponByDiscountType(each.getType())
                    .calculate(goodsAmount, maximumDiscountAmount, termsOfUse);

            QueryCouponsDetailRespDTO queryCouponsDetailRespDTO = BeanUtil.toBean(each, QueryCouponsDetailRespDTO.class);
            queryCouponsDetailRespDTO.setCouponAmount(couponAmount);

            if (couponAmount.compareTo(BigDecimal.ZERO) > 0) {
                availableCouponList.add(queryCouponsDetailRespDTO);
            } else {
                notAvailableCouponList.add(queryCouponsDetailRespDTO);
            }
        }, executorService))
        .toArray(CompletableFuture[]::new));

CompletableFuture.allOf(emptyGoodsTasks, notEmptyGoodsTasks)
        .thenRun(() -> availableCouponList.sort((first, second) -> second.getCouponAmount().compareTo(first.getCouponAmount())))
        .join();
```

这段代码的关键点不是金额算法，而是任务编排：

1. 全场券创建一批异步任务。
2. 指定商品券创建另一批异步任务。
3. 两批任务全部完成后，对可用券排序。
4. 最后返回结果。

## 5. `CompletableFuture.runAsync`

`CompletableFuture.runAsync` 用来异步执行一段没有返回值的任务。

```java
CompletableFuture<Void> future = CompletableFuture.runAsync(() -> {
    System.out.println("异步任务执行中");
}, executorService);
```

如果任务有返回值，可以使用 `supplyAsync`。

```java
CompletableFuture<Integer> future = CompletableFuture.supplyAsync(() -> {
    return 1 + 2;
}, executorService);
```

本项目每个任务会直接把结果写入共享列表，所以使用 `runAsync` 即可。

更推荐的学习顺序是：

1. 先理解同步 for 循环。
2. 再理解单个 `runAsync`。
3. 最后理解多个 `CompletableFuture` 通过 `allOf` 汇总。

## 6. `CompletableFuture.allOf`

`CompletableFuture.allOf` 用来等待多个异步任务全部完成。

```java
CompletableFuture<Void> task1 = CompletableFuture.runAsync(() -> System.out.println("任务1"));
CompletableFuture<Void> task2 = CompletableFuture.runAsync(() -> System.out.println("任务2"));

CompletableFuture.allOf(task1, task2).join();
```

项目中使用了两层 `allOf`：

```java
CompletableFuture<Void> emptyGoodsTasks = CompletableFuture.allOf(...);
CompletableFuture<Void> notEmptyGoodsTasks = CompletableFuture.allOf(...);

CompletableFuture.allOf(emptyGoodsTasks, notEmptyGoodsTasks).join();
```

第一层分别等待全场券任务和商品券任务。第二层等待这两大类任务都完成。

`join()` 的作用是阻塞当前线程，直到异步任务执行完成。如果异步任务抛出异常，`join()` 会把异常包装成运行时异常抛出。

## 7. 为什么使用线程安全 List

并发任务会同时向 `availableCouponList` 和 `notAvailableCouponList` 添加元素。如果使用普通 `ArrayList`，多个线程同时修改可能导致数据错乱或异常。

项目使用：

```java
List<QueryCouponsDetailRespDTO> availableCouponList = Collections.synchronizedList(new ArrayList<>());
List<QueryCouponsDetailRespDTO> notAvailableCouponList = Collections.synchronizedList(new ArrayList<>());
```

`Collections.synchronizedList` 会给列表操作加同步保护。

错误示例：

```java
List<Integer> list = new ArrayList<>();

IntStream.range(0, 1000).parallel().forEach(list::add);
```

上面代码在并发场景下不安全。

安全示例：

```java
List<Integer> list = Collections.synchronizedList(new ArrayList<>());

IntStream.range(0, 1000).parallel().forEach(list::add);
```

不过需要注意，`synchronizedList` 只能保证单次操作线程安全。如果遍历和修改同时发生，仍然需要额外同步。本项目是在所有任务完成后才排序和返回，因此这个用法是合理的。

## 8. `Collectors.toMap` 的合并函数

指定商品券需要根据商品编号快速找到请求中的商品金额，所以先把商品列表转成 Map。

```java
Map<String, QueryCouponGoodsReqDTO> goodsRequestMap = requestParam.getGoodsList().stream()
        .collect(Collectors.toMap(
                QueryCouponGoodsReqDTO::getGoodsNumber,
                Function.identity(),
                (existing, replacement) -> existing
        ));
```

`Collectors.toMap` 的第三个参数是 key 冲突时的合并函数。如果请求里出现两个相同商品编号，这里保留第一个。

基础示例：

```java
List<String> names = List.of("a", "b", "a");

Map<String, String> map = names.stream()
        .collect(Collectors.toMap(
                each -> each,
                Function.identity(),
                (first, second) -> first
        ));
```

如果没有第三个参数，重复 key 会抛出 `IllegalStateException`。

## 9. 并发和事务的边界

本节并发计算只读取数据并组装响应结果，没有修改数据库，也没有依赖事务上下文。因此适合并发执行。

如果异步任务中要执行数据库写入，需要额外考虑：

- Spring 事务是否会传递到新线程。
- 多线程写库是否会产生顺序问题。
- 异常后是否需要整体回滚。
- 是否会造成连接池压力。

一个常见误区是认为 `@Transactional` 会自动覆盖异步线程。实际上，Spring 事务基于线程上下文，切到新线程后通常不会自动继承原事务。

```java
@Transactional
public void parentMethod() {
    CompletableFuture.runAsync(() -> {
        // 这里通常不在 parentMethod 的事务上下文中
        updateDatabase();
    });
}
```

本节代码规避了这个问题，因为异步任务只做计算和内存列表追加。

## 10. 并发实现的收益和风险

收益：

- 多张优惠券可以同时计算。
- 用户持券数量较多时，接口响应时间更稳定。
- 结算服务更适合高并发下单场景。

风险：

- 线程池配置不合理会导致 CPU 争抢。
- 共享集合必须线程安全。
- 异步异常需要被正确暴露，否则问题不容易排查。
- 如果每个任务都很轻量，并发开销可能抵消收益。

本项目使用 CPU 核心数作为线程数，属于偏保守的配置。因为本节主要是本地计算，线程数不宜远大于 CPU 核心数。

## 12. 如何运行和测试本节功能

### 12.1 启动服务

启动依赖和上一节一致：

- Nacos。
- Redis。
- MySQL。
- `onecoupon-settlement` 服务。

启动结算服务前，建议先确认 Redis 中已经有用户优惠券列表和优惠券模板缓存。

### 12.2 对比同步与并发接口

先调用同步接口：

```bash
curl -X POST "http://localhost:端口/api/settlement/coupon-query-sync" ^
  -H "Content-Type: application/json" ^
  -H "userId: 1001" ^
  -d "{\"orderAmount\":120.00,\"shopNumber\":10001,\"goodsList\":[{\"goodsNumber\":\"G001\",\"goodsAmount\":80.00},{\"goodsNumber\":\"G002\",\"goodsAmount\":40.00}]}"
```

再调用并发接口：

```bash
curl -X POST "http://localhost:端口/api/settlement/coupon-query" ^
  -H "Content-Type: application/json" ^
  -H "userId: 1001" ^
  -d "{\"orderAmount\":120.00,\"shopNumber\":10001,\"goodsList\":[{\"goodsNumber\":\"G001\",\"goodsAmount\":80.00},{\"goodsNumber\":\"G002\",\"goodsAmount\":40.00}]}"
```

两个接口的业务结果应该一致。区别只在内部执行方式。

### 12.3 验证点

需要检查：

- 同步接口和并发接口返回的可用券数量是否一致。
- 不可用券数量是否一致。
- 每张可用券的 `couponAmount` 是否一致。
- 可用券是否都按优惠金额倒序排列。
- 服务日志是否有异步任务异常。

### 12.4 压测建议

可以给同一个用户准备较多优惠券，然后对比两个接口耗时。

测试时不要只看单次请求，因为单次耗时受 JVM 预热、网络、Redis 状态影响较大。建议连续请求多次后观察平均耗时。

如果并发接口没有明显提升，可能原因包括：

- 用户持券数量太少。
- 单张优惠券计算太简单。
- Redis 查询耗时占主要部分。
- 测试环境 CPU 核心数较少。

## 13. 本节小结

本节不是新增优惠券业务规则，而是优化结算计算的执行方式。

学习重点有三个：

1. 同步逻辑和并发逻辑的业务结果必须一致。
2. 多线程写共享集合必须使用线程安全容器或其他汇总方式。
3. `CompletableFuture.allOf(...).join()` 是等待一批异步任务完成的关键。

理解这一节后，再看真实电商结算链路中的优惠试算、推荐最优券、组合优惠计算，会更容易抓住性能优化的边界。
