## 2. 为什么需要结算服务

优惠券系统前面几章已经完成了模板创建、发放、领取、预约提醒、锁定、核销、退还等能力。到了用户下单阶段，业务方最关心的是：

1. 用户有哪些券？
2. 当前订单能不能用这些券？
3. 每张券能抵扣多少钱？
4. 不可用的券为什么不可用？
5. 可用券如何排序，方便前端默认推荐最优券？

这些能力不适合放在模板服务或分发服务里，因为它们属于下单结算时的实时计算逻辑，所以项目单独提供 `settlement` 模块。

## 3. 接口入口

结算服务的查询入口在 `CouponQueryController` 中。

```java

import com.nageoffer.onecoupon.framework.result.Result;
import com.nageoffer.onecoupon.settlement.dto.req.QueryCouponsReqDTO;
import com.nageoffer.onecoupon.settlement.dto.resp.QueryCouponsRespDTO;
import com.nageoffer.onecoupon.settlement.service.CouponQueryService;
import lombok.RequiredArgsConstructor;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

/**
 * 查询用户优惠券控制层
 */
@RestController
@RequiredArgsConstructor
public class CouponQueryController {

    private final CouponQueryService couponQueryService;

    /**
     * 查询用户可用/不可用优惠券列表，并计算每张可用券的优惠金额
     */
    @PostMapping("/api/settlement/coupon-query")
    public Result<QueryCouponsRespDTO> listQueryCoupons(@RequestBody QueryCouponsReqDTO requestParam) {
        return Results.success(couponQueryService.listQueryUserCoupons(requestParam));
    }

    /**
     * 同步方式查询用户可用/不可用优惠券列表
     */
    @PostMapping("/api/settlement/coupon-query-sync")
    public Result<QueryCouponsRespDTO> listQueryCouponsBySync(@RequestBody QueryCouponsReqDTO requestParam) {
        return Results.success(couponQueryService.listQueryUserCouponsBySync(requestParam));
    }
}
```

这里有两个接口：

- `/api/settlement/coupon-query-sync`：同步实现，适合理解业务流程。
- `/api/settlement/coupon-query`：并发实现，下一节重点解释。

如果你刚开始学习 Spring Boot，需要先理解几个注解：

```java

```

`@RestController` 表示这个类是 Web 接口控制器，方法返回值会直接作为 HTTP 响应体。`@PostMapping` 表示这个方法处理 POST 请求。`@RequestBody` 表示从请求 JSON 中反序列化出 Java 对象。

## 4. 请求参数结构

查询用户优惠券时，前端需要传入订单金额、店铺编号、商品列表。

```java
package com.nageoffer.onecoupon.settlement.dto.req;

import lombok.Data;

import java.math.BigDecimal;
import java.util.List;

/**
 * 查询用户优惠券请求参数
 */
@Data
public class QueryCouponsReqDTO {

    /**
     * 订单金额
     */
    private BigDecimal orderAmount;

    /**
     * 店铺编号
     */
    private Long shopNumber;

    /**
     * 商品列表
     */
    private List<QueryCouponGoodsReqDTO> goodsList;
}
```

`BigDecimal` 是 Java 中处理金额的常用类型。不要用 `double` 表示金额，因为 `double` 是二进制浮点数，可能出现精度误差。

```java
BigDecimal amount = new BigDecimal("99.90");
BigDecimal threshold = new BigDecimal("100.00");

if (amount.compareTo(threshold) >= 0) {
    System.out.println("达到使用门槛");
}
```

`BigDecimal.compareTo` 的返回值含义：

- 返回 `-1`：左边小于右边。
- 返回 `0`：左边等于右边。
- 返回 `1`：左边大于右边。

金额比较不要使用 `equals`，因为 `new BigDecimal("1.0").equals(new BigDecimal("1.00"))` 会返回 `false`，它会比较小数位精度。

## 6. 查询用户优惠券的主流程

同步版本是理解本节最重要的代码。它大致做了以下事情：

1. 从 Redis ZSet 中查询用户持有的优惠券。
2. 根据优惠券模板 ID 批量查询模板缓存。
3. 把优惠券模板按「是否指定商品」分组。
4. 对全场券和指定商品券分别判断是否可用。
5. 计算优惠金额。
6. 对可用优惠券按优惠金额倒序排序。

核心代码结构如下：

```java
@Override
public QueryCouponsRespDTO listQueryUserCouponsBySync(QueryCouponsReqDTO requestParam) {
    // 查询用户拥有的所有优惠券。ZSet value 形如：couponTemplateId_userCouponId
    Set<String> userCouponTemplateIds = stringRedisTemplate.opsForZSet()
            .range(USER_COUPON_TEMPLATE_LIST_KEY + UserContext.getUserId(), 0, -1);

    if (CollUtil.isEmpty(userCouponTemplateIds)) {
        return QueryCouponsRespDTO.builder()
                .availableCouponList(List.of())
                .notAvailableCouponList(List.of())
                .build();
    }

    List<String> couponTemplateIds = userCouponTemplateIds.stream()
            .map(each -> StrUtil.split(each, "_").get(0))
            .toList();

    List<Object> couponTemplateCaches = stringRedisTemplate.executePipelined((RedisCallback<String>) connection -> {
        couponTemplateIds.forEach(each -> {
            String couponTemplateCacheKey = String.format(COUPON_TEMPLATE_KEY, each);
            connection.hashCommands().hGetAll(couponTemplateCacheKey.getBytes());
        });
        return null;
    });

    List<CouponTemplateQueryRespDTO> couponTemplateList = couponTemplateCaches.stream()
            .map(each -> BeanUtil.toBean(each, CouponTemplateQueryRespDTO.class))
            .toList();

    Map<Boolean, List<CouponTemplateQueryRespDTO>> partitionedCouponTemplates = couponTemplateList.stream()
            .collect(Collectors.partitioningBy(each -> StrUtil.isEmpty(each.getGoods())));

    List<CouponTemplateQueryRespDTO> goodsEmptyList = partitionedCouponTemplates.get(true);
    List<CouponTemplateQueryRespDTO> goodsNotEmptyList = partitionedCouponTemplates.get(false);

    List<QueryCouponsDetailRespDTO> availableCouponList = new ArrayList<>();
    List<QueryCouponsDetailRespDTO> notAvailableCouponList = new ArrayList<>();

    goodsEmptyList.forEach(each -> {
        JSONObject consumeRule = JSON.parseObject(each.getConsumeRule());
        BigDecimal maximumDiscountAmount = consumeRule.getBigDecimal("maximumDiscountAmount");
        BigDecimal termsOfUse = consumeRule.getBigDecimal("termsOfUse");
        BigDecimal couponAmount = CouponFactory.getCouponByDiscountType(each.getType())
                .calculate(requestParam.getOrderAmount(), maximumDiscountAmount, termsOfUse);

        QueryCouponsDetailRespDTO queryCouponsDetailRespDTO = BeanUtil.toBean(each, QueryCouponsDetailRespDTO.class);
        queryCouponsDetailRespDTO.setCouponAmount(couponAmount);

        if (couponAmount.compareTo(BigDecimal.ZERO) > 0) {
            availableCouponList.add(queryCouponsDetailRespDTO);
        } else {
            notAvailableCouponList.add(queryCouponsDetailRespDTO);
        }
    });

    Map<String, QueryCouponGoodsReqDTO> goodsRequestMap = requestParam.getGoodsList().stream()
            .collect(Collectors.toMap(
                    QueryCouponGoodsReqDTO::getGoodsNumber,
                    Function.identity(),
                    (existing, replacement) -> existing
            ));

    goodsNotEmptyList.forEach(each -> {
        JSONObject consumeRule = JSON.parseObject(each.getConsumeRule());
        BigDecimal maximumDiscountAmount = consumeRule.getBigDecimal("maximumDiscountAmount");
        BigDecimal termsOfUse = consumeRule.getBigDecimal("termsOfUse");
        List<String> goodsNumbers = JSON.parseArray(each.getGoods(), String.class);

        BigDecimal goodsAmount = goodsNumbers.stream()
                .map(goodsRequestMap::get)
                .filter(Objects::nonNull)
                .map(QueryCouponGoodsReqDTO::getGoodsAmount)
                .reduce(BigDecimal.ZERO, BigDecimal::add);

        BigDecimal couponAmount = CouponFactory.getCouponByDiscountType(each.getType())
                .calculate(goodsAmount, maximumDiscountAmount, termsOfUse);

        QueryCouponsDetailRespDTO queryCouponsDetailRespDTO = BeanUtil.toBean(each, QueryCouponsDetailRespDTO.class);
        queryCouponsDetailRespDTO.setCouponAmount(couponAmount);

        if (couponAmount.compareTo(BigDecimal.ZERO) > 0) {
            availableCouponList.add(queryCouponsDetailRespDTO);
        } else {
            notAvailableCouponList.add(queryCouponsDetailRespDTO);
        }
    });

    availableCouponList.sort((first, second) -> second.getCouponAmount().compareTo(first.getCouponAmount()));

    return QueryCouponsRespDTO.builder()
            .availableCouponList(availableCouponList)
            .notAvailableCouponList(notAvailableCouponList)
            .build();
}
```

上面代码不一定和最终源码逐行完全一致，但业务流程和关键 API 与项目实现一致。学习时建议先按同步流程画出时序图，再阅读并发实现。

## 7. Redis ZSet 在本节的作用

用户优惠券列表存储在 Redis ZSet 中，key 按用户维度组织。

```java
String key = USER_COUPON_TEMPLATE_LIST_KEY + UserContext.getUserId();
Set<String> values = stringRedisTemplate.opsForZSet().range(key, 0, -1);
```

ZSet 的特点是每个元素都有一个 score，可以用来排序。优惠券列表使用 ZSet，通常是为了根据过期时间、创建时间或其他业务字段排序查询。

简单示例：

```java
stringRedisTemplate.opsForZSet().add("user:coupon:list:1001", "2001_90001", 1710000000);
stringRedisTemplate.opsForZSet().add("user:coupon:list:1001", "2002_90002", 1711000000);

Set<String> coupons = stringRedisTemplate.opsForZSet().range("user:coupon:list:1001", 0, -1);
```

这里 value 使用 `templateId_userCouponId` 的组合格式。这样做可以在一个集合中同时保留模板 ID 和用户优惠券 ID，查询模板缓存时使用模板 ID，后续锁定或核销时使用用户优惠券 ID。

## 8. Redis Pipeline

本节需要根据多个模板 ID 查询多个模板缓存。如果循环调用 Redis，每次请求都要经历一次网络往返，性能较差。项目使用 Pipeline 批量发送命令。

```java
List<Object> couponTemplateCaches = stringRedisTemplate.executePipelined((RedisCallback<String>) connection -> {
    couponTemplateIds.forEach(each -> {
        String couponTemplateCacheKey = String.format(COUPON_TEMPLATE_KEY, each);
        connection.hashCommands().hGetAll(couponTemplateCacheKey.getBytes());
    });
    return null;
});
```

Pipeline 的特点：

- 客户端一次性把多个命令发给 Redis。
- Redis 依次执行这些命令。
- 客户端最后一次性拿到多个结果。

普通方式：

```java
for (String id : ids) {
    Object value = redisTemplate.opsForHash().entries("coupon:template:" + id);
}
```

Pipeline 方式：

```java
List<Object> result = redisTemplate.executePipelined((RedisCallback<Object>) connection -> {
    for (String id : ids) {
        connection.hashCommands().hGetAll(("coupon:template:" + id).getBytes());
    }
    return null;
});
```

Pipeline 不会让 Redis 并行执行命令，它减少的是客户端和 Redis 之间的网络往返次数。

## 9. `Collectors.partitioningBy`

项目使用 `Collectors.partitioningBy` 把优惠券模板分成两类：

```java
Map<Boolean, List<CouponTemplateQueryRespDTO>> partitionedCouponTemplates = couponTemplateList.stream()
        .collect(Collectors.partitioningBy(each -> StrUtil.isEmpty(each.getGoods())));
```

含义是：

- `true`：`goods` 为空，表示全场券。
- `false`：`goods` 不为空，表示指定商品券。

基础示例：

```java
List<Integer> numbers = List.of(1, 2, 3, 4, 5);

Map<Boolean, List<Integer>> result = numbers.stream()
        .collect(Collectors.partitioningBy(each -> each % 2 == 0));

List<Integer> evenNumbers = result.get(true);
List<Integer> oddNumbers = result.get(false);
```

`partitioningBy` 只适合分成 true/false 两组。如果要按多个类型分组，应该使用 `Collectors.groupingBy`。

## 10. 优惠金额计算策略

不同优惠券类型的计算方式不同。例如满减券、折扣券、立减券不能写在一个巨大 `if else` 中，否则后续新增券类型会越来越难维护。

项目通过 `CouponFactory` 找到对应的计算策略。

```java
public final class CouponFactory {

    public static DiscountCalculationStrategy getCouponByDiscountType(Integer type) {
        DiscountCalculationStrategy discountCalculationStrategy = COUPON_MAP.get(type);
        if (discountCalculationStrategy == null) {
            throw new ClientException("优惠券类型不存在");
        }
        return discountCalculationStrategy;
    }
}
```

策略接口如下：

```java
package com.nageoffer.onecoupon.settlement.service.strategy;

import java.math.BigDecimal;

/**
 * 优惠券折扣计算策略
 */
public interface DiscountCalculationStrategy {

    /**
     * 计算优惠金额
     */
    BigDecimal calculate(BigDecimal amount, BigDecimal maximumDiscountAmount, BigDecimal termsOfUse);
}
```

这是典型的策略模式。业务代码只关心「我要计算优惠金额」，不关心具体是哪一种券的算法。

一个简化示例：

```java
public interface PayStrategy {
    void pay(BigDecimal amount);
}

public class AliPayStrategy implements PayStrategy {
    @Override
    public void pay(BigDecimal amount) {
        System.out.println("使用支付宝支付：" + amount);
    }
}

public class WechatPayStrategy implements PayStrategy {
    @Override
    public void pay(BigDecimal amount) {
        System.out.println("使用微信支付：" + amount);
    }
}
```

使用策略模式后，新增支付方式只需要新增一个实现类，调用方不用大量修改。

## 11. 全场券与商品券的判断差异

全场券直接使用订单总金额计算。

```java
BigDecimal couponAmount = CouponFactory.getCouponByDiscountType(each.getType())
        .calculate(requestParam.getOrderAmount(), maximumDiscountAmount, termsOfUse);
```

指定商品券只能使用命中的商品金额计算。

```java
List<String> goodsNumbers = JSON.parseArray(each.getGoods(), String.class);

BigDecimal goodsAmount = goodsNumbers.stream()
        .map(goodsRequestMap::get)
        .filter(Objects::nonNull)
        .map(QueryCouponGoodsReqDTO::getGoodsAmount)
        .reduce(BigDecimal.ZERO, BigDecimal::add);

BigDecimal couponAmount = CouponFactory.getCouponByDiscountType(each.getType())
        .calculate(goodsAmount, maximumDiscountAmount, termsOfUse);
```

这里的关键点是：指定商品券不能拿订单总金额判断门槛，否则会导致用户用不符合范围的商品凑单。

## 12. 可用与不可用的判断

项目使用优惠金额是否大于 0 判断优惠券是否可用。

```java
if (couponAmount.compareTo(BigDecimal.ZERO) > 0) {
    availableCouponList.add(queryCouponsDetailRespDTO);
} else {
    notAvailableCouponList.add(queryCouponsDetailRespDTO);
}
```

这背后的业务含义是：如果没有达到门槛，或者指定商品没有命中，策略计算结果会是 0，那么这张券就不能在当前订单使用。

更完整的生产系统通常还会给不可用券附带原因，例如：

```java
queryCouponsDetailRespDTO.setUnavailableReason("未达到满减门槛");
```

本项目这一节重点放在可用性判断和金额计算，所以不可用原因不是主线。

## 13. 排序逻辑

可用优惠券按抵扣金额从大到小排序。

```java
availableCouponList.sort((first, second) -> second.getCouponAmount().compareTo(first.getCouponAmount()));
```

排序后前端可以默认展示最优券。

示例：

```java
List<BigDecimal> amounts = new ArrayList<>();
amounts.add(new BigDecimal("5"));
amounts.add(new BigDecimal("20"));
amounts.add(new BigDecimal("10"));

amounts.sort((first, second) -> second.compareTo(first));

System.out.println(amounts); // [20, 10, 5]
```

## 14. 本节容易混淆的点

第一，用户优惠券和优惠券模板不是同一个概念。用户优惠券表示某个用户真实拥有的一张券，优惠券模板表示券的规则。

第二，Redis 中用户优惠券列表只保存索引信息，具体规则仍然要通过模板缓存查询。

第三，全场券和商品券的金额口径不同。全场券看订单总金额，商品券只看命中商品金额。

第四，优惠券是否可用不是只看状态，还要看当前订单是否满足使用条件。

第五，优惠金额排序只应该对可用券做，不可用券不参与最优券推荐。

测试时重点看这些结果：

- `availableCouponList` 是否包含满足门槛的券。
- `notAvailableCouponList` 是否包含不满足门槛的券。
- 全场券是否按订单总金额计算。
- 指定商品券是否只按命中的商品金额计算。
- 可用券是否按 `couponAmount` 倒序排列。

### 15.5 常见问题

如果返回空列表，优先检查 Redis 用户优惠券 ZSet 是否存在。

如果所有券都不可用，检查订单金额、商品编号和模板 `consumeRule` 是否匹配。

如果接口报 JSON 解析错误，检查模板中的 `consumeRule` 和 `goods` 是否是合法 JSON 字符串。

如果金额计算不符合预期，先用同步接口调试，再对照 `CouponFactory` 中具体策略实现。
