# 第 03 小节：牛券项目代码规范

## 新手先读

代码规范不是背单词表，而是帮助你快速判断一个类大概负责什么。比如 `DTO` 多半是接口传参或返回值，`DO` 多半对应数据库表，`Mapper` 多半负责数据库访问，`Service` 多半负责业务逻辑。

第一次读本节时，建议把命名规则当成“源码导航工具”。后面看到陌生类名时，先根据后缀猜职责，再打开代码验证。

## 1. 本节目标

本节目标是理解项目的命名、分层和代码风格。规范不是形式主义，它会直接影响你阅读代码的速度。

## 2. 教程核心内容提炼

教程主要讲：

- 方法命名。
- 参数命名。
- 领域模型命名规约。
- 代码开发规约。
- 注释规范。
- 消息队列规约。

这些规范在后续代码里会反复出现，例如 `CouponTemplateDO`、`CouponTemplateCreateReqDTO`、`CouponTaskExecuteEvent`、`UserCouponStatusEnum`。

## 3. 方法命名规范

常见规则：

| 动作 | 推荐前缀 | 示例 |
| --- | --- | --- |
| 查询单个对象 | `get` / `find` | `findCouponTemplate` |
| 查询多个对象 | `list` | `listCouponTemplate` |
| 统计数量 | `count` | `countUserCoupon` |
| 新增 | `save` / `create` | `createCouponTemplate` |
| 删除 | `remove` | `removeCouponTemplate` |
| 修改 | `update` | `updateCouponTemplate` |

代码示例：

```java
public interface CouponTemplateService {

    CouponTemplateQueryRespDTO findCouponTemplate(CouponTemplateQueryReqDTO requestParam);

    void createCouponTemplate(CouponTemplateCreateReqDTO requestParam);

    void updateCouponTemplateNumber(CouponTemplateNumberReqDTO requestParam);
}
```

学习时看到方法名，应先推断它的业务意图，再进入实现细节。

## 4. 参数命名规范

### 4.1 对象参数

Controller、Service、Mapper 三层中，请求对象通常命名为 `requestParam`。

```java
public Result<CouponTemplateQueryRespDTO> findCouponTemplate(
        @RequestBody CouponTemplateQueryReqDTO requestParam) {
    return Results.success(couponTemplateService.findCouponTemplate(requestParam));
}
```

好处是统一阅读习惯，避免每个方法都发明一个局部变量名。

### 4.2 单一参数

如果参数是单个 ID、状态、用户标识，直接用语义命名。

```java
CouponTaskQueryRespDTO findCouponTaskById(String taskId);
```

## 5. 领域模型命名

| 后缀 | 含义 | 示例 |
| --- | --- | --- |
| `DO` | Data Object，对应数据库表 | `CouponTemplateDO` |
| `DTO` | Data Transfer Object，请求或响应传输对象 | `CouponTemplateCreateReqDTO` |
| `ReqDTO` | 请求 DTO | `CouponTaskCreateReqDTO` |
| `RespDTO` | 响应 DTO | `CouponTemplateQueryRespDTO` |
| `Configuration` | 配置类 | `DataBaseConfiguration` |
| `Constant` | 常量类 | `MerchantAdminRedisConstant` |
| `Context` | 上下文 | `UserContext` |
| `Enum` | 枚举 | `CouponTemplateStatusEnum` |
| `Event` | MQ 或领域事件 | `CouponTaskExecuteEvent` |
| `Consumer` | MQ 消费者 | `CouponTaskExecuteConsumer` |
| `Producer` | MQ 生产者 | `CouponTaskActualExecuteProducer` |

不要把类命名为 `xxxPOJO`。`POJO` 是泛称，不表达业务语义。

## 6. 分层命名与职责

以 `merchant-admin` 为例：

```text
controller
  接收 HTTP 请求，做参数校验和响应包装

service
  承载业务流程

dao/entity
  数据库表对象

dao/mapper
  MyBatis-Plus Mapper

dto/req
  请求参数

dto/resp
  响应结果

mq
  事件、生产者、消费者

config
  配置类
```

阅读代码时不要跨层混淆：Controller 不应承载复杂业务；Mapper 不应做业务决策；Service 是理解业务流程的核心。

## 7. 代码开发规约

推荐规则：

- 类、方法、变量命名要顾名思义。
- 静态常量使用大写和下划线。
- 捕获异常变量命名为 `ex`，忽略异常命名为 `ignored`。
- 返回值变量常用 `result`。
- 循环变量常用 `each`，Map 遍历变量常用 `entry`。

示例：

```java
Map<String, Integer> couponCountMap = new HashMap<>();
for (Map.Entry<String, Integer> entry : couponCountMap.entrySet()) {
    String couponTemplateId = entry.getKey();
    Integer count = entry.getValue();
}
```

## 8. 注释规范

建议重点给这些内容写注释：

- 复杂业务规则。
- 分布式锁、幂等、缓存一致性等非显而易见逻辑。
- MQ 消息的状态流转。
- 线程池、延时队列、定时任务的边界条件。

不建议写无意义注释，例如：

```java
// 设置名称
couponTemplate.setName(name);
```

这种注释不能提供额外信息。

## 9. MQ 命名建议

消息队列代码建议统一关注：

| 类型 | 命名示例 |
| --- | --- |
| Topic 常量 | `MerchantAdminRocketMQConstant` |
| 事件对象 | `CouponTaskExecuteEvent` |
| 生产者 | `CouponTaskActualExecuteProducer` |
| 消费者 | `CouponTaskExecuteConsumer` |
| 消息包装 | `MessageWrapper` |

看 MQ 代码时要追踪四件事：

- 谁发消息。
- 发到哪个 Topic/Tag。
- 消息体是什么。
- 谁消费，消费失败如何处理。

- 命名规范如何提升项目可维护性？
- 常量类、枚举类、上下文类分别解决什么问题？

## 11. 学习检查清单

- 能根据类名判断它属于哪一层。
- 能根据方法名前缀判断大致动作。
- 能区分数据库对象和接口请求对象。
- 能找到 MQ 的生产者、消费者和事件对象。
